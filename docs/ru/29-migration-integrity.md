# Урок 29: целостность миграций и обновление схемы только вперёд

[English version](../29-migration-integrity.md)

План на 50–65 минут: 10 минут чтения, 10–15 минут запуска примера и минимум 30 минут на задание. HTTP-адаптер урока 28 и consumer урока 27 остаются отдельными нерешёнными заданиями.

## От bootstrap SQL к протоколу обновления

`CREATE TABLE IF NOT EXISTS` не обновляет существующую таблицу. В уроке 13 появились версионируемые миграции; здесь добавляются checksum точных байтов, строгая проверка истории и реальные тесты ошибок и конкуренции. Прочитай [main.go](../../lessons/29-migration-integrity/main.go) и два [встроенных SQL-файла](../../lessons/29-migration-integrity/migrations).

Миграция 1 создаёт `lesson29_messages`. Миграция 2 добавляет положительный `version` для оптимистичного редактирования: существующие строки получают версию 1 без замены текста. Это независимые учебные таблицы: CLI не обновляет урок 28 или backend-референс.

Локальный план явно упорядочен от 1 без пропусков. Журнал БД должен быть точным префиксом этого плана:

```text
plan:    [1:checksum_a, 2:checksum_b]
history: []                         -> применить 1 и 2
history: [1:checksum_a]              -> применить 2
history: [1:checksum_a, 2:checksum_b] -> проверить; не повторять DDL
history: [1:changed_checksum]       -> отказ до нового DDL
history: [2:checksum_b]             -> отказ: пропущен префикс
history: [1:checksum_a, 2:checksum_b, 3:...] -> отказ старому бинарнику
```

Нельзя «исправлять» несовпадение перезаписью checksum или удалением записей журнала. Остановись, сопоставь развёрнутый бинарник и БД, затем согласуй восстановление отдельной проверенной процедурой. Старый бинарник не должен молча понижать версию схемы.

## Хешируются байты, а не смысл SQL

Checksum вычисляется для всего встроенного файла, включая комментарии и последний перевод строки:

```go
func checksum(statement string) string {
    sum := sha256.Sum256([]byte(statement))
    return hex.EncodeToString(sum[:])
}
```

SQL плана — доверенный исходный код внутри бинарника, а не HTTP-ввод. Не добавляй загрузку SQL через endpoint и не подставляй пользовательские имена объектов. Значения версии и checksum записываются в журнал параметрами.

Checksum обнаруживает изменение байтов миграции относительно журнала. Он **не** подтверждает подлинность сборщика, не защищает журнал от атакующего с правом его переписать и не сравнивает живую схему таблицы с ожидаемой. Ручной `ALTER TABLE` этот механизм не обнаружит. Для этих рисков нужны права доступа, ревью, резервные копии и отдельная проверка schema drift.

## Одна транзакция и одна согласованная блокировка

Runner выполняет последовательность на одном `sql.Tx`:

```text
проверить план -> BeginTx(Read Committed)
  -> transaction-level advisory lock
  -> создать/прочитать журнал -> проверить весь применённый префикс
  -> выполнить новый SQL + записать его checksum
  -> Commit -> сообщить об успехе
```

Блокировка берётся **до** создания журнала. Одновременный `CREATE TABLE IF NOT EXISTS` сам по себе не является нашим протоколом синхронизации. Все согласованные runner должны использовать один ключ и одну БД. Ключ этого примера сериализует runner урока 29 даже в их разных тестовых схемах, но не запрещает работу стороннему инструменту, который эту блокировку не использует.

Read Committed даёт последующим командам свежий снимок после ожидания блокировки. Transaction-level lock освобождается при завершении транзакции; у session-level lock другой срок жизни, здесь он не используется. Все команды выполняй через `tx`, а не `db`; закрой строки результата перед следующими командами на том же соединении транзакции.

Все новые миграции и их записи журнала входят в **одну пакетную транзакцию**. Ошибка второго шага откатывает и первый шаг этого запуска. Но версия 1, закоммиченная раньше, сохраняется при ошибке последующего обновления. Отложенное ограничение может отказать на `Commit`: успешного выполнения всех SQL недостаточно.

Передавай ограниченный context в `BeginTx`, ожидание блокировки и запросы. Вызывающий код может прекратить ожидание другого runner. Как и при других записях в БД, потеря ответа commit может оставить результат неизвестным: переподключись и проверь историю перед дальнейшим решением, а не считай любую сетевую ошибку доказательством rollback.

## Запуск на одноразовой БД

Нужны Go, Docker и `openssl`; выполняй команды из корня репозитория. Создай только временный экземпляр со случайным паролем и случайным портом на loopback:

```sh
lesson29_password=$(openssl rand -hex 24)
lesson29_container=$(docker run --rm -d \
  --tmpfs /var/lib/postgresql/data \
  -p 127.0.0.1::5432 \
  -e POSTGRES_USER=course -e POSTGRES_DB=course \
  -e POSTGRES_PASSWORD="$lesson29_password" postgres:17-alpine)
docker exec "$lesson29_container" pg_isready -U course -d course
```

Если БД ещё не готова, повтори readiness-команду перед продолжением. Изменяемый тег образа подходит для локального обучения, а не закрепления production-образа. Не используй production/общую БД, не печатай URL с паролем и не коммить учётные данные.

```sh
lesson29_port=$(docker port "$lesson29_container" 5432/tcp | awk -F: '{print $NF}')
export DATABASE_URL="postgres://course:$lesson29_password@127.0.0.1:$lesson29_port/course?sslmode=disable"
export POSTGRES_TEST_URL="$DATABASE_URL"
go run ./lessons/29-migration-integrity
go run ./lessons/29-migration-integrity
go test -count=1 -v ./lessons/29-migration-integrity
```

Оба запуска печатают одинаковый результат; второй проверяет историю и не повторяет уже применённый DDL:

```json
{"schema_version":2}
```

Это локальный migration CLI, а не HTTP-сервер или production deployment system. Здесь нет down-миграций, автоматического исправления checksum, backup/restore, выбора tenant или оркестрации выкладки приложения.

## Ограничения перед production

Runner намеренно рассчитан на небольшой набор транзакционных SQL-шагов. В файлах не должно быть собственных `BEGIN`, `COMMIT` или `ROLLBACK`: транзакцией владеет runner. Это правило ревью исходников, а не гарантия SQL-парсера. `CREATE INDEX CONCURRENTLY` нельзя выполнить внутри этой транзакции. Не убирай транзакцию только ради такой команды: нетранзакционные миграции требуют отдельного протокола восстановления.

DDL может брать сильные блокировки и мешать работающему приложению. Успех локальной миграции не доказывает zero downtime, ограниченное время production-блокировок или совместимость со старыми экземплярами приложения. Большие backfill и создание индексов в живой системе — отдельная эксплуатационная работа. В настоящем chat backend согласуй схему с версиями reader/writer: checksum не решает этот контракт совместимости.

## Что доказывают тесты

Unit-тесты проверяют порядок плана, SHA-256 точных байтов, строгий префикс, неизвестные/более новые версии, отсутствие конфигурации и отмену до доступа к БД.

PostgreSQL-тесты создают случайную приватную схему на подтест и удаляют только её. Они проверяют сохранение сообщения при обновлении, неизменность времени записей журнала при повторе, изменение применённого SQL, пропущенную/более новую историю, rollback при ошибке SQL и отложенного commit, сохранение ранее закоммиченного префикса, два согласованных runner и ограниченный deadline при блокировке в другой транзакции. В тесте блокировки используется настоящий deadline, а не угаданный sleep для порядка выполнения.

Без `POSTGRES_TEST_URL` SQL-тесты **пропускаются**. Это не доказательство работы миграций или конкуренции в PostgreSQL. Тесты не моделируют потерю сети при commit или rolling deployment в production.

## Задание: одна совместимая миграция soft delete — не реализовано

Добавь миграцию 3 только для этого урока, сохранив оба опубликованных SQL-файла без изменений.

1. Добавь сообщениям nullable timestamp `deleted_at`. У существующих строк должны сохраниться ID, беседа, текст, время создания и версия; время удаления изначально NULL.
2. Добавь частичный индекс истории активных сообщений: область `conversation_id`, порядок `created_at DESC, id DESC`, без soft-deleted строк. В маленьком локальном задании используется обычный транзакционный индекс; не называй это онлайн-миграцией production.
3. Расширь явный встроенный manifest версией 3. Не меняй алгоритм checksum, существующие записи журнала или политику отказа при несовпадении. Не реализуй HTTP soft delete и прежние задания.
4. Добавь тесты **полного** плана из `loadMigrations()`: установка с нуля, обновление с версий 1 и 2 с существующими строками, NULL/default и сохранность данных, колонки/predicate индекса, неизменность повтора и конкурентные runner. Прежний helper намеренно фиксирует исходный пример из двух шагов; сохрани эти тесты и добавь новые отдельно.
5. Смоделируй отказ кандидатной миграции в test-only плане: ни частичная схема, ни запись журнала не должны сохраниться. Также докажи, что изменение уже применённого SQL по-прежнему вызывает отказ, а не автоматический ремонт. Не меняй опубликованные SQL-fixtures ради имитации ошибки.

Критерий завершения: прежние и новые тесты проходят на реальном одноразовом PostgreSQL; версия 3 обновляет существующие данные без переписывания истории; объяснено, что ещё потребуется для выкладки и плана отката. Новая миграция и её тесты остаются твоими.

## Проверки и очистка

Пока временная БД работает:

```sh
gofmt -l lessons/29-migration-integrity/*.go
go test -p 1 -count=1 ./...
go test -race -p 1 -count=1 ./...
go vet ./...
```

Останови только созданный выше экземпляр; временные учебные данные будут удалены:

```sh
docker stop "$lesson29_container"
unset DATABASE_URL POSTGRES_TEST_URL lesson29_password lesson29_port lesson29_container
```

Типичные ошибки: менять старый SQL, чтобы скрыть несовпадение; хешировать нормализованный SQL вместо точных байтов; проверять только последнюю версию; создавать журнал до блокировки; смешивать `db` и `tx`; не закрывать rows или не проверять `Commit`; принимать checksum за проверку живой схемы; считать обычный индекс доказательством zero downtime.

Источники: [Транзакции Go database/sql](https://pkg.go.dev/database/sql#DB.BeginTx), [Advisory locks PostgreSQL](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS), [Транзакционные ограничения CREATE INDEX](https://www.postgresql.org/docs/17/sql-createindex.html).
