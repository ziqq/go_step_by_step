# Урок 31: бюджеты времени и размера исходящего HTTP-ответа

[English version](../31-outbound-http.md)

Выделите минимум 40 минут, из них не меньше 30 — на задание с JSON-контрактом. Задание урока 30 с общим бюджетом маршрутов остаётся без решения и без изменений.

## Место в бюджете не ограничивает саму работу

Урок 30 ограничивает число одновременно работающих обработчиков. Но зависшая зависимость всё равно может занять все места. Огромный ответ расходует память даже при одном активном запросе. Поэтому добавим два независимых ограничения: время операции и размер тела ответа.

Откройте [main.go](../../lessons/31-outbound-http/main.go) и [целевые тесты](../../lessons/31-outbound-http/main_test.go). Небольшой клиент на стандартной библиотеке читает синтетический snapshot сервиса уведомлений. Пример сам запускает loopback-сервер `httptest`, делает GET и завершается. Это не публичный proxy и не deployment.

В read-only референсе backend чата есть похожие границы времени, redirect и размера ответа для внешних провайдеров. Берём принцип, не копируем учётные данные и не меняем тот проект. Простой клиент урока 19 остаётся как опубликован: здесь отдельный пример, а не его незаметная переработка.

## Переиспользуем клиент и сохраняем context вызывающего кода

Конструктор задаёт таймаут в одну секунду и запрещает переход по redirect:

```go
client := &http.Client{
    Timeout: time.Second,
    CheckRedirect: func(*http.Request, []*http.Request) error {
        return http.ErrUseLastResponse
    },
}
```

Клиент можно использовать параллельно. Настраивать его нужно до запросов, не во время работы. Каждый вызов создаёт отдельный запрос через `http.NewRequestWithContext`, сохраняя отмену и deadline вызывающей стороны. Уже отменённый context возвращает ошибку до обращения к transport.

Со стандартным transport Go таймаут клиента охватывает получение и чтение ответа, а не только заголовки. Более короткий deadline вызывающего кода тоже действует. Собственный `RoundTripper` обязан сам учитывать context; байтовый ограничитель не делает произвольный зависающий `Reader` отменяемым. Это механизмы ограниченного вызова, не гарантия realtime-планирования.

## Заголовки ещё не означают завершённую операцию

Ответ из `Do` не доказывает, что body целиком получен. Код сразу откладывает `Body.Close`, принимает только статус `200`, затем читает через байтовую границу:

```go
body, err := io.ReadAll(io.LimitReader(response.Body, maxSnapshotBytes+1))
if err != nil {
    return nil, fmt.Errorf("read snapshot: %w", err)
}
if len(body) > maxSnapshotBytes {
    return nil, ErrResponseTooLarge
}
```

Лимит — 1024 байта. Чтение ровно 1024 байт незаметно приняло бы начало более длинного ответа; дополнительный байт отличает точное попадание от переполнения. Считаем реальные байты, даже без `Content-Length`. Пустое тело разрешено транспортным reader; валидный JSON — отдельное задание.

При ошибке чтения частичный payload не возвращается. Обёртка ошибки сохраняет `errors.Is` для отмены и deadline. При отказе по статусу в ошибку входит только число, не диагностическое тело зависимости. Другие внутренние ошибки могут включать URL: не отдавайте и не логируйте сырые ошибки/URL с credentials или чувствительными query-параметрами.

Отложенный close срабатывает при успехе, ошибочном статусе, переполнении и сбое чтения body. Это не неограниченный drain: отклонённое тело не дочитывается целиком только ради переиспользования соединения. На этих путях reuse может потеряться. При автоматической gzip-распаковке стандартного transport лимит относится к распакованным байтам body; он не ограничивает всю память процесса, заголовки, сжатый трафик, CPU или число активных вызовов. Используйте его вместе с admission, не объявляйте универсальным ограничителем ресурсов.

## Политика redirect и endpoint

`ErrUseLastResponse` оставляет redirect-ответ доступным, не отправляя следующий запрос. Наша проверка статуса отклоняет `3xx` и закрывает body. По адресу назначения redirect эта политика не обращается.

Это **не SSRF-защита произвольного начального URL**. Endpoint должен приходить из доверенной конфигурации сервиса, не из HTTP query или текста сообщения. Локальный HTTP в примере нужен только для тестов; для настоящего удалённого провайдера используйте HTTPS с обычной проверкой сертификатов. Не отключайте TLS-проверку ради успешного запроса.

Цикла повторов приложения здесь нет. Стандартный transport может внутренне повторять некоторые допустимые запросы, поэтому нельзя называть пример exactly-once сетевым протоколом. GET не доказывает идемпотентность записывающего сообщения POST и не выясняет исход неоднозначного commit базы. Здесь нет cookies, токенов провайдеров, proxy endpoint или production-решений о readiness.

```sh

go test -count=1 -v ./lessons/31-outbound-http
go test -race -count=20 ./lessons/31-outbound-http
```

Ожидаемый синтетический ответ:

```json
{"service":"notifications","pending":3}
```

Тесты проверяют точную байтовую границу и переполнение с фиксированными/chunked-ответами, отказ от redirect с нулём посещений target, отмену до заголовков и во время body, таймаут после заголовков, автоматическую gzip-распаковку, закрытие body, ошибки чтения/transport, неправильный URL, заранее отменённый context и параллельный reuse клиента. Порядок отмены задают канальные барьеры; watchdog только завершает зависший тест ошибкой. Это не доказательство production-задержек, поведения TLS/proxy/DNS или устойчивости развёрнутого провайдера.

## Задание: проверить ограниченный snapshot — не реализовано

Добавьте один типизированный адаптер поверх reader этого урока. Не добавляйте HTTP-сервер и не меняйте предыдущие уроки.

1. Валидный snapshot — один JSON-объект ровно с двумя обязательными полями: `service` равен `"notifications"`; `pending` — целое число не меньше нуля. Ноль допустим и должен отличаться от отсутствующего поля. Обычные JSON-пробелы и другой порядок полей разрешены.
2. Отклоняйте неправильный JSON, массив, верхнеуровневый `null`, отсутствующие/null-поля, неизвестные поля, неверный service, отрицательный/дробный/строковый счётчик, второй JSON-документ или непробельный хвост. Не считайте, что стандартный decoder автоматически запрещает повтор ключей или требует точный регистр: политики дубликатов и регистра вне задания.
3. При любой ошибке возвращайте нулевой результат. Транспортные ошибки должны оставаться доступны через `errors.Is`, включая `ErrResponseTooLarge`, `ErrUpstreamStatus`, отмену и deadline. Адаптер не повторяет запросы, не следует redirect и не подменяет context вызывающего кода.
4. Добавьте table-driven decoder tests и тесты адаптера с локальным сервером: допустимый нулевой/ненулевой счётчик, неверные документы, слишком большой body, статус не-200 и отмена. Сохраните опубликованные транспортные тесты без изменений. Адаптер и новые тесты остаются за вами.

Критерий завершения: вызывающий код получает проверенный типизированный snapshot либо нулевой результат и ошибку; частичный результат не считается здоровым. Объясните, почему `200`, небольшой body и один успешный Decode ещё не доказывают соответствие контракту зависимости. Эта заготовка не определяет readiness настоящего backend чата.

## Проверки и типичные ошибки

```sh
gofmt -l lessons/31-outbound-http/*.go
go test -p 1 -count=1 ./...
go test -race -p 1 -count=1 ./...
go vet ./...
```

SQL integration tests прошлых уроков требуют одноразовый PostgreSQL и `POSTGRES_TEST_URL`; иначе они пропускаются. Этому уроку Docker и внешний сервис не нужны.

Типичные ошибки: нулевой таймаут клиента; потеря родительского context; доверие к `Content-Length`; усечение как успешный ответ; незакрытый отклонённый body; неограниченный drain; redirect или произвольный пользовательский URL; утечка диагностики upstream; изменение общего клиента во время запросов; смешение транспорта и JSON-валидации; слепой повтор записи.

Источники: [время жизни и таймаут HTTP-клиента](https://pkg.go.dev/net/http#Client), [request context](https://pkg.go.dev/net/http#NewRequestWithContext), [отказ от redirect](https://pkg.go.dev/net/http#ErrUseLastResponse), [чтение с байтовой границей](https://pkg.go.dev/io#LimitReader).
