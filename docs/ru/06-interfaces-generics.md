# Урок 6: интерфейсы, type assertions, generics и границы пакетов

## Цель

После урока вы должны уметь:

- определять небольшой интерфейс в месте его использования;
- понимать, что в Go интерфейсы реализуются неявно;
- использовать безопасную форму type assertion с `comma-ok`;
- писать небольшую generic-функцию с ограничением типа;
- понимать, когда новый пакет создаёт настоящую границу ответственности, а не просто добавляет папки.

Backend часто работает с несколькими конкретными типами через одно узкое поведение: сообщения, системные события, записи хранилища или HTTP-ответы могут предоставлять одну небольшую операцию. Интерфейс делает такую границу явной без наследования.

## 1. Интерфейсы описывают поведение

Интерфейс содержит сигнатуры методов, но не данные. `Renderable` говорит только о том, что значение умеет отрисовать себя:

```go
type Renderable interface {
	Render() string
}
```

`Message` и `SystemEvent` удовлетворяют интерфейсу, потому что у обоих есть метод `Render() string`. Никакого явного объявления не требуется:

```go
type Message struct {
	ID      int
	Author  string
	Content string
}

func (m Message) Render() string {
	return fmt.Sprintf("message #%d from %s: %s", m.ID, m.Author, m.Content)
}

type SystemEvent struct {
	Kind string
}

func (e SystemEvent) Render() string {
	return fmt.Sprintf("event: %s", e.Kind)
}
```

Compile-time assertions в примере делают эту связь заметной и сразу ломают сборку, если метод переименуют или изменят его сигнатуру:

```go
var _ Renderable = Message{}
var _ Renderable = SystemEvent{}
```

## 2. Используйте минимальный интерфейс на границе потребителя

Срез значений `Renderable` может содержать разные конкретные типы:

```go
func renderAll(items []Renderable) []string {
	result := make([]string, 0, len(items))
	for _, item := range items {
		result = append(result, item.Render())
	}

	return result
}

items := []Renderable{
	Message{ID: 1, Author: "Anton", Content: "Hello"},
	SystemEvent{Kind: "message.created"},
}
```

Вызывающему коду не нужно знать, как именно отрисовывается каждое значение. В backend это полезно, когда handler зависит от одной способности, но не должен зависеть от конкретной реализации хранилища или транспорта.

Делайте интерфейсы маленькими. Интерфейс с одним-двумя методами проще реализовать, заменить fake-реализацией и протестировать, чем большой интерфейс для всей подсистемы. Если это сохраняет ясность владения контрактом, определяйте интерфейс там, где он нужен потребителю.

## 3. Type assertion возвращает конкретное значение

Интерфейсное значение содержит динамическое конкретное значение и его тип. Type assertion проверяет, имеет ли динамическое значение нужный тип. Безопасная форма использует `comma-ok`:

```go
func renderAuthor(item Renderable) (string, bool) {
	message, ok := item.(Message)
	if !ok {
		return "", false
	}

	return message.Author, true
}
```

Вызов `renderAuthor` для `SystemEvent` вернёт `false`, а не вызовет panic. Прямая assertion без `, ok` паникует при другом типе:

```go
message := item.(Message)
```

Когда для разных конкретных типов нужно разное поведение, используйте type switch:

```go
switch value := item.(type) {
case Message:
	fmt.Println(value.Author)
case SystemEvent:
	fmt.Println(value.Kind)
default:
	fmt.Println("unknown renderable")
}
```

Value receiver означает, что и `Message`, и `*Message` удовлетворяют `Renderable`, но их динамические типы всё равно различаются. Assertion для `Message` не совпадёт с `*Message`. Проверяйте именно ожидаемый тип или не извлекайте конкретный тип, если достаточно метода интерфейса.

## 4. Generics делают алгоритмы переиспользуемыми и типобезопасными

Функция `first` работает с любым сравнимым типом. Ограничение `comparable` разрешает использовать `==` и `!=`:

```go
func first[T comparable](values []T, want T) (T, bool) {
	for _, value := range values {
		if value == want {
			return value, true
		}
	}

	var zero T
	return zero, false
}
```

Компилятор выводит `T` из аргументов:

```go
state, ok := first([]string{"queued", "sent", "failed"}, "sent")
id, found := first([]int{10, 20, 30}, 20)
```

Generics полезны, когда алгоритм одинаковый, а меняется только тип элементов. Это не повод заменять ими любой интерфейс: интерфейс описывает общее поведение разных типов, а type parameter сохраняет конкретный тип элемента в переиспользуемом алгоритме.

Нулевое значение `T` получается через `var zero T`. Возврат вместе с `false` не заставляет придумывать специальное значение, которое само может быть корректным входом.

## 5. Границы пакетов — это границы ответственности

Пока пример маленький, оставляйте один пакет. Создавайте пакет, когда он владеет целостной ответственностью и предоставляет полезный API другому пакету. Граница пакета должна отвечать на три вопроса:

- Какие типы и функции публичны?
- Какие детали должны остаться приватными?
- Кто владеет контрактом интерфейса?

Возможная форма backend-проекта:

```text
cmd/api/main.go
internal/render/message.go
internal/render/event.go
internal/httpapi/handler.go
```

Не создавайте `pkg`, `repository`, `service` или `factory` только потому, что эти названия звучат архитектурно. Пакет оправдан стабильной ответственностью, а не предпочтительной структурой папок. Делайте детали реализации непубличными, пока они действительно не понадобились другому пакету.

## 6. Прочитайте пример вместе с тестами

В примере один интерфейс используется для разнородных renderable-значений, одна безопасная type assertion — для редкого случая, когда нужно узнать автора, и один generic-алгоритм — для поиска сравнимых значений. Тесты покрывают обычный вывод, сохранение порядка, пустой вход, неудачную assertion, строки, числа и отсутствующее значение.

Интерфейс намеренно маленький. Если будущему HTTP-handler нужен только `Render`, он сможет зависеть от `Renderable`, а не от `Message`, `SystemEvent` или большого интерфейса сервиса.

## Частые ошибки

- Искать явное ключевое слово `implements`: в Go его нет.
- Определять большой интерфейс до появления потребителя.
- Использовать прямую type assertion, когда динамический тип может отличаться.
- Путать статический тип интерфейсного значения с динамическим конкретным типом.
- Использовать generics там, где небольшой интерфейс яснее описывает поведение.
- Возвращать магический ноль или sentinel без отдельного признака успеха.
- Создавать пакеты только ради переноса файлов, без ответственности и владельца.
- Делать все типы и функции нового пакета публичными по умолчанию.

## Практика

Реализуйте задания в `lessons/06-interfaces-generics/main.go` и добавьте целевые тесты в `main_test.go`.

1. Добавьте `FileAttachment` с полями `Name` и `Size`. Сделайте его реализацией `Renderable` с выводом вроде `file: report.pdf (2048 bytes)`, добавьте его в `main` и протестируйте.
2. Добавьте generic-функцию `count[T comparable](values []T, want T) int`. Протестируйте пустой срез, отсутствующее значение и повторы для строк и чисел.
3. Добавьте `renderKind(item Renderable) string` с type switch. Возвращайте `message` для `Message`, `system_event` для `SystemEvent` и `unknown` для другого типа, реализующего `Renderable`.
4. Не увеличивайте интерфейсы и не добавляйте отдельный пакет только ради этой практики. В коротком комментарии укажите, какой будущий backend-потребитель должен владеть `Renderable`.
5. Сохраните все существующие тесты зелёными и добавьте тесты для каждого нового поведения, включая отрицательные и пустые случаи.
