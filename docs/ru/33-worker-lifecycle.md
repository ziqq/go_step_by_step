# Урок 33: владей полным временем жизни worker

[English version](../33-worker-lifecycle.md)

Разбери приём задач, отмену и ожидание завершения по отдельности. Запусти тесты с каналами-барьерами, нарисуй временную последовательность конкурентных `Start`/`Stop`, затем выполни задание с ограниченным ожиданием shutdown. Задание с jitter из урока 32 остаётся отдельным и нерешённым.

## Отмена просит остановиться; join подтверждает завершение

Урок 32 передаёт общий дедлайн через попытки и паузы повторов. Процессу также нужно знать, когда фоновая работа действительно вернулась. Одна отмена context этого не доказывает: callback может ещё освобождать ресурсы.

Открой [main.go](../../lessons/33-worker-lifecycle/main.go) и [целевые тесты](../../lessons/33-worker-lifecycle/main_test.go). Локальный пример запускает один синтетический worker, ждёт сигнал начала, запрашивает отмену, дожидается завершения и проверяет отказ новой задаче. Сеть, Docker и обработчик системных сигналов не нужны.

Backend чата, используемый только для чтения, учитывает жизненный цикл процесса и закрывает приём перед ожиданием активной работы. Здесь выделим это правило владения в небольшую группу задач. Референсный backend, HTTP-сервер урока 12 и задания с очередью, outbox и повторами не меняются.

## У одной группы с одним жизненным циклом есть владелец

Создавай `taskGroup` через `newTaskGroup(parent)`; нулевое значение не поддерживается, копировать группу нельзя. Для worker процесса используй родительский context времени жизни процесса. Context запроса подходит только работе, принадлежащей этому запросу.

`Start` отклоняет nil-callback с `ErrInvalidTask`. Пока приём открыт, уже отменённый или просроченный родитель даёт ошибку context без запуска callback. После закрытия приёма через `Stop` корректные новые callback получают `ErrStopping`. Nil из `Start` означает, что callback принят и учтён, а не что он уже успешно выполнен.

Отмена родителя доходит до принятых callback, но владелец всё равно вызывает `Stop` и ждёт его сигнал. Скрытого наблюдателя, превращающего отмену родителя в завершённый join, нет.

## Учти задачу до запуска горутины

Этот фрагмент выполняется с захваченным mutex приёма; `Stop` проверяет и меняет состояние закрытия под тем же mutex:

```go
g.active.Add(1)
g.mu.Unlock()
go func() {
    defer g.active.Done()
    task(g.ctx)
}()
```

Если перенести `Add` внутрь новой горутины, конкурентное ожидание может увидеть ноль до регистрации задачи. Общая блокировка приёма гарантирует: задача либо учтена до закрытия, либо отклонена после него. Затем ожидание работает с набором, в котором уже не появятся новые участники. Каждому принятому callback соответствует один `Done`.

Callback работает вне mutex. Он может сам запросить `Stop`, но затем должен вернуться, а не ждать завершения своей группы: ожидание себя создаст цикл зависимостей. Группа не перезапускается и не переиспользует wait group для второго жизненного цикла.

## Закрой приём, запроси отмену, дождись завершения

Первый `Stop` закрывает приём, отменяет дочерний context и запускает одного ожидающего. Каждый вызов возвращает тот же доступный только для чтения канал завершения. Повторные `Stop` не создают нового ожидающего и не закрывают канал дважды.

Ожидающий публикует завершение только после возврата всех принятых callback:

```go
g.active.Wait()
close(g.done)
```

Отложенные действия callback заканчиваются до вызова `Done` его обёрткой, поэтому получение из закрытого канала завершения следует и за cleanup. Конкурентные вызывающие `Stop` используют это общее подтверждение; один возврат из `Stop` не доказывает, что все задачи уже заметили отмену или закончили работу.

Приём и выполнение — разные события. Задача, принятая перед закрытием, может начать выполнение после возврата `Stop` и получить уже отменённый context. Callback должен проверять его до работы и передавать в блокирующие вызовы. Отмена кооперативная: группа не может принудительно прервать произвольный код. Для демонстрации тесты намеренно удерживают callback после отмены.

Группа владеет учётом времени жизни, а не ёмкостью, сохранностью, повторами или сбором ошибок worker. Она не обеспечивает бюджет конкурентности урока 30. Callback сами сообщают ошибки своих операций; panic следует обычному поведению процесса Go. Общие ресурсы процесса, используемые callback, должны оставаться доступны до join либо явно выбранного завершения процесса.

## У HTTP shutdown своя граница

`http.Server.Shutdown` управляет своим HTTP-сервером; он не ожидает произвольные фоновые горутины. Hijacked-соединения вроде WebSocket тоже требуют собственной координации остановки. Закрытый listener или `ErrServerClosed` не доказывает завершение всей работы процесса.

На границе процесса задай порядок закрытия HTTP-приёма, отмены worker, ожиданий и закрытия общих ресурсов. Этот пример показывает только часть с worker. В задании ограничим ожидание вызывающего, не делая вид, что незавершённый callback уничтожен.

## Запуск из корня репозитория

```sh
go run ./lessons/33-worker-lifecycle
go test -count=1 -v ./lessons/33-worker-lifecycle
go test -race -count=20 ./lessons/33-worker-lifecycle
```

Ожидаемый вывод:

```text
worker joined; new task rejected
```

Тесты покрывают пустую группу, nil-callback, cleanup до join, несколько удерживаемых задач, отмену и дедлайн родителя, отмену дочернего context без отмены родителя, конкурентные повторные остановки, гонки приёма с остановкой, запрос остановки из callback и ошибки вывода. Каналы задают порядок; watchdog лишь прерывают зависшие тесты. Успех race detector не доказывает все возможные расписания, остановку ОС или cleanup БД/WebSocket в развёрнутом сервисе.

## Задание: ограниченное ожидание shutdown — не реализовано

Добавь `Shutdown(ctx context.Context) error` в `taskGroup` этого урока. Сохрани `Start`, `Stop` и все опубликованные тесты; не меняй прошлые уроки и не добавляй ещё один менеджер worker.

1. Всегда запрашивай `Stop`, в том числе при уже отменённом context ожидания. Переданный context управляет только длительностью ожидания этого вызывающего; он не должен заменять context worker группы или снова открывать приём.
2. Если общий сигнал join уже закрыт при проверке, возвращай nil даже при отменённом context ожидания. Иначе ожидай join или отмену/дедлайн вызывающего. Если ожидание заканчивается первым, возвращай context-ошибку, распознаваемую через `errors.Is`. При гонке join и отмены во время ожидания допустим любой результат; nil требует наблюдения завершения.
3. Истечение ожидания должно оставить настоящий сигнал join открытым, пока работа не закончилась. Не закрывай его, не объявляй успех, не заставляй callback вернуться и не запускай нового ожидающего на каждый вызов. Последующий `Shutdown` с активным context ожидания должен по-прежнему увидеть успешный join.
4. Добавь тесты с каналами для успешного и повторного shutdown, удерживаемого cleanup после дедлайна ожидания, последующего успешного join, предварительной отмены ожидания с обязательным закрытием приёма, приоритета уже завершённого join и конкурентных вызывающих с разными context ожидания. Освобождай все удерживаемые callback при cleanup теста. Сохрани идентичность ошибок отмены/дедлайна и отказ задачам после остановки.

Критерий: тесты показывают, как один вызывающий прекращает ожидание, пока другой продолжает ждать ту же незавершённую работу. Объясни, почему таймаут shutdown требует решения владельца процесса, но не доказывает, что горутины и общие ресурсы можно отбросить. Метод и его тесты остаются за тобой.

## Проверки и типичные ошибки

```sh
gofmt -l lessons/33-worker-lifecycle/*.go
go test -p 1 -count=1 ./...
go test -race -p 1 -count=1 ./...
go vet ./...
```

Для предыдущих SQL-интеграций нужны временный PostgreSQL и `POSTGRES_TEST_URL`, иначе они пропускаются. Типичные ошибки: `Add` после запуска горутины; открытый приём во время `Wait`; закрытие сигнала завершения при отмене; ожидание себя; потеря cleanup при падении теста; новый ожидающий на каждого наблюдателя; повторное использование остановленной группы; закрытие общих ресурсов при ещё работающих callback.
