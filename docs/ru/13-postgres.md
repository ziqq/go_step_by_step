# Урок 13: PostgreSQL, SQL, миграции и транзакции

## Цель

Работать с PostgreSQL из Go через `database/sql`, применять версионированные миграции схемы, писать параметризованные запросы, читать строки и объединять связанные записи в одну транзакцию. Пример атомарно записывает расход и событие аудита.

В целевом chat backend используется похожий общий подход: `database/sql` с pgx stdlib driver, запросы с context, PostgreSQL placeholders, миграции и транзакции. Версия pgx закреплена на v5.7.4, потому что учебный модуль использует Go 1.22, а [в go.mod pgx указана версия Go 1.21](https://raw.githubusercontent.com/jackc/pgx/v5.7.4/go.mod). Адаптер pgx stdlib регистрирует драйвер PostgreSQL для `database/sql`. См. [официальное руководство pgx по database/sql](https://github.com/jackc/pgx/wiki/Getting-started-with-pgx-through-database-sql).

## Запусти локальный PostgreSQL

В одном терминале запусти отдельную локальную базу для обучения:

```sh
docker run --rm --name go-course-postgres -e POSTGRES_USER=go -e POSTGRES_PASSWORD=go -e POSTGRES_DB=go_course -p 127.0.0.1:5432:5432 postgres:16
```

Во втором терминале задай URL подключения и запусти пример:

```sh
DATABASE_URL='postgres://go:go@localhost:5432/go_course?sslmode=disable' go run ./lessons/13-postgres
```

На новой базе программа применит миграции и выведет:

```text
No expenses yet
```

База предназначена для локальных учебных данных. `go run` создаст в ней таблицу учёта миграций, таблицы урока и индекс.

## Открой базу и проверь соединение

Импортируй пакет регистрации драйвера ради побочного эффекта, затем открой выбранное имя драйвера. `sql.Open` проверяет имя драйвера и подготавливает пул; он не доказывает, что сервер доступен. При запуске вызови `PingContext` с deadline.

```go
db, err := sql.Open("pgx", databaseURL)
if err != nil {
	return err
}
if err := db.PingContext(ctx); err != nil {
	_ = db.Close()
	return err
}
```

`*sql.DB` — потокобезопасный пул соединений, а не одно соединение. Задай разумные ограничения пула и закрывай его при остановке процесса. Передавай context запроса или операции каждому запросу, чтобы отмена и deadline дошли до базы.

## Миграции

Пример встраивает три небольших SQL-файла. Он создает `schema_migrations`, берет PostgreSQL transaction-level advisory lock, проверяет примененные версии, запускает каждую новую миграцию и в той же транзакции записывает ее версию. При ошибке миграции транзакция отменит и изменение схемы, и запись в журнале.

Файлы создают:

- `expenses` с ограничениями базы на непустое описание и положительную сумму;
- `expense_events`, связанную с расходом внешним ключом;
- индекс, подходящий для упорядочивания последних расходов.

Считай примененные миграции неизменяемыми. Production-система миграций также должна обнаруживать изменение checksum и безопасно обрабатывать одновременный запуск; в уроке журнал оставлен небольшим, чтобы его можно было понять целиком.

## Параметризованные запросы и Scan

Используй placeholders для значений. В PostgreSQL это `$1`, `$2` и далее. Не вставляй пользовательский ввод в SQL через форматирование строки.

```go
err := tx.QueryRowContext(ctx, `
	INSERT INTO expenses (description, amount_cents)
	VALUES ($1, $2)
	RETURNING id, description, amount_cents, created_at`,
	description,
	amountCents,
).Scan(&expense.ID, &expense.Description, &expense.AmountCents, &expense.CreatedAt)
```

Используй `QueryRowContext`, когда ожидается ровно одна строка, и `QueryContext` для нескольких. Для итератора строк закрой его и после цикла проверь `rows.Err()`; ошибки могут появиться во время чтения.

## Транзакции и ограничения базы

Создание расхода и события — одна операция. Пример начинает транзакцию, добавляет расход, добавляет событие и делает commit только после успеха обоих запросов. Отложенный rollback безопасен и после успешного commit, а при раннем выходе освобождает транзакцию.

Проверка в Go возвращает понятную ошибку до SQL-запроса. Ограничения базы всё равно нужны, поскольку к таблицам могут обращаться другие участки кода или будущие процессы. Оба слоя обеспечивают соблюдение основных правил.

## Индексы и форма запроса

Запрос `recent` сортирует строки по `created_at DESC, id DESC` и ограничивает размер результата. В индексе те же столбцы в том же порядке; `id` даёт стабильный порядок при совпадающих timestamp. Индекс ускоряет подходящее чтение, но занимает диск и замедляет записи, поэтому создавай его под реальные запросы.

## Тесты

Большинству тестов база не нужна: тесты проверяют валидацию и наличие встроенных миграций в порядке версий. Интеграционный тест репозитория запускается, только если `POSTGRES_TEST_URL` указывает на отдельную временную PostgreSQL-базу. Он применяет миграции, создает расход и событие, читает расход и удаляет свою тестовую строку.

```sh
go test ./lessons/13-postgres
```

Чтобы включить интеграционный тест, оставь локальную базу запущенной и используй:

```sh
POSTGRES_TEST_URL='postgres://go:go@localhost:5432/go_course_test?sslmode=disable' go test ./lessons/13-postgres -run TestPostgresRepositoryIntegration -count=1
```

Используй изолированную тестовую базу: тест применяет к ней миграции. Никогда не направляй эту переменную на production или базу с важными данными.

Запусти проверки репозитория:

```sh
go test ./...
go test -race ./...
go vet ./...
```

## Типичные ошибки

- считать, что `sql.Open` уже проверил соединение;
- забыть закрыть `*sql.DB` или строки запроса;
- строить SQL через `fmt.Sprintf` с пользовательскими значениями;
- не проверять `rows.Err()` после чтения;
- зафиксировать только одну часть многошаговой операции;
- полагаться только на Go-валидацию и не задавать ограничения в базе;
- изменять уже примененную миграцию вместо добавления новой версии;
- добавить индекс, не проверив, какой запрос он ускоряет;
- запускать миграции или интеграционные тесты на базе с важными данными.

## Практика: получить расход по ID

Реализуй метод репозитория `getByID(ctx context.Context, id int64) (Expense, error)` в `lessons/13-postgres`.

Требования:

1. Отклоняй ID меньше или равный нулю стабильной ошибкой валидации до обращения к базе.
2. Используй `QueryRowContext` и параметр `$1`; не добавляй ID в SQL конкатенацией.
3. Возвращай отдельную ошибку `ErrExpenseNotFound`, когда `errors.Is(err, sql.ErrNoRows)` истинно.
4. Оборачивай остальные ошибки базы контекстом, сохраняя их доступными для `errors.Is` или `errors.As`.
5. Добавь unit-проверку неверных ID и интеграционные проверки существующего и отсутствующего ID. Интеграционный тест должен по-прежнему запускаться только при заданном `POSTGRES_TEST_URL`.
6. Не изменяй существующие файлы миграций и не добавляй изменение схемы ради этого запроса.

## Критерии завершения

Ты можешь объяснить, зачем после `sql.Open` вызывается `PingContext`, как работают журнал миграций и advisory lock, почему расход и событие используют общую транзакцию, и как индекс соответствует запросу списка. Интеграционный PostgreSQL-тест проверяет создание и чтение на отдельной учебной базе.
