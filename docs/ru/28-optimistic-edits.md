# Урок 28: оптимистичное редактирование без lost update

[English version](../28-optimistic-edits.md)

План на 50–70 минут: 10 минут чтения, 10–15 минут запуска примера и минимум 30 минут на задание. Consumer из урока 27 остаётся отдельным нерешённым заданием.

## Два редактора, одна версия

Два клиента могут прочитать одно сообщение и отправить разные изменения. Безусловный UPDATE позволит поздней записи молча затереть раннюю. Потребуй версию, которую клиент действительно прочитал:

```text
Оба клиента прочитали версию 1.
A отправляет expected_version=1 -> успех; в БД становится версия 2.
B отправляет expected_version=1 -> отказ; текст A остаётся в БД.
```

Прочитай [main.go](../../lessons/28-optimistic-edits/main.go). Проверка и изменение должны быть **одной SQL-командой**, а не чтением в Go с последующим безусловным UPDATE:

```sql
UPDATE lesson28_messages
SET body=$4, version=version+1
WHERE conversation_id=$1 AND id=$2 AND version=$3
RETURNING id, conversation_id, body, version
```

При стандартном для PostgreSQL уровне Read Committed конкурирующий UPDATE может дождаться строки и повторно проверить условие. После успеха другого writer старая версия уже не совпадает. «Оптимистичное» не означает lock-free: ожидание блокировки строки возможно, поэтому передавай request context.

## Запуск с одноразовым PostgreSQL

Нужны Go, Docker и `openssl`; команды выполняются из корня репозитория. Здесь используются временные данные, случайный пароль и случайный порт только на loopback:

```sh
lesson28_password=$(openssl rand -hex 24)
lesson28_container=$(docker run --rm -d \
  --tmpfs /var/lib/postgresql/data \
  -p 127.0.0.1::5432 \
  -e POSTGRES_USER=course -e POSTGRES_DB=course \
  -e POSTGRES_PASSWORD="$lesson28_password" postgres:17-alpine)
docker exec "$lesson28_container" pg_isready -U course -d course
```

Если PostgreSQL ещё не готов, повтори проверку готовности перед продолжением. Изменяемый тег образа подходит для локальной практики, а не закрепления production-образа. Не используй общую/production БД и не печатай/коммить URL с паролем.

```sh
lesson28_port=$(docker port "$lesson28_container" 5432/tcp | awk -F: '{print $NF}')
export DATABASE_URL="postgres://course:$lesson28_password@127.0.0.1:$lesson28_port/course?sslmode=disable"
export POSTGRES_TEST_URL="$DATABASE_URL"
go run ./lessons/28-optimistic-edits
go test -count=1 -v ./lessons/28-optimistic-edits
```

Пример вывода; ID будет другим. Каждый запуск создаёт новую demo-строку и один раз меняет её:

```json
{"id":1,"conversation_id":"lesson-chat","text":"edited once","version":2}
```

## Контракт хранилища и ограничения

`EditDraft` содержит беседу, положительный ID сообщения, ожидаемую версию и новый текст. ID беседы обрезается по краям и содержит 1–80 ASCII-букв, цифр, подчёркиваний или дефисов. После обрезания пробелов текст — корректный UTF-8, 1–280 Unicode code points, без NUL. Ожидаемая версия лежит между 1 и `2^63-2`; запрет верхней границы предотвращает переполнение PostgreSQL `bigint` при увеличении.

Успешный результат приходит из `RETURNING`, а не из угаданной в Go версии или второго SELECT. Даже замена на тот же текст увеличивает версию при совпавшем условии. Успех записи не обещает, что следующий writer не успел изменить строку к моменту получения ответа клиентом.

`sql.ErrNoRows` превращается в `ErrEditRejected` при **любом** несовпадении: старая версия, отсутствующий ID или неверная беседа. Пример намеренно не делает второй запрос, чтобы различить эти случаи. При любой ошибке возвращается пустой `Message`; остальные ошибки БД оборачиваются с сохранением причины. Отказ SQL-ограничения — не конфликт редактирования.

Нельзя получать свежую версию и автоматически повторять с ней старый текст: так ты молча отбросишь работу другого редактора. Клиент должен перечитать данные и решить, объединить изменения или заменить текст. Здесь нет idempotency receipt и особого успешного пути для «того же повтора». Потеря ответа всё ещё может оставить результат неизвестным.

Для этого изменения одной строки достаточно одной SQL-команды. Если вместе с edit нужно записать outbox-событие, обе записи требуют одной явной транзакции, как в уроке 27; отправка события после изменения только в память вернёт окно потери.

В примере нет аутентификации, проверки автора, tenant isolation, состояния удаления, доставки outbox и HTTP-сервера. Условие по беседе — не авторизация. Встроенный [schema.sql](../../lessons/28-optimistic-edits/schema.sql) создаёт учебную таблицу, а не заменяет версионированные production-миграции.

Read-only референс `tetradka/chat/backend/internal/storage/postgres/message_lifecycle.go` тоже проверяет ожидаемую версию при edit. Его настоящий сценарий дополнительно проверяет membership/автора/удаление, ведёт историю и события и имеет другую семантику повторов. Этот урок не заменяет тот протокол.

## Что проверяют тесты

Unit-тесты покрывают нормализацию, неверный/слишком длинный текст, неверные ID/версии, защиту от переполнения, отсутствие БД и заранее отменённый context.

Интеграционные тесты создают отдельную случайную схему для каждого подтеста. Проверяются результат в БД, сохранность строки при старой версии/отсутствующем ID/неверной беседе, ровно один победитель из двух edit с версией 1, увеличение версии при том же тексте, классификация ошибок ограничений и отсутствие изменений после отказа валидации или отмены. Текст, похожий на SQL, остаётся параметром.

Без `POSTGRES_TEST_URL` SQL-кейсы пропускаются. Такой запуск не доказывает конкурентное поведение PostgreSQL. Тесты не моделируют потерю сети при commit и не проверяют авторизацию.

## Задание: HTTP-адаптер с ожидаемой версией — не реализовано

Добавь один локальный адаптер на `net/http` и проверь его через `httptest`. Не меняй семантику writer и не реализуй consumer урока 27.

1. Обработай `PATCH /conversations/{conversation_id}/messages/{message_id}`. Беседу/ID бери из route, а не JSON. Принимай ровно один JSON-объект с `text` и целочисленным `expected_version`; отклоняй неизвестные поля, второй JSON, отсутствующие/неверные значения и тело больше 1 MiB.
2. Передавай request context в небольшой интерфейс редактора на стороне потребителя с текущим контрактом `Edit(context.Context, EditDraft) (Message, error)`. Для тестов адаптера используй детерминированный fake; существующие SQL-тесты проверяют реальный store.
3. Возвращай `200` с JSON сохранённого `Message` при успехе, `400` при неверном вводе, `413` при слишком большом теле, `409` с `{"error":"edit rejected"}` при `ErrEditRejected` и обобщённую JSON-ошибку `500` при неожиданном отказе хранилища. Это статусы приложения, а не полная реализация HTTP `If-Match`.
4. Не повторяй вызов при `ErrEditRejected`, не ищи свежую версию, не раскрывай SQL-ошибку и не возвращай сообщение другой беседы. Несовпавшая беседа и отсутствующий ID остаются тем же отказом `409`, без дополнительного поиска существования.
5. Проверь успех, отказ без второго обращения к store, повреждённый JSON/неизвестные поля/второй JSON/слишком большое тело, неверные route ID и версии, передачу request context и сокрытие внутреннего маркера ошибки. Неверные запросы не должны доходить до редактора.
6. Оставь всё локальным: без публичного сервера, обхода аутентификации, ETag, очереди и новых зависимостей. Опиши доверенную границу аутентификации, необходимую перед публикацией такого route в настоящем сервисе.

Критерий завершения: целевые тесты адаптера и все прежние проверки проходят; отклонённые edit не затирают данные; HTTP-реализация остаётся твоей.

## Проверки и очистка

Пока временная БД работает:

```sh
gofmt -l lessons/28-optimistic-edits/*.go
go test -p 1 -count=1 ./...
go test -race -p 1 -count=1 ./...
go vet ./...
```

Останови только ID временного контейнера, сохранённый выше; его данные намеренно будут удалены:

```sh
docker stop "$lesson28_container"
unset DATABASE_URL POSTGRES_TEST_URL lesson28_password lesson28_port lesson28_container
```

## Типичные ошибки и источники

Типичные ошибки: проверять версию только в Go; убрать условие версии или беседы; присвоить произвольную новую версию клиента; считать любую SQL-ошибку старой версией; автоматически повторять со свежей версией; принимать scoped UPDATE за авторизацию; считать пропущенные SQL-тесты доказательством поведения БД.
