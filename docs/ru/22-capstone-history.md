# Урок 22: итоговый проект III — постраничная выдача истории беседы

Время на урок: 40–55 минут.

На этом шаге защищённое чтение становится ограниченным endpoint истории. Пример проверяет проверенный principal и membership беседы на каждой странице, затем возвращает сообщения от новых к старым с keyset-cursor по паре `(created_at, message_id)`. ID служит tie-breaker: временные метки не обязаны быть уникальными.

Целевой chat-backend отдаёт историю через команду `messages.load` и имеет более богатый контракт: якоря по ID, дополнительные фильтры и history revision. Самостоятельный REST-пример учит стабильной пагинации и ограничению области данных; это не копия протокола и здесь нет согласованного снимка БД между страницами.

## Запуск примера

```sh
go run ./lessons/22-capstone-history
go test ./lessons/22-capstone-history
```

```text
200 OK messages=2 has_more=true
```

Маршрут использует method и path wildcards `ServeMux` из Go 1.22. Значение wildcard читается через `Request.PathValue`; см. [обзор маршрутизации Go](https://go.dev/blog/routing-enhancements). Cursor кодируется URL-safe Base64 без padding согласно [`encoding/base64`](https://pkg.go.dev/encoding/base64#RawURLEncoding).

## Контракт запроса и страницы

- `GET /conversations/{conversationID}/messages` требует principal, уже проверенный доверенным middleware. `withDemoPrincipal` лишь имитирует этот шаг для урока и не является аутентификацией.
- Необязательный `limit` по умолчанию равен 20 и должен быть от 1 до 50. Повторные или некорректные значения отклоняются с `400`.
- Необязательный cursor `before` задаёт исключительную позицию. Страницы упорядочены по `created_at DESC, id DESC`; следующая страница содержит строки строго старше последнего возвращённого кортежа.
- Cursor — это позиция, а не удостоверение доступа. Base64 не является шифрованием или подписью. Обработчик повторно проверяет membership, а запрос хранилища ограничен указанной беседой, даже если клиент изменил cursor.
- Ответ содержит `messages`, `has_more` и, если есть следующая страница, `next_cursor`. In-memory адаптер определяет наличие дополнительной строки после сортировки локальной копии; PostgreSQL-адаптер может выбирать `limit + 1` строку.
- Нет principal — `401`; неправильный путь, query или cursor — `400`; нет membership — `403`; ошибка зависимости закрывает доступ общей ошибкой `500` или `504` при deadline; успех — `200`.

Keyset-пагинация меньше подвержена смещениям через `OFFSET`, когда перед текущей страницей появляются новые сообщения. Нужен стабильный уникальный порядок: только по timestamp можно пропустить или повторить записи с одинаковым временем. In-memory пример сортирует копию для наглядности; реализация на БД должна применять условие по беседе и сравнение кортежа в SQL, а индекс должен учитывать эту область и порядок.

## Что доказывают тесты

Тесты проходят две страницы с одинаковыми timestamp и проверяют отсутствие пропусков и дублей, проверяют membership на каждой странице, запрещают вызов хранилища для отказанного запроса, отклоняют неверный limit и повреждённый cursor, сохраняют пустую страницу как JSON-массив и не возвращают строки другой беседы. Они не доказывают план SQL-запроса, целостность cursor или общий снимок для нескольких запросов.

```sh
gofmt -w ./lessons/22-capstone-history
go test ./lessons/22-capstone-history
go test -race ./lessons/22-capstone-history
```

## Задание — добавить фильтр по времени создания

Расширьте endpoint необязательными query-параметрами `created_from` и `created_to`:

1. Разбирайте оба значения как RFC 3339. `created_from` включается в диапазон, `created_to` не включается.
2. Отклоняйте некорректные значения и диапазон, в котором `created_from` не раньше `created_to`, стабильным ответом `400`.
3. Применяйте тот же диапазон к первой и каждой cursor-странице. Не меняйте кортеж cursor и область membership; при переходе по `next_cursor` клиент должен передавать фильтры дальше.
4. Добавьте целевые тесты границ, пустого диапазона, некорректного ввода и прохода двух страниц с теми же фильтрами. Проверьте, что отказ в membership по-прежнему не вызывает хранилище.

Запланируйте минимум 35 минут. Задание завершено, когда проходят позитивные и негативные случаи, порядок страниц стабилен для одинаковых timestamp, а race detector не находит гонок общего состояния.

## Типичные ошибки

- пагинация только по timestamp, из-за чего теряются строки с одинаковым временем;
- `OFFSET` для изменяющейся истории с предположением, что поздние страницы останутся на месте;
- восприятие cursor, похожего на непрозрачный, как доказательства доступа;
- проверка membership только на первой странице;
- запрос по ID или времени без ограничения областью беседы;
- возврат nil-среза как `null`, когда контракт требует `[]`;
- включение фильтров в cursor с потерей этих фильтров при следующем запросе;
- утверждение, что отдельные запросы страниц используют общий согласованный снимок БД.

## Критерии завершения

Вы можете объяснить порядок `(created_at, id)`, показать, почему сравнение cursor исключительное, доказать проверку авторизации на каждом запросе и описать область SQL-запроса и индекс для PostgreSQL-хранилища истории.
