# Урок 38: ограниченные метрики операций и согласованные histogram

[English version](../38-bounded-metrics.md)

Урок 37 различает исчерпание квоты и ёмкости ограничителя. Для наблюдения этих решений нужны агрегаты с фиксированным словарём, а не временной ряд для каждого principal. Продолжим обзор урока 16: снимок histogram с собственными данными и явные инварианты экспорта. HTTP-адаптер урока 37 остаётся отдельным нерешённым заданием.

## Что именно считаем

Открой [main.go](../../lessons/38-bounded-metrics/main.go) и [целевые тесты](../../lessons/38-bounded-metrics/main_test.go). Нулевое значение `operationMetrics` готово к работе. Используй указатель и не копируй его после начала использования. `Observe(operation, result, elapsed)` записывает одну завершённую операцию с классификацией вызывающего кода; он не выводит HTTP-статус, не авторизует и не ограничивает приём.

| Измерение | Точные сохраняемые значения |
|---|---|
| operation | `history.read`, `message.write`, `other` |
| result | `ok`, `rejected`, `failed`, `other` |
| верхняя граница длительности, секунды | `0.01`, `0.1`, `1`, `+Inf` |

Любое неизвестное написание, включая другой регистр или пробелы, независимо сводится к `other` в каждом измерении. Исходные строки не сохраняются. Всего 12 ячеек. Каждая экспортирует четыре накопительных bucket, сумму и счётчик: ровно **72 значения** в каждом документе, включая нулевые ячейки. Это число рядов приложения на один target до labels, добавляемых сборщиком. Экземпляры и меняющиеся deployment labels всё равно могут умножать объём мониторинга.

Не используй tenant/user/conversation/request ID, исходные URL, токены и тексты ошибок как labels. Хеш ID пользователя тоже создаёт отдельное значение для каждого пользователя. Фиксированные labels ограничивают сохранённое состояние, но не делают management endpoint безопасным для публичного доступа. Read-only референс `internal/metrics/registry.go` целевого backend экспортирует агрегаты операций, а его архитектура защищает `/metrics` отдельной management-границей. Здесь собственная in-memory фикстура, не замена тому registry или его политике доступа.

## Раздельные интервалы внутри, накопительные — снаружи

Массив хранит одно наблюдение ровно в одном непересекающемся интервале. Граница включительна: ноль и ровно 10 ms входят в первый интервал; 10 ms + 1 ns — во второй. Отрицательная длительность возвращает `ErrInvalidDuration` без изменений. Имя метрики заканчивается на `_seconds`; сумма и границы задаются в секундах, не миллисекундах.

Фрагмент цикла накопительного экспорта:

```go
var cumulative uint64
for bin, upper := range [...]string{"0.01", "0.1", "1", "+Inf"} {
    cumulative += cell.bins[bin]
    fmt.Fprintf(&body, "%s_bucket{operation=%q,result=%q,le=%q} %d\n",
        name, operation, result, upper, cumulative)
}
```

В каждой ячейке экспортированные buckets не убывают при росте `le`, а `+Inf` равен `_count`. `_sum` — суммарная длительность, не перцентиль. Среднее не раскрывает хвост задержек; грубые интервалы тоже не восстанавливают точные перцентили. Production-границы выбирают по реальной цели задержки. Фикстура не предоставляет PromQL, scraper, распределённую трассировку, alerts или постоянное хранение.

Целая сумма наносекунд форматируется в десятичные секунды без float-конверсии. Система мониторинга может хранить значения в floating-point и терять точность младших разрядов. Исчерпание count или суммы возвращает `ErrMetricOverflow` до изменения любого bin/count/sum; при исчерпанной сумме ещё можно записать нулевую длительность, пока есть место в count. Это явная учебная политика, а не рекомендация ломать бизнес-запрос из-за телеметрии. Вызывающий код выбирает обработку ошибок телеметрии; нельзя молча утверждать, что отклонённое наблюдение записано.

## Один снимок, затем writer I/O

Один mutex защищает все ячейки и все части наблюдения. `snapshot()` копирует вложенные массивы под ним; результат владеет своими данными. Экспорт сериализует только эту копию после освобождения mutex. Он не читает более новый count при записи старых buckets; медленный writer не удерживает mutex наблюдений. Аллокация буфера, форматирование и writer I/O находятся вне критической секции.

`WritePrometheus(w)` требует ненулевой `io.Writer`, возвращает его ошибку, а короткую запись отмечает `io.ErrShortWrite`. До ошибки часть вывода могла уйти: не дописывай второй документ в тот же ответ и не считай, что ничего не передано. Экспорт не обнуляет и не изменяет счётчики. Каждый writer обеспечивает синхронизацию своего места назначения, если она нужна. Буфер ограничен фиксированным словарём labels и шириной целых чисел; это не обещает постоянную задержку при конкуренции за mutex.

## Запуск из корня репозитория

```sh
go run ./lessons/38-bounded-metrics
go test -count=1 -v ./lessons/38-bounded-metrics
go test -race -count=20 ./lessons/38-bounded-metrics
```

Демо экспортирует полный документ из 74 строк: две строки метаданных и 72 значения. Ниже только фрагмент `history.read` / `ok`; остальные категории тоже присутствуют:

```text
go_course_operation_duration_seconds_bucket{operation="history.read",result="ok",le="0.01"} 2
go_course_operation_duration_seconds_bucket{operation="history.read",result="ok",le="0.1"} 3
go_course_operation_duration_seconds_bucket{operation="history.read",result="ok",le="1"} 3
go_course_operation_duration_seconds_bucket{operation="history.read",result="ok",le="+Inf"} 4
go_course_operation_duration_seconds_sum{operation="history.read",result="ok"} 1.020000002
go_course_operation_duration_seconds_count{operation="history.read",result="ok"} 4
```

Тесты проверяют точные границы и соседние наносекунды, максимальную длительность, неизвестные/приватные входы, независимость категорий, неверный вход, переполнение count/суммы, владение снимками, полный стабильный экспорт, ошибки writer и согласованность конкурентных наблюдений/экспорта. Reentrant writer в тесте записывает новое наблюдение: это выявляет I/O под mutex и проверяет использование прежнего снимка. Корректность не устанавливается scheduling-sleep.

## Практика: HTTP-адаптер только для диагностики

Добавь `newMetricsHandler(m *operationMetrics) (http.Handler, error)` и `ErrInvalidHandler`; сохрани collector и его тесты. Реализуй один адаптер без открытия listener:

1. Nil collector возвращает nil и `ErrInvalidHandler`. Для любого запроса с уже завершённым context вернись до выбора метода без записи headers/body и без наблюдения. Используй spy, считающий записи: статус recorder по умолчанию сам по себе не доказывает отсутствие записи.

2. Поддержи GET и HEAD. Верни 200 с `Content-Type: text/plain; version=0.0.4; charset=utf-8` и `Cache-Control: no-store`. GET возвращает полный документ histogram из одного снимка. HEAD возвращает эти заголовки и ноль байт тела; не вызывай body writer даже с пустым slice.

3. Остальные методы возвращают 405 с `Allow: GET, HEAD` и общим `method not allowed`. Не отражай path, query, headers, идентификаторы или ошибки. Приоритет context и правила методов — явная политика задания.

4. GET/HEAD scrape, отказ метода и уже отменённый запрос никогда не изменяют метрики операций. Не оборачивай адаптер instrumentation операций и не придумывай бизнес-операцию `metrics.scrape`. Не обнуляй счётчики после scrape.

5. Через `httptest` проверь GET, HEAD, отказы методов, отменённый context, полный фиксированный набор labels, повторное чтение и конкурентные наблюдения/scrape. Проверь накопительные buckets и `+Inf == count` внутри каждого документа, заголовки, отсутствие приватного входа в ответе и неизменность наблюдений после чисто диагностического трафика. Не расширяй утверждения об ошибках writer/сети сверх доказанного тестами.

Критерий: объясни предел 72 ряда, накопительные и раздельные интервалы, согласованность снимка и сброс счётчиков при перезапуске. Адаптер и его тесты остаются за тобой. При сборке сервиса подключай его только за существующей защищённой диагностической границей; задание не реализует аутентификацию, публичный endpoint или адаптер урока 37.

## Проверки и типичные ошибки

```sh
gofmt -l lessons/38-bounded-metrics/*.go
go test -p 1 -count=1 ./...
go test -race -p 1 -count=1 ./...
go vet ./...
```

Прежним SQL-интеграциям нужны временный PostgreSQL и `POSTGRES_TEST_URL`; без него они пропускаются. Типичные ошибки: исходные labels в map, хеширование приватных ID в labels, раздельные интервалы вместо накопительных, bucket и count из разных снимков, mutex во время I/O, смешение секунд и миллисекунд, игнорирование короткой записи, рекурсивный учёт scrape и представление локальных счётчиков как постоянного мониторинга.

Источники: [Prometheus labels и единицы](https://prometheus.io/docs/practices/naming/), [text exposition и инварианты histogram](https://prometheus.io/docs/instrumenting/exposition_formats/), [histogram и summary](https://prometheus.io/docs/practices/histograms/).
