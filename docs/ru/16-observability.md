# Урок 16: наблюдаемость — логи, метрики, трассировки и профили

## Цель

Научиться разбираться в работе HTTP-сервиса, когда что-то пошло не так. Пример использует структурированный Go logger, небольшой endpoint метрик с ограниченной кардинальностью и встроенные pprof-профили и execution trace.

Эти сигналы отвечают на разные вопросы:

- **Логи** описывают отдельные события и содержат сгенерированный request ID для корреляции.
- **Метрики** суммируют поведение во времени: например, количество запросов и их общую длительность.
- **Распределённые трассировки** связывают span-ы между сервисами. Одного request ID недостаточно, чтобы считать его трассировкой.
- **Профили** показывают, где процесс тратит CPU, память или время ожидания. Go execution trace показывает работу scheduler и goroutine внутри одного процесса.

В примере нет внешних telemetry-зависимостей. Для распределённой трассировки в реальном сервисе используй OpenTelemetry: [официальную документацию для Go](https://opentelemetry.io/docs/languages/go/) и [otelhttp](https://pkg.go.dev/go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp). Перед добавлением проверь минимальную версию Go выбранного релиза относительно go.mod.

## Запусти сервис

Публичный API слушает :8080. Метрики и профили обслуживаются отдельным listener, привязанным только к 127.0.0.1:6060.

```sh
go run ./lessons/16-observability
```

Выполни запрос и посмотри заголовок ответа:

```sh
curl -i http://127.0.0.1:8080/reports
```

Ответ содержит сгенерированный сервером X-Request-ID. Тот же ID появится в JSON-записи лога. Значение, присланное клиентом, не принимается за доверенное; query string не записывается в лог.

Прочитай метрики через локальный diagnostics listener:

```sh
curl http://127.0.0.1:6060/metrics
```

Пример вывода:

```text
# TYPE go_course_http_requests_total counter
go_course_http_requests_total{route="reports",method="GET",status_class="2xx"} 1
# TYPE go_course_http_request_duration_seconds summary
go_course_http_request_duration_seconds_count 1
go_course_http_request_duration_seconds_sum 0.000021000
```

Метки берутся из фиксированных значений маршрута, метода и класса статуса. Не добавляй в метрики исходный URL, tenant ID, user ID или request ID: каждое уникальное сочетание меток создаёт отдельный time series.

## Посмотри профиль и Go execution trace

Открой локальный heap profile командой go tool pprof:

```sh
go tool pprof http://127.0.0.1:6060/debug/pprof/heap
```

Сними короткий runtime execution trace и открой его в go tool trace:

```sh
curl -o trace.out 'http://127.0.0.1:6060/debug/pprof/trace?seconds=5'
go tool trace trace.out
```

Trace из pprof — это runtime execution trace Go, а не распределённая трассировка со span-ами, передаваемыми в PostgreSQL или другой сервис. Для причинно-следственной связи между сервисами используй OpenTelemetry и передавай trace context. В [документации Go net/http/pprof](https://pkg.go.dev/net/http/pprof) описаны endpoints и инструменты профилирования.

Diagnostics mux не подключён к публичному API. Сервер привязывает его к loopback, потому что профили могут раскрывать детали процесса и потреблять ресурсы. В production открывай диагностику только через специально защищённую management-сеть; не публикуй порт 6060 в интернете.

## Как устроена инструментация

JSON slog handler создаёт записи, которые можно разбирать автоматически. Middleware генерирует случайный request ID, заменяет значение клиента, добавляет ID в ответ и logger, а затем записывает ограниченную категорию маршрута, метод, класс HTTP-статуса и длительность.

Обёртка response writer отслеживает статус и реализует Unwrap, чтобы http.ResponseController мог получить исходный writer. Она предназначена только для обычных буферизованных обработчиков. Обёртка может скрыть optional-интерфейсы вроде http.Flusher от прямой проверки типа; не копируй эту middleware без изменений вокруг streaming или WebSocket handler-ов. Для них используй подходящую инструментацию и тестируй необходимые интерфейсы.

Metrics handler делает snapshot счётчиков под read lock. Значения меток нормализуются до фиксированного набора, чтобы ограничить кардинальность. Счётчики хранятся в памяти и обнуляются при перезапуске процесса; production-системе нужен scraper/exporter и внешнее долговременное хранение.

Debug mux явно регистрирует pprof handlers вместо side-effect импорта net/http/pprof в http.DefaultServeMux. Раздельные listeners и mux делают границу между публичными маршрутами и диагностикой видимой в коде.

## Проверки

```sh
gofmt -w ./lessons/16-observability
go test ./lessons/16-observability
go test -race ./lessons/16-observability
go test ./...
go test -race ./...
go vet ./...
```

Целевые тесты проверяют сгенерированный ID корреляции, метрики статуса и длительности, ограниченные метки для неизвестных маршрутов и методов, конкурентный доступ к метрикам, ошибку генератора ID и то, что pprof доступен только через отдельный diagnostics handler.

## Типичные ошибки

- считать correlation ID распределённой трассировкой;
- добавлять в метки метрик неограниченные значения: исходные пути, tenant ID или request ID;
- записывать в лог query string, credentials, токены или персональные данные;
- публиковать pprof на публичном listener или считать его безопасным только потому, что он ничего не изменяет;
- полагать, что обёртка response writer сохраняет интерфейсы для streaming и WebSocket;
- использовать счётчики в памяти как постоянное хранилище мониторинга;
- делать выводы о связи разных сервисов по runtime execution trace одного процесса.

## Практика: добавь распределённую трассировку генерации отчётов

Добавь OpenTelemetry-инструментацию для GET /reports и одного исходящего HTTP-запроса к зависимости. В тестах используй in-memory span exporter; collector и внешний сервис не нужны.

Требования:

1. Создай server span для генерации отчёта и дочерний client span для исходящего запроса. Передавай request context через все вызовы.
2. Передай W3C trace context тестовому upstream и проверь, что у дочернего span тот же trace ID, что у server span.
3. Фиксируй ошибки зависимости и отменённые запросы, не записывая секреты и не используя пользовательские значения в названиях span.
4. Завершай tracer provider с ограниченным по времени context, чтобы отправить буферизованные span-ы.
5. Учитывай версию Go в этом репозитории: выбери совместимые версии модулей OpenTelemetry либо обоснуй изменение toolchain, не повышая базовую версию молча.
6. Добавь тесты успешного вызова, ошибки upstream, отмены и передачи trace context.

## Критерии завершения

Ты умеешь различать логи, метрики, распределённые span-ы и Go runtime-профили; объясняешь, почему число сочетаний меток нужно ограничивать; снимаешь локальный heap profile и runtime trace; показываешь, что pprof listener отделён от публичного API. Тесты примера проходят с race detector, а новое задание ты реализуешь самостоятельно.
