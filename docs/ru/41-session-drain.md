# 41. Лимит и завершение долгоживущих сессий

[English version](../41-session-drain.md) · [Запускаемый пример](../../lessons/41-session-drain/main.go)

Подключение к чату может оставаться открытым долго после HTTP-апгрейда. Владелец подключения удерживает слот до завершения сессии и освобождения её ресурсов. [Server.Shutdown](https://pkg.go.dev/net/http#Server.Shutdown) оставляет управление перехваченными подключениями, включая WebSocket, приложению. В сервере чата учитывается всё время работы WebSocket-обработчика, чтобы общие ресурсы оставались доступны до его выхода.

## Запуск примера

```sh
go run ./lessons/41-session-drain
go test -count=1 -v ./lessons/41-session-drain
go test -race -count=20 ./lessons/41-session-drain
go vet ./lessons/41-session-drain
```

```text
session stopped
all sessions drained
```

Одна горутина имитирует сессию. Общий для процесса лимит слотов и два канала описывают жизненный цикл независимо от транспорта.

## Как живёт слот

1. Зарезервируй слот до запуска работы, которая будет владеть подключением. Когда все слоты заняты, `acquire` сразу возвращает `errSessionLimit`. При успехе вызывающий получает функцию освобождения. Вызови её и при ошибке подготовки, и при обычном выходе, после очистки, которой ещё нужны общие ресурсы.

2. `beginDrain` прекращает приём под тем же мьютексом, который защищает счётчик. При гонке с остановкой вызов `acquire` либо получает учтённый слот, либо возвращает `errDraining`. После прекращения приёма `errDraining` имеет приоритет даже при заполненном реестре.

3. Закрытие `stopping` сообщает всем сессиям о запросе на остановку. Владельцы сессий замечают сигнал и завершают свою работу. В реальном WebSocket-обработчике заблокированному чтению может понадобиться дедлайн транспорта или закрытие подключения, прежде чем обработчик сможет освободить ресурсы.

4. Реестр закрывает `done` при начале остановки с пустым реестром либо когда последняя учтённая сессия освобождает слот во время остановки. Повторные вызовы `beginDrain` возвращают тот же канал. Каждая функция освобождения использует `sync.Once`, поэтому повторный вызов не освобождает чужой слот.

## Практика · Ограничь ожидание завершения сессий

Добавь `waitDrained(ctx context.Context) error`. Координатор остановки вызывает `beginDrain` и ждёт в рамках своего контекста остановки. Сохрани правила приёма, сигнала остановки и освобождения слотов.

1. Жди закрытия `done` или завершения контекста. Вызов до начала остановки допустим и оставляет приём открытым. Вызывающий с действующим контекстом получает nil, когда все сессии завершились.

2. Возвращай `ctx.Err()`, если контекст уже завершён при входе или в момент, когда вызывающий увидел завершение всех сессий. Проверь уже отменённый контекст на уже завершившем работу реестре. Результат не должен зависеть от выбора готовой ветки `select`. Отмена после успешной проверки может произойти одновременно с возвратом.

3. Отмена ожидания одного вызывающего не влияет на сессии и других ожидающих. В тесте отмени одно ожидание, пока сессия держит слот, затем освободи слот и проверь успех второго вызывающего с действующим контекстом. Отдельно проверь уже истёкший дедлайн через `errors.Is`.

4. Объясни, как должен действовать координатор, если время ожидания вышло, а сессия ещё может обращаться к хранилищу. Политику принудительного завершения транспорта оставь за пределами реестра.

Координируй горутины в тестах каналами и дожидайся их выхода. Дедлайны помогут выявить зависший тест. Не определяй порядок событий по задержкам. Существующие тесты проверяют основной контракт реестра и должны проходить вместе с новыми.

## Типичные ошибки

- Если проверять `draining` и увеличивать `active` в разных критических секциях, можно принять сессию после завершения остановки.
- Если освобождать слот сразу при закрытии `stopping`, сигнал завершения может прийти, пока сессия ещё использует базу данных при очистке.
- Если закрывать общие каналы из отменённого ожидания, один вызывающий сможет повлиять на жизненный цикл всего сервиса.
- Дедлайн ожидания сам по себе не прерывает заблокированную операцию транспорта.

## Критерии завершения

Пример печатает обе строки в указанном порядке. Существующие и новые тесты проходят с детектором гонок. Два вызывающих ждут независимо, а отмена возвращает ошибку контекста, сохраняя состояние приёма, владение слотами и общий сигнал завершения.
