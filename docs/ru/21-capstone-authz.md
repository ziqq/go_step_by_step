# Урок 21: итоговый проект II — проверка membership перед отправкой сообщения

Время на урок: 40–55 минут.

В уроке 20 HTTP-обработчик, прикладная операция и адаптер хранения были разделены. Теперь добавляем границу безопасности: проверенный principal может отправлять сообщения только в те беседы, где membership policy разрешает запись. Аутентификация и авторизация — разные проверки. Вошедший в систему пользователь не получает автоматический доступ ко всем беседам.

Референсный chat-backend принимает аутентифицированные command envelopes и проверяет active membership в PostgreSQL. Этот небольшой REST-пример нужен для изучения границы; он не реализует протокол того backend. Код не разбирает JWT и не проверяет credentials. `withDemoPrincipal` только имитирует principal, который уже проверило доверенное authentication middleware. Никогда не используйте эту demo-функцию для аутентификации реального запроса.

## Запуск примера

```sh
go run ./lessons/21-capstone-authz
go test ./lessons/21-capstone-authz
```

```text
201 Created sender=alice message=1 conversation=chat-1
```

Порядок важен: потребовать principal, проверить форму запроса, проверить membership policy и только затем вызвать writer. Переданный клиентом `user_id` отклоняется как неизвестное поле JSON; ID отправителя берётся из проверенного контекста principal. Go рекомендует использовать значения context только для данных области запроса и объявлять ключ отдельным неэкспортируемым типом, чтобы избежать коллизий; см. рекомендации пакета [`context`](https://pkg.go.dev/context#WithValue).

Для защищённых операций запрещайте доступ по умолчанию и проверяйте права на каждом запросе. Если сервис политики недоступен, обработчик вернёт общую серверную ошибку и не выполнит запись. [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) рекомендует проверять права на каждом запросе и запрещать доступ по умолчанию.

## HTTP- и authorization-контракт

- Нет или некорректен server-side principal: `401 Unauthorized`.
- Пользователь аутентифицирован, но не состоит в беседе: `403 Forbidden`.
- Некорректный, слишком большой запрос, неизвестное поле или невалидное сообщение: стабильный JSON `400 Bad Request`.
- Ошибка membership-зависимости: общая `500 Internal Server Error` (либо `504` при deadline); не переходить к writer.
- Разрешённое создание: `201 Created`; `sender_id` вычисляется из principal, а не из тела запроса.
- Неподдерживаемый метод: `405 Method Not Allowed`.

Membership callback в примере — простое фиксированное правило. В реальном сервисе проверяйте актуальный membership по проверенному ID пользователя и запрошенной беседе. Держите проверку рядом с защищённой операцией и при необходимости передавайте аутентифицированную область в условия SQL. Проверки аутентификации в middleware недостаточно, чтобы подтвердить доступ к беседе.

## Что доказывают тесты

Целевые тесты проверяют, что запросы без аутентификации и от пользователя без membership не вызывают writer, поддельный `user_id` не принимается, ошибка membership приводит к отказу, а ID разрешённого пользователя становится отправителем. Также проверяются некорректный JSON/ввод, границы Unicode-длины, слишком большое тело, общие ошибки и методы. Локальные тесты не проверяют криптографию JWT, PostgreSQL-запросы membership или работающий chat-backend.

```sh
gofmt -w ./lessons/21-capstone-authz
go test ./lessons/21-capstone-authz
go test -race ./lessons/21-capstone-authz
```

## Задание — добавить защищённое чтение сообщения

Добавьте `GET /conversations/{conversationID}/messages/{messageID}`:

1. Получайте ID пользователя только из проверенного principal в request context; никогда не принимайте его из path, query или JSON.
2. Проверяйте membership на каждом запросе и до вызова message reader. Запрещённый запрос не должен вызывать reader.
3. Ограничивайте поиск одновременно ID беседы и ID сообщения, чтобы по известному ID нельзя было получить сообщение из другой беседы.
4. Возвращайте `401` без principal, `403` неучастнику, `404` для отсутствующего сообщения в доступной беседе и стабильную общую `500` при ошибке авторизации или хранилища. Не раскрывайте внутренние ошибки.
5. Добавьте тесты разрешённого чтения, отсутствующего principal, пользователя без membership, отсутствующего сообщения, несовпадающих ID беседы и сообщения, ошибки зависимости. Проверяйте, что отказ не доходит до reader.

Оставьте demo identity helper только учебной имитацией: не реализуйте самодельный JWT parser. Запланируйте минимум 35 минут. Задание завершено, когда проходят позитивные и негативные access-тесты, database lookup включает область беседы, а race detector не находит гонок общего состояния.

## Типичные ошибки

- смешение аутентификации (кто обращается?) и авторизации (может ли этот пользователь работать с беседой?);
- получение `sender_id` или `user_id` из недоверенного JSON;
- восприятие валидного JWT как доказательства membership;
- проверка membership после чтения или записи защищённых данных;
- разрешение доступа, если membership-зависимость завершилась таймаутом или ошибкой;
- проверка membership только на первой странице или первом запросе;
- глобальный поиск сообщения по ID без ограничения доступной беседой;
- использование demo principal helper как production-аутентификации.

## Критерии завершения

Вы можете проследить путь доверенной identity до обработчика, объяснить, почему membership — отдельная проверка для каждого ресурса, показать, что запрещённый запрос не доходит до хранилища, и перечислить, что ещё требуется для deployment: PostgreSQL membership и настоящая аутентификация.
