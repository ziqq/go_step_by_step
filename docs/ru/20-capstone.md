# Урок 20: итоговый проект I — сборка сервиса отправки сообщения

Время на урок: 40–60 минут.

Это первый вертикальный сценарий итогового проекта. Он соединяет HTTP-обработчик с прикладным сервисом и небольшим интерфейсом хранилища, а затем подключает in-memory адаптер в composition root. Главное здесь — ответственность слоёв и поток данных, а не добавление слоёв ради слоёв: интерфейс хранилища нужен сервису как граница, которую позже сможет реализовать PostgreSQL.

Пример — учебный REST API, а не копия референсного chat-backend. Там используются аутентифицированные command envelopes и проверяется право доступа через membership беседы. В этом примере нет аутентификации и авторизации; не публикуйте его как настоящий endpoint чата.

## Запуск примера

```sh
go run ./lessons/20-capstone
go test ./lessons/20-capstone
```

```text
201 Created id=1 conversation=chat-1 text=hello from the capstone
```

Путь запроса:

```text
HTTP-запрос -> обработчик проверяет JSON -> MessageService проверяет сценарий -> MessageStore сохраняет -> HTTP-ответ
```

Обработчику неизвестно, как генерируются ID и где хранятся сообщения. `MessageService` зависит от небольшого интерфейса `MessageStore`, который он использует. `main` выбирает in-memory реализацию. Позже её можно заменить PostgreSQL-адаптером, не меняя контракт HTTP-запроса.

## Ответственность компонентов

- Обработчик отвечает за HTTP: декодирует одно ограниченное JSON-значение, преобразует известные ошибки ввода в `400`, скрывает детали хранилища за стабильной ошибкой `500` и возвращает `201 Created`.
- Сервис отвечает за прикладные правила: ID беседы обязателен, текст обрезается по краям, длина ограничена 280 Unicode code points.
- Хранилище отвечает за сохранение и возвращает созданное сообщение. In-memory адаптер использует mutex, потому что HTTP-обработчики могут выполняться одновременно.
- `main` — composition root: создаёт адаптер, передаёт его сервису, а сервис — роутеру.

Интерфейс намеренно объявлен рядом с потребителем. Здесь нет отдельного слоя repository, графа фабрик и интерфейса для каждого конкретного типа.

В шаблонах Go 1.22 `ServeMux` используется `POST /messages`; версия модуля закреплена на Go 1.22. Если путь зарегистрирован для другого метода, стандартный роутер возвращает `405 Method Not Allowed`. См. [обзор маршрутизации Go 1.22](https://go.dev/blog/routing-enhancements). Обработчик использует `http.MaxBytesReader`, чтобы JSON-декодер не читал неограниченное тело запроса; см. [`net/http.MaxBytesReader`](https://pkg.go.dev/net/http#MaxBytesReader).

## Контракт и проверки

Endpoint принимает один JSON-объект с `conversation_id` и `text`. Неизвестные поля, некорректный JSON, второй JSON-объект, слишком большое тело, отсутствие ID беседы, пустой или слишком длинный текст приводят к стабильной JSON-ошибке `400`. Успешное создание возвращает сохранённое сообщение (включая сгенерированные ID и время создания в UTC) в JSON со статусом `201 Created` и заголовком `Location`. Неожиданная ошибка хранилища приводит к общей ошибке `500`; внутренний текст ошибки клиенту не раскрывается. Неподдерживаемый метод возвращает `405`.

Тесты проверяют валидацию и делегирование сервиса, конкурентную выдачу ID in-memory адаптером, успешный HTTP-контракт, ошибки JSON/тела запроса, методы и безопасное отображение ошибок. Они пока не доказывают работу БД-адаптера, аутентификации, авторизации или production-развёртывания.

```sh
gofmt -w ./lessons/20-capstone
go test ./lessons/20-capstone
go test -race ./lessons/20-capstone
```

## Задание — заменить адаптер на PostgreSQL

Реализуйте PostgreSQL-версию `MessageStore`, не меняя сервис и HTTP-контракт:

1. Добавьте миграцию для таблицы `messages` с генерируемым ID, ID беседы, нормализованным текстом и временем создания. Добавьте индекс для чтения новых сообщений беседы в стабильном порядке.
2. Реализуйте `Create` через `pgx` и передавайте контекст вызывающего к запросу к БД. Возвращайте сгенерированные базой ID и время.
3. Читайте URL базы данных из runtime-конфигурации; не коммитьте учётные данные и не встраивайте их в бинарник или Docker image.
4. Подключите PostgreSQL-адаптер в production composition root, сохранив in-memory адаптер для тестов или примера.
5. Добавьте интеграционный тест с `POSTGRES_TEST_URL`. Он должен проверить сохранённые значения и сгенерированные поля, а также удалить собственные тестовые данные. Если переменная не задана, пропускайте только integration test с понятной причиной.
6. Оставьте тесты обработчика независимыми от PostgreSQL и докажите, что сервис не зависит от конкретного хранилища.

На этом шаге не добавляйте аутентификацию, outbox, повторы или новый роутер. Сначала сохраните вертикальный сценарий и контракт ошибок, заменив только адаптер хранения. Запланируйте минимум 40 минут; задание завершено, когда целевые unit-тесты проходят, а opt-in integration test проверяет полный успешный цикл с PostgreSQL.

## Типичные ошибки

- создание пула БД или выполнение SQL прямо в HTTP-обработчике;
- интерфейс с методами, которые сервис не использует;
- возврат сырой ошибки БД клиенту;
- отсутствие request context в вызове хранилища;
- неограниченное декодирование или принятие второго JSON-значения;
- совместное использование изменяемого in-memory хранилища без синхронизации;
- заявление, что пример готов к production, хотя в нём нет аутентификации, авторизации, надёжного хранения и развёртывания.

## Критерии завершения

Вы можете проследить запрос через обработчик, сервис, интерфейс и выбранный адаптер; объяснить, почему интерфейс принадлежит потребителю; определить, какой слой отвечает за валидацию и отображение ошибок; и перечислить, что нужно добавить до безопасной публикации примера как реального chat-сервиса.
