# 53. Удержать membership до фиксации сообщения

[English version](../53-membership-lock.md) · [Запускаемый пример](../../lessons/53-membership-lock/main.go) · [Схема](../../lessons/53-membership-lock/schema.sql)

Урок 52 требует актуальной авторизации даже при повторе команды. Между обычным SELECT membership и последующим INSERT есть промежуток: другая транзакция может отозвать доступ. Здесь одна транзакция READ COMMITTED блокирует строку активной membership, записывает сообщение и выполняет commit до освобождения блокировки.

Референсный chat backend проверяет membership внутри транзакции сообщения и блокирует строки изменяемого состояния чата. Этот небольшой пример выделяет одно правило membership; он не воспроизводит и не проверяет тот backend целиком. Tenant и actor должны приходить из проверенной аутентификации. ID диалога сам по себе не даёт полномочий. Другие политики, HTTP-ответы, идемпотентность и доставка outbox остаются отдельными задачами. В частности, этот урок не решает практику урока 52 с outbox.

## Запуск с временным PostgreSQL

Используй только временную базу. Пароль ниже — публичное значение для локального примера. Запусти контейнер с портом только на loopback в одном терминале и дождись готовности; после проверки останови его через Ctrl-C.

```sh
docker run --rm --name go-lesson53 \
  --tmpfs /var/lib/postgresql/data:rw,size=512m \
  -e POSTGRES_PASSWORD=lesson53_local \
  -p 127.0.0.1:55453:5432 postgres:17-alpine
```

Из корня репозитория в другом терминале:

```sh
export DATABASE_URL='postgres://postgres:lesson53_local@127.0.0.1:55453/postgres?sslmode=disable'
export POSTGRES_TEST_URL="$DATABASE_URL"
go run ./lessons/53-membership-lock
go test -count=1 -v ./lessons/53-membership-lock
go test -race ./lessons/53-membership-lock
go vet ./lessons/53-membership-lock
```

Ожидаемый вывод:

```text
authorized write committed: true
write after revocation denied: true
```

Пример создаёт таблицы этого урока, активирует свою фиксированную демонстрационную membership, сохраняет сообщение и отзывает membership перед второй отправкой. Каждый запуск сохраняет ещё одно сообщение: ключа команды здесь нет. Тесты используют собственные случайные схемы. Без POSTGRES_TEST_URL тесты базы пропускаются; успешный запуск только unit-тестов не доказывает поведение PostgreSQL.

## Сохранить решение о доступе до записи

1. Сначала проверь context, затем положительные tenant/conversation/actor ID и непустой UTF-8 текст не длиннее 280 кодовых точек. Отклоняй NUL и сохраняй принятый текст без изменений. Неверный ввод и отсутствие базы возвращают ID ноль. Открой явную транзакцию READ COMMITTED и отложи rollback для каждого раннего выхода.

2. Выбери одну активную membership по всем трём ID с FOR SHARE. Отсутствие подходящей активной строки даёт errForbidden и ID ноль; отсутствующая, неактивная и чужая область имеют одну ошибку. Другие ошибки базы остаются ошибками, а не отказом в доступе.

```sql
SELECT actor_id FROM lesson53_members
WHERE tenant_id=$1 AND conversation_id=$2 AND actor_id=$3 AND active
FOR SHARE;
```

3. Вставляй через tx, а не через db. Транзакция должна быть короткой, без сетевых вызовов под блокировкой. Возвращай созданный ID только после успешного Commit. Ошибка вставки или commit возвращает ноль. Неопределённое подтверждение commit может скрывать сохранённую запись; не повторяй эту неидемпотентную операцию вслепую.

4. Если Send первым удерживает разделяемую блокировку строки, UPDATE с отзывом membership ждёт его commit или rollback. Если первым конфликтующую блокировку получил отзыв, блокирующее чтение ждёт, затем перепроверяет обновлённую строку после commit отзыва. Теперь active равен false, поэтому Send получает отказ. Если транзакция отзыва выполняет rollback, доступ сохраняется. Порядок определяется получением конфликтующих блокировок, а не временем начала HTTP-запросов.

5. FOR SHARE допускает другие разделяемые проверки membership, но блокирует UPDATE поля active. FOR KEY SHARE слишком слаб для такого изменения неключевого поля. Внешний ключ доказывает существование, а не активное право доступа. В схеме намеренно нет внешнего ключа от исторических сообщений к membership: отзыв или удаление membership не должны удалять историю. Сверь [режимы блокировки строк PostgreSQL](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS) и [перепроверку в READ COMMITTED](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED).

Интеграционные тесты наблюдают реальные ожидания блокировок через pg_stat_activity, а не угадывают порядок через sleep. Один тест первым удерживает отзыв. Другой временно блокирует таблицу сообщений, останавливая Send после чтения membership, затем доказывает, что отзыв ждёт этот Send. Блокировка таблицы — механизм синхронизации теста, а не production-стратегия. Все горутины тестов дожидаются завершения. Проверяются также отмена context, точный текст, изоляция областей, ошибка вставки и отложенное нарушение ограничения при commit.

## Практика · Ограничить ожидание блокировки в транзакции

Добавь SendWithLockWait(ctx context.Context, d draft, waitMillis int) (int64, error) и errBusy. Сохрани Send и исходные тесты. Сохрани правило membership и границу commit; не добавляй повторы, горутины, NOWAIT или SKIP LOCKED.

1. Используй тот же порядок проверки context и draft, что в Send. Затем потребуй waitMillis в 1..5000, иначе верни errInvalid и ID ноль до обращения к базе. Задай этой операции локальный для транзакции lock_timeout PostgreSQL через связанный параметр. Не устанавливай значение для всей сессии через db: пул может выполнить запись на другом соединении или передать настройку следующему пользователю соединения. Таймаут ограничивает каждое получение блокировки, а не всю транзакцию; вызывающей стороне по-прежнему нужен дедлайн context.

2. При SQLSTATE 55P03 выполни rollback и верни ID ноль с ошибкой, распознаваемой через errors.Is как errBusy. Сохрани распознавание отмены и дедлайна; не превращай отказ в доступе, ошибки вставки и другие SQLSTATE в busy. Возвращай ID только после commit. Настройка не должна переживать commit или rollback на повторно используемом соединении.

3. Добавь тесты базы с реально удерживаемой блокировкой membership, истекающим бюджетом ожидания, более коротким дедлайном context, успешным получением после освобождения, неактивной membership и посторонней SQL-ошибкой. Дождись всех горутин. Используй отдельное соединение для блокирующей транзакции и пул операции из одного соединения, чтобы доказать восстановление прежнего lock_timeout после успешного commit и после rollback. Проверяй нулевые ID при ошибках, число строк, успешное дальнейшее использование и исходный порядок авторизации. Не привязывайся к точному числу прошедших миллисекунд. Объясни, почему таймаут блокировки не доказывает безопасность повтора запроса.

```sh
gofmt -w lessons/53-membership-lock/main.go lessons/53-membership-lock/main_test.go
go test ./...
go test -race ./...
go vet ./...
```

## Типичные ошибки

- Проверка membership до открытия транзакции оставляет промежуток для отзыва.

- Вызов db.QueryRowContext после блокирующего SELECT на tx разрывает логическую связь авторизации и записи.

- FOR KEY SHARE не блокирует обычное изменение флага active.

- Превращение SQL-ошибки в forbidden скрывает сбой; возврат предварительного ID до commit выдумывает успех.

- Сетевой вызов под блокировкой задерживает отзыв и занимает соединение пула.

- Дедлайн context ограничивает ожидание, но ни отмена, ни потерянный ответ не доказывают отсутствие commit.

## Критерии завершения

Покажи, что активный участник в своей области может записать сообщение, чужая или отозванная membership не может, а оба порядка конкурентных блокировок дают описанный результат. Пройди реальные тесты базы и общие проверки с заданным POSTGRES_TEST_URL. Выполни практику ограничения ожидания и докажи, что изменённый таймаут не остаётся на соединениях пула.
