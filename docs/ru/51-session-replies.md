# 51. Безопасные ответы на команды сессии

[English version](../51-session-replies.md) · [Запускаемый пример](../../lessons/51-session-replies/main.go)

После проверки кадра, команды и подпротокола обработка даёт результат или внутреннюю ошибку. Клиенту нужен стабильный код. Пример переводит ошибки в маленький JSON-ответ и не сериализует их текст. В референсном backend dispatcher возвращает результат в очередь единственного writer; здесь изучается только граница публичного ответа, без сокета и записи в базу.

## Как устроен ответ

1. replyFor принимает уже проверенный ID корреляции и результат одной операции. ID связывает ответ с запросом; он не является principal, разрешением или ключом идемпотентности. JSON содержит только id и code. Порядок полей показан для чтения, клиент не должен зависеть от порядка ключей.

2. nil означает ok. errors.Is распознаёт обёрнутые sentinel-ошибки. Порядок политики: invalid_command → forbidden → deadline_exceeded → canceled → internal. Для errors.Join первое подходящее условие выигрывает независимо от порядка дочерних ошибок. Это явный контракт примера. Ошибка с таким же текстом, но другой identity, остаётся internal.

3. Неизвестная ошибка всегда даёт internal. Mapper не вызывает Error и не включает детали SQL, tenant, stack или входного сообщения. Тест с Error, который паникует, проверяет, что граница не форматирует внутреннюю ошибку. Настоящие внутренние логи требуют отдельной политики редактирования чувствительных данных.

4. Mapper не повторяет операцию, не отменяет context и не пишет в соединение. Даже canceled или deadline_exceeded не доказывают rollback записи: операция могла завершиться до получения ошибки. Потерянный ответ не означает отсутствие эффекта. Идемпотентность и подтверждение commit остаются отдельными контрактами. Отправку ответа выполняет writer из урока 45, если транспорт ещё доступен.

[errors.Is](https://pkg.go.dev/errors#Is) · [context errors](https://pkg.go.dev/context#pkg-variables)

## Практика · Проверьте корреляцию перед выполнением

Добавьте execute(ctx context.Context, id string, run func(context.Context) error) reply как синхронную границу перед вызовом обработчика. Реализацию не подсказывает пример.

1. Сначала проверьте ID: от 1 до 64 байт, только ASCII-буквы, цифры, дефис и подчёркивание. Неверный ID возвращает пустой id и code invalid_request_id; не отражайте неверный ввод и не вызывайте run. Не обрезайте и не нормализуйте ID.

2. Для корректного ID сначала проверьте ctx.Err; готовая отмена или истёкший deadline возвращаются через replyFor без run. Затем nil callback даёт internal. Иначе вызовите run ровно один раз с тем же context и передайте его результат в replyFor. Не создавайте горутину, не повторяйте вызов, не перехватывайте panic и не заменяйте результат последующей проверкой context. ctx должен быть ненулевым — это предусловие вызывающего кода.

3. Проверьте длины 0, 1, 64 и 65, каждый допустимый класс символов, пробелы, Unicode и управляющие символы; неверный ID имеет приоритет перед отменой и nil callback. Проверьте отменённый и истёкший context, nil callback, передачу того же context и его значения, один вызов при успехе и ошибке, а также callback, который отменяет context и возвращает nil: ответ остаётся ok. Сохраните исходные тесты и докажите отсутствие отражения неверного ID. Объясните, почему ID не обеспечивает дедупликацию и почему ответ canceled не разрешает слепой повтор записи.

## Типичные ошибки

- Отправлять err.Error или определять код по тексту ошибки.

- Менять ответ на canceled после успешного завершения callback.

- Публиковать непроверенный ID или считать его identity.

- Пытаться гарантировать доставку ответа чистым mapper.

## Критерии завершения

Проследите все три результата, выполните execute без решения из примера и сохраните исходные тесты. Покажите приоритет проверок, передачу context, один вызов callback и отсутствие внутренних деталей в JSON. Объясните различие результата операции и доставки ответа.
