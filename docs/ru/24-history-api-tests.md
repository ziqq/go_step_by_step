# Урок 24: итоговый проект V — контрактные тесты HTTP-истории

[English version](../24-history-api-tests.md)

Время на урок: 50–65 минут: 10 минут чтения, 10 минут запуска и разбора примера, затем минимум 30 минут на задание.

В уроке 23 PostgreSQL-операция проверяет membership, ограничивает область беседы, читает стабильную страницу и завершает транзакцию. Теперь проверяем HTTP-границу вокруг этой операции. Корректный SQL сам по себе ещё не доказывает правильные статусы, заголовки и JSON для вызывающей стороны.

## Запуск примера

Из корня репозитория:

```sh
go run ./lessons/24-history-api-tests
```

```text
200 OK
403 Forbidden
401 Unauthorized
```

Пример выполняет три внутрипроцессных запроса: разрешённый principal, запрещённый principal и отсутствие principal. Он использует небольшой fake-loader без PostgreSQL. Identity-helper имитирует доверенный authentication middleware; query-параметр или непроверенный заголовок Authorization не становятся identity.

## Одна граница и два владельца ответственности

`historyLoader` получает context, доверенный ID пользователя, ID беседы, необязательный cursor и размер страницы. Форма аргументов и результата соответствует `ListPage` из урока 23. HTTP-обработчик проверяет транспортный ввод и формирует публичные ответы; loader отвечает за membership и область хранения. В PostgreSQL эти проверки должны оставаться внутри snapshot-транзакции урока 23.

Каждый урок остаётся отдельным исполняемым пакетом. Этот пример не импортирует и не подключает `main` урока 23. В собираемом приложении общие типы объявляются один раз и подключается настоящий адаптер; копировать эти отдельные учебные пакеты в production без изменений не следует.

Референсный backend использует аутентифицированные command envelopes и более богатый контракт `messages.load`. Этот REST-пример обучает проверке границ, а не совместимости с его wire-протоколом.

## Контракт обработанного маршрута истории

Маршрут — `GET /conversations/{conversationID}/messages`. Допустимы только `limit` и `before`. Неизвестные query-ключи, повторы, неправильное кодирование query и неверные cursor отклоняются. Фильтры дат остаются отдельными заданиями ученика в уроках 22–23.

| Ввод или результат | Наблюдаемое поведение | Вызовы loader |
|---|---|---|
| Нет проверенного principal | `401`, JSON-ошибка, Bearer challenge | 0 |
| Неверные параметры страницы | `400`, `invalid_page` | 0 |
| Разрешённый запрос | `200`, JSON-страница, `Cache-Control: no-store` | 1 |
| Обёрнутый `ErrNotMember` | `403`, `forbidden` | 1 |
| Обёрнутый `context.DeadlineExceeded` | `504`, `history_timeout` | 1 |
| Неожиданная ошибка loader | `500`, `history_unavailable`, без внутренних деталей | 1 |
| Context запроса уже отменён | Нет записи тела или статуса ответа | 0 |

Успешная пустая страница содержит `messages: []`, а не `null`. Следующий cursor возвращается только при `has_more=true`. Если адаптер обещает следующую страницу без пригодной позиции, обработчик выдаёт общую `500`. Неизвестные пути и неподдерживаемые методы стандартный mux обрабатывает собственными ответами `404`/`405`; JSON-таблица описывает обработанный маршрут.

`errors.Is` сохраняет классификацию ошибок после оборачивания. Публичный JSON содержит стабильные поля `code` и `message`; строки подключения к БД и SQL туда не попадают. Обработчик также повторно проверяет входящий context после загрузки, чтобы отменённый запрос не превратился в успешный ответ.

## Как тесты делают контракт наблюдаемым

`httptest.NewRequest` и `NewRecorder` вызывают настоящий обработчик. Успешный тест записывает аргументы зависимости и значение из context запроса, затем проверяет статус, заголовки, один JSON-документ, пустой массив и следующий cursor. Тесты отказа доказывают отсутствие вызова loader. Fake, возвращающий обёрнутую ошибку, позволяет проверить HTTP-отображение без сломанной БД.

Это HTTP contract tests. Они не доказывают SQL-авторизацию, настоящие транзакции, проверку JWT, работу сокетов или доставку ответа отключившемуся клиенту. Opt-in PostgreSQL-тесты урока 23 остаются отдельным доказательством.

Читайте `recorder.Result()` после завершения обработчика и закрывайте body ответа. Не сравнивайте весь `http.Response` через `reflect.DeepEqual`: API recorder не обещает стабильность каждого поля. Для отмены считайте настоящие вызовы `WriteHeader`/`Write`; неявная `200` recorder не означает, что отключившемуся клиенту отправлен ответ. См. официальную [документацию httptest](https://pkg.go.dev/net/http/httptest#ResponseRecorder.Result).

```sh
go test -count=1 -v ./lessons/24-history-api-tests
go test -race -count=1 ./lessons/24-history-api-tests
```

## Задание — добавить бюджет времени запроса истории

Расширьте `newRouter`: принимайте положительный бюджет `time.Duration` и возвращайте ошибку для нуля или отрицательного значения. Сохраните текущий публичный контракт страницы и ошибок.

1. После проверки identity и query создавайте дочерний context от входящего запроса и передавайте его loader. Освобождайте ресурсы дочернего context при любом выходе.
2. Сохраняйте более ранний входящий deadline и распространяйте отмену клиента. Не заменяйте context запроса на `context.Background()`.
3. При истечении бюджета возвращайте стабильную `504 history_timeout`. При отмене клиентского context не записывайте ответ. Проверяйте состояние context до публикации результата, включая loader, вернувший успех после истечения времени.
4. Добавьте целевые тесты отказа конфигурации, ограниченного дочернего deadline, более раннего родительского deadline, отмены родителя, истечения бюджета, позднего успеха и освобождения дочернего context после обычного успешного ответа. Существующие проверки identity, query и сокрытия ошибок должны проходить.

Запланируйте минимум 30–40 минут. [Документация context](https://pkg.go.dev/context#WithTimeout) описывает дочерние deadline и очистку; она не обещает принудительно остановить loader, который игнорирует context. Оставьте загрузку синхронной и учитывающей отмену, не запускайте работу, переживающую завершившийся по таймауту обработчик.

Используйте fake, ожидающий `ctx.Done()` и сигнализирующий о входе через канал. Избегайте произвольных sleep и проверок точного числа миллисекунд. Ограничьте зависающий тест щедрым watchdog, чтобы пропущенная отмена приводила к понятной ошибке, а не к бесконечному ожиданию.

## Типичные ошибки и критерии завершения

- Доверие `user_id` или содержимому непроверенного Bearer-заголовка.
- Проверка только `200` без заголовков, JSON, аргументов области и запрещённых вызовов.
- Проверка только необёрнутой ошибки, хотя production возвращает обёрнутую.
- Утверждение, что `403` от fake доказывает корректность membership SQL.
- Ожидание JSON от всех ошибок mux или трактовка статуса recorder по умолчанию как сетевого ответа.
- Таймаут без освобождения ресурсов, потеря родительского context или возврат позднего успеха.

Задание завершено, когда новые тесты бюджета покрывают успех и ошибки, запрос без проверенного principal или с неверными параметрами не вызывает loader, а вы можете объяснить, какие гарантии требуют PostgreSQL или настоящих сетевых тестов.

Проверьте весь репозиторий:

```sh
gofmt -w ./lessons/24-history-api-tests
go test ./...
go test -race ./...
go vet ./...
```
