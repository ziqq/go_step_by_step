# Урок 34: ограничь очередь worker и обработай принятые задачи

[English version](../34-bounded-queue.md)

Удержи worker, заполни буфер ожидания, получи отказ, затем закрой приём и дождись обработки. Нарисуй последовательность producer/worker и выполни задание с приёмом пачки. Упражнение с ограниченным ожиданием shutdown из урока 33 остаётся отдельным и нерешённым.

## Ёмкости нужен контракт перегрузки

Урок 33 учитывает время жизни задач, но запускает горутину для каждой принятой задачи. Здесь один worker читает ID задач из ограниченного канала. Лимит учитывает ожидающие задачи: при ёмкости C не более C задач ждут и один callback выполняется. Увеличение буфера сглаживает всплеск, но не ускоряет медленный callback.

Открой [main.go](../../lessons/34-bounded-queue/main.go) и [тесты](../../lessons/34-bounded-queue/main_test.go). Локальный пример удерживает первый callback каналом-барьером, заполняет одно место ожидания, отклоняет лишнюю задачу, закрывает приём, освобождает callback и ждёт две принятые задачи. База, сеть и управление порядком через таймеры не нужны.

## Один worker, один владелец канала

Создавай `jobQueue` через `newJobQueue(capacity, handle)`. Нужны положительная ёмкость и ненулевой обработчик; неверная конфигурация возвращает nil и `ErrInvalidQueue` до запуска worker. Нулевое значение очереди не поддерживается, копировать её нельзя.

`TrySubmit` отклоняет пустой или состоящий только из пробельных символов ID с `ErrInvalidJob`, даже после закрытия. Непустые ID сохраняются без изменения. Корректный ID получает `ErrClosed` после закрытия приёма; при открытом приёме — `ErrFull`, если отправка невозможна, либо nil при успехе. Одинаковые ID считаются разными задачами. Nil подтверждает приём в память, а не успех callback или надёжную доставку.

Следующий фрагмент работает после проверки флага закрытия под mutex приёма:

```go
select {
case q.jobs <- job:
    return nil
default:
    return ErrFull
}
```

Ветка default исключает ожидание места в канале. При этом `TrySubmit` может ждать короткую критическую секцию mutex; это не lock-free API и не гарантия времени ответа. Переполнение относится к конкретной попытке: сразу после неё worker может освободить место. Нельзя отвечать на `ErrFull` молчаливой потерей надёжной работы, бесконечным циклом или неограниченным числом ожидающих горутин. Вызывающему нужна явная политика отказа, бюджета повторов либо надёжной передачи через хранилище.

Один mutex защищает отправку и закрытие канала. Проверка состояния без этой координации может столкнуться с `close` и вызвать panic при отправке. `select` с default не делает отправку в закрытый канал безопасной. Канал закрыт внутри типа, поэтому вызывающий не обходит его владельца.

## Закрой приём, затем обработай остаток

Первый `Close` помечает очередь закрытой и закрывает канал задач под mutex приёма. Последующие вызовы возвращают тот же сигнал завершения. Вызывающий не ждёт callback под mutex. Единственный worker выполняет callback вне блокировки:

```go
for job := range q.jobs {
    handle(job)
}
close(q.done)
```

Закрытие канала задач сохраняет значения в буфере. Worker читает их в порядке отправки и публикует завершение только после возврата последнего callback вместе с его отложенной очисткой. Для конкурентных producer порядок фактического прихода не обещается; последовательные успешные отправки сохраняют порядок. Callback этой очереди не выполняются одновременно.

Callback может запросить `Close`, но не должен ждать завершения своей очереди. Зависший callback оставляет сигнал завершения открытым; эта политика обработки остатка не отменяет задачи и не задаёт дедлайн остановки. Получение из закрытого сигнала завершения синхронизирует наблюдение записей callback. Один возврат из `Close` не подтверждает окончание обработки. Panic следует обычному поведению Go; пример не перехватывает его и не трактует результаты callback.

## Сохрани видимую границу надёжности

Ёмкость ограничивает число ожидающих ID, а не их размер в байтах или всю память вызывающих. Это учебный пример в памяти: завершение процесса теряет остаток задач, а единственный вызов обработчика здесь не доказывает exactly-once для внешних эффектов.

Урок 27 сохраняет намерение доставки в транзакции. Production-диспетчер должен оставлять его восстанавливаемым до подтверждения эффекта протоколом доставки; успешное помещение в очередь таким подтверждением не является. Референс backend чата, доступный только для чтения, в `internal/push/worker.go` загружает ограниченные пачки из хранилища и отдельно фиксирует завершение/повтор. Он не реализован каналом этого урока. Референсный backend и предыдущие упражнения не меняются.

## Запуск из корня репозитория

```sh
go run ./lessons/34-bounded-queue
go test -count=1 -v ./lessons/34-bounded-queue
go test -race -count=20 ./lessons/34-bounded-queue
```

Ожидаемый вывод:

```text
processed: job-1, job-2; overload rejected; queue drained
```

Тесты покрывают неверную конфигурацию/ID, точную ёмкость ожидания, отказ лишней работе, FIFO-обработку остатка, освобождение места после чтения, очистку до завершения, сохранение значений/дубликатов, конкурентное закрытие, закрытие из callback и гонки приёма с закрытием. Барьеры задают порядок; watchdog только завершает зависший тест ошибкой. Повторный race detector не доказывает все расписания, восстановление после сбоя, подтверждение доставки или production-производительность.

## Задание: приём пачки целиком — не реализовано

Добавь `TrySubmitBatch(jobs []string) error` в `jobQueue` этого урока, сохранив `TrySubmit`, `Close` и все опубликованные тесты. Это одно упражнение на приём; не добавляй ещё worker, неограниченный backlog, сохранение в базе или сетевую доставку.

1. Отклоняй пустую/nil-пачку или любой пустой/пробельный ID с `ErrInvalidJob` до приёма чего-либо, в том числе после закрытия. Проверяй всю пачку. Сохраняй принятые ID без изменения и допускай дубликаты как отдельные задачи.
2. Для корректной пачки возвращай `ErrClosed`, если приём закрыт. Иначе принимай её целиком только при наличии мест ожидания на момент решения о приёме. Недостаток мест, включая размер пачки больше ёмкости, даёт `ErrFull` без приёма любого элемента. Не жди места и не запускай горутину для каждой задачи/вызывающего.
3. Элементы принятой пачки должны идти подряд в порядке отправки и сохранять порядок среза относительно конкурентных одиночных/пакетных producer. Callback может начать работу до возврата метода. Атомарность приёма не является транзакцией над эффектами callback; не обещай одновременное выполнение или откат эффектов.
4. Добавь тесты с каналами-барьерами: успех, дубликаты, nil/пустая пачка, пробельный последний элемент, размер больше ёмкости, частично свободный буфер без частичного приёма, успех после чтения worker, приоритет закрытия/валидации и конкурентные пачки/одиночные задачи в гонке с `Close`. Проверь выполнение только принятых задач в допустимом порядке и однократную обработку каждой принятой задачи. Освобождай удерживаемые callback при cleanup теста.

Критерий: отклонённая пачка не даёт ни одного callback даже после обработки остатка, а другой producer не вклинивается между принятыми элементами пачки. Объясни, почему один цикл с вызовами `TrySubmit` не обеспечивает этот контракт. Метод и его тесты остаются за тобой.

## Проверки и типичные ошибки

```sh
gofmt -l lessons/34-bounded-queue/*.go
go test -p 1 -count=1 ./...
go test -race -p 1 -count=1 ./...
go vet ./...
```

Предыдущим SQL-интеграциям нужны временный PostgreSQL и `POSTGRES_TEST_URL`; иначе они пропускаются. Типичные ошибки: считать только очередь всей незавершённой работой; блокировать отправку под mutex закрытия; проверять закрытие без синхронизации; закрывать канал со стороны получателя при работающих отправителях; ждать свой callback; считать ёмкость бюджетом байтов; терять удерживаемые callback теста; подтверждать надёжную доставку при enqueue.

Источники: [буферы и порядок каналов Go](https://go.dev/ref/spec#Channel_types), [поведение select](https://go.dev/ref/spec#Select_statements), [синхронизация каналов](https://go.dev/ref/mem#Channel_communication).
