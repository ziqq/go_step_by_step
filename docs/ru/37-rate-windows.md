# Урок 37: ограниченные окна частоты и число сохранённых ключей

[English version](../37-rate-windows.md)

Урок 30 ограничивает одновременную работу, а урок 36 объединяет одинаковые активные чтения. Ни один из них не ограничивает частоту запросов principal во времени. Проследите фиксированное окно, запустите детерминированные тесты истечения/ёмкости и напишите HTTP-адаптер, различающий исчерпанную квоту и недоступность состояния limiter. Задание `Close` из урока 36 остаётся отдельным и нерешённым.

## Одна фиксированная политика, точные ключи области

Откройте [main.go](../../lessons/37-rate-windows/main.go) и [тесты](../../lessons/37-rate-windows/main_test.go). Создавайте `newWindowLimiter(capacity, limit, window, now)` с положительными значениями и ненулевым clock; ошибочная конфигурация возвращает nil и `ErrInvalidLimiter`. Создавайте до использования, не копируйте и не меняйте политику. Один limiter применяет одинаковые limit и window ко всем ключам. Для разных политик нужны отдельные экземпляры.

`rateKey` содержит точные строки tenant, user и операции, выбранной сервером. Поля только из пробелов недопустимы, но непустые identity не обрезаются и не объединяются. Структура исключает коллизии разделителя. Identity должна приходить из проверенного серверного состояния: limiter не выполняет аутентификацию или авторизацию. Не берите ключ из произвольных `X-User-ID`, `X-Tenant-ID` или заголовков forwarded IP.

Референсный chat backend выбирает ключ tenant/user/method в `internal/command/dispatcher.go` и содержит локальный limiter в `internal/ratelimit/limiter.go`. Документы operations/deployment отделяют локальные ограничения от общих квот ingress. Здесь используется собственный учебный пример с неизменяемой политикой: он не изменяет и не воспроизводит протокол backend. Референс остаётся read-only.

## Контракт приёма

| Ситуация `Allow(ctx, key)` | Decision и ошибка |
|---|---|
| Nil context или пустое поле ключа | Нулевая decision и `ErrInvalidRequest` до проверки отмены/состояния |
| Ошибка context замечена до приёма | Нулевая decision и эта ошибка; без чтения clock, выделения ключа и списания |
| Новый ключ при свободном/освобождённом месте | Разрешён, задержка нулевая; списать один запрос и начать полное окно |
| Живой ключ с остатком квоты | Разрешён, задержка нулевая; списать один без переноса истечения |
| Живой ключ с исчерпанной квотой | Отказ, положительный остаток времени, nil error; без увеличения счётчика/продления |
| Истёкший существующий ключ, включая полную ёмкость | Разрешён; использовать его место и начать полное окно от текущего времени |
| Новый ключ, когда все сохранённые места живые | Нулевая decision и `ErrCapacity`; без обещания времени повтора |

Каждый разрешённый вызов расходует квоту, даже если дальнейшая работа завершилась ошибкой, panic или отменой. Операции release/refund нет. `RetryAfter` описывает текущее окно данного ключа, не резервирует будущую обработку и не обещает наличие места при повторе. У неизвестного ключа при заполнении нет известного личного окна квоты, поэтому этот отказ не считается нарушением квоты.

Один mutex сериализует чтение clock, поиск, счётчик, очистку и вставку. Проверяйте context перед захватом и повторно после захвата. Отмена, замеченная второй проверкой, выигрывает до работы с clock/состоянием; более поздняя отмена не отменяет уже состоявшийся приём. Короткий mutex может вызывать конкуренцию: пример не ждёт сброса квоты и не создаёт очередь запросов, но не обещает приём без ожидания блокировки.

## Точное истечение и ограниченное состояние

Первый разрешённый запрос начинает `[now, now + window)`. Последующие запросы не сдвигают окно. Равенство границе начинает новое окно без переноса неиспользованного остатка. Нулевое время допустимо: не используйте `time.Time{}` как признак неинициализированной сохранённой записи.

Фрагмент ветки живого окна под mutex:

```go
if current.used >= l.limit {
    return rateDecision{RetryAfter: current.expiresAt.Sub(now)}, nil
}
current.used++
l.entries[key] = current
return rateDecision{Allowed: true}, nil
```

Запускаемый файл содержит поиск, точное истечение, валидацию и очистку. Когда новый ключ встречает заполненную ёмкость, удалите истёкшие записи по одному сохранённому значению времени, сохраните каждую живую запись, затем перепроверьте ёмкость. Истёкший существующий ключ уже занимает место и сбрасывается напрямую. Всего хранится не больше `capacity` записей, включая истёкшие до повторного использования/очистки. Фонового sweeper нет. Полный обход занимает O(capacity) под mutex; ограничено число ключей, но не байты строк или одновременные запросы. При адаптации сервиса используйте ограниченные доверенные ID и отдельные бюджеты одновременной работы/зависимостей.

Переданный clock должен быть быстрым, неубывающим и не вызывать limiter повторно: он работает под mutex. Для локального измерения длительности используйте `time.Now`: его монотонная составляющая сохраняется при `Add`, сравнениях и вычитании внутри процесса. Тесты используют синхронизированный fake clock и явно продвигают время; sleep не доказывает истечение. Сериализация времени не сохраняет монотонную составляющую. Откат clock находится вне контракта этого примера.

Это фиксированное окно, а не гарантия sliding window или token bucket. Запросы могут группироваться около границы. Разные процессы/экземпляры имеют независимые бюджеты, перезапуск теряет историю. Тесты показывают это ограничение и не обещают защиту всего кластера. Счётчик не заменяет долговечную идемпотентность команд или авторизацию.


Ожидаемый вывод (попытка 4 продвигает fake clock ровно на секунду):

```text

attempt=2 allowed=true retry_after=0s
attempt=3 allowed=false retry_after=1s
attempt=4 allowed=true retry_after=0s
```

Тесты проверяют ошибочные/отменённые вызовы, отмену при ожидании mutex, границу в одну наносекунду, несдвигаемое окно, отказ по ёмкости, очистку без предварительного чтения, точную изоляцию области/разделителей, максимальную длительность, конкурентный приём по квоте/ёмкости, независимые экземпляры и ошибки вывода. Каналы задают порядок конкурентной работы; таймаут теста лишь защищает от deadlock.

## Практика: HTTP-адаптер для приватной истории

Добавьте `limitHistory(l *windowLimiter, next http.Handler) (http.Handler, error)` и `ErrInvalidHandler`. Добавьте приватные типы identity для задания; тесты передают их как уже проверенный серверный context без реализации аутентификации:

```go
type principal struct { TenantID, UserID string }
type principalKey struct{}
```

Сохраните limiter и его тесты. Реализуйте один адаптер с контрактом:

1. Nil limiter или nil handler возвращает nil и `ErrInvalidHandler`. До поиска identity запрос с уже завершённым context возвращается без записи заголовков/body и вызова limiter/next. То же правило без записи действует, если `Allow` возвращает ошибку отмены/дедлайна context.
2. Читайте **значение** типа `principal` из `r.Context().Value(principalKey{})`. Отсутствующая identity, неверный тип или пустые поля дают 401, `WWW-Authenticate: Bearer` и общее `authentication required`; ключ не расходуется. Используйте точную доверенную identity и константу операции `history.read`. Игнорируйте клиентские identity/operation в заголовках и query. Текущая авторизация остаётся обязанностью следующего обработчика.
3. Отказ по квоте даёт 429 с `Retry-After` в десятичных целых секундах, округлённых вверх, минимум один. Преобразование не должно переполняться при максимальной `time.Duration`; проверьте 1 ns, ровную секунду, дробную секунду и максимальную длительность. Ответ — общее `rate limit exceeded` без идентификаторов. Не ждите, не повторяйте внутри и не вызывайте next.
4. `ErrCapacity` даёт 503 и общее `limiter unavailable`, **без** `Retry-After`: пример не имеет безопасной оценки доступности. Не утверждайте, что новая identity превысила квоту. Другие неожиданные ошибки limiter дают общий 500. Ответы об ошибках не раскрывают ключи, токены, пути или внутренние ошибки.
5. Разрешённый вызов передаёт исходные request и writer в next ровно один раз. Сохраните заголовки/status/body следующего обработчика и context; не возвращайте квоту после ошибки next или отмены после приёма. Используйте `httptest` и spy, считающий записи, для проверки отмены без записи. Проверьте отсутствующую/поддельную identity, изоляцию области, 429 против 503, точный сброс при полной ёмкости, отсутствие вызова next при отказе, конкурентные запросы и сохранение ответа next.

Критерий: объясните частоту против одновременности, квоту против ёмкости, безопасное округление задержки и причину, по которой один локальный счётчик не задаёт общую квоту кластера. Адаптер, вспомогательная функция округления при необходимости и их тесты остаются за вами. Не добавляйте реальную проверку токенов, Redis, proxy policy или `Close` из урока 36.

## Проверки и типичные ошибки

```sh
gofmt -l lessons/37-rate-windows/*.go
go test -p 1 -count=1 ./...
go test -race -p 1 -count=1 ./...
go vet ./...
```

Для SQL-интеграций прошлых уроков нужны отдельная PostgreSQL и `POSTGRES_TEST_URL`, иначе они пропускаются. Типичные ошибки: неограниченная карта identity; вытеснение живого ключа ради нового; сброс живого окна при каждом запросе; запрет сброса истёкшего ключа при заполнении; смешение ёмкости состояния с личной квотой; доверие клиентской identity; ожидание внутри handler; переполнение округления; выдача локального лимита за распределённую гарантию.

Источники: [монотонные часы Go](https://pkg.go.dev/time#hdr-Monotonic_Clocks), [семантика 429](https://www.rfc-editor.org/rfc/rfc6585.html#section-4), [синтаксис Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after). HTTP-ответы и приоритет отмены выше — явно выбранная политика задания.
