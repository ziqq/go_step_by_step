# Урок 11: HTTP, JSON, маршрутизация и валидация

## Цель

Собрать небольшой HTTP API на стандартной библиотеке. В примере разбираются маршрутизация по методу через `http.ServeMux`, JSON в запросах и ответах, валидация входных данных, HTTP-статусы и изолированные тесты обработчиков с `httptest`.

Это граница между функцией Go и backend-сервисом. В целевом chat backend используется похожая общая схема: router выбирает handler, handler валидирует HTTP-запрос, а helper ответа формирует стабильный JSON-контракт.

## Запускаемый пример

Полный пример находится в `lessons/11-http-json/main.go`. Он запускает in-memory test server, отправляет один запрос и печатает ответ, не занимая настоящий порт.

```sh
go run ./lessons/11-http-json
```

```text
201 Created id=1 text=hello from HTTP
```

In-memory server удобен для детерминированного примера. Реальный процесс может использовать тот же handler с `http.Server`:

```go
server := &http.Server{Addr: ":8080", Handler: newRouter(store)}
err := server.ListenAndServe()
```

## Маршрутизация через ServeMux

В Go 1.22 в `http.ServeMux` появились шаблоны с HTTP-методом. Шаблон `POST /messages` выбирает только POST для этого пути, а `GET /messages` — только GET.

```go
mux := http.NewServeMux()
mux.HandleFunc("GET /messages", listMessages(store))
mux.HandleFunc("POST /messages", createMessage(store))
```

Если путь существует, но метод не поддерживается, стандартный mux возвращает `405 Method Not Allowed`. Пусть это решение принимает router, а не дублирующиеся проверки метода внутри каждого handler-а.

Позже шаблон `GET /messages/{id}` сможет прочитать параметр пути через `r.PathValue("id")`. Это используется в практическом задании.

## JSON — это контракт

Декодируй тело в конкретный тип запроса. `DisallowUnknownFields` обнаруживает опечатки и неожиданные поля вместо их молчаливого игнорирования.

```go
decoder := json.NewDecoder(r.Body)
decoder.DisallowUnknownFields()
var input createMessageRequest
if err := decoder.Decode(&input); err != nil {
	writeError(w, http.StatusBadRequest, "invalid JSON")
	return
}
```

Успешный первый `Decode` еще не доказывает, что в теле был только один JSON-объект. Выполни второй decode и требуй `io.EOF`; иначе тело с двумя JSON-объектами может быть принято случайно. Ограничивай размер запроса до декодирования недоверенных данных.

Заголовок `Content-Type` нужно установить до `WriteHeader`. После записи статуса изменение заголовков не меняет уже отправленный клиенту ответ.

## Валидация и статусы

Пример обрезает пробелы у текста, отклоняет пустое значение и ограничивает его 280 Unicode code points. `utf8.RuneCountInString` лучше соответствует пользовательским символам, чем `len`, который считает байты.

В примере используются:

- `201 Created`, когда сообщение сохранено;
- `200 OK`, когда сообщения запрошены;
- `400 Bad Request` для сломанного JSON или неверных данных;
- `405 Method Not Allowed` от mux для неподдерживаемого метода.

Не возвращай HTTP-клиенту детали внутренних ошибок. Публичные сообщения должны быть стабильными и полезными клиенту, но не раскрывать сведения о базе, файловой системе или stack trace.

## HTTP-тесты без прослушивания порта

`httptest.NewRequest` создает запрос, а `httptest.NewRecorder` сохраняет ответ. Handler можно вызвать напрямую:

```go
request := httptest.NewRequest(http.MethodPost, "/messages", strings.NewReader(`{"text":"hello"}`))
response := httptest.NewRecorder()
newRouter(store).ServeHTTP(response, request)
```

Так тесты остаются быстрыми и детерминированными. Проверяй полный контракт: статус, content type, форму JSON, нормализацию и ошибочные случаи. `httptest.NewServer` полезен, когда нужно проверить именно работу HTTP-клиента, как в запускаемом примере.

## Типичные ошибки

- зарегистрировать handler для пути, но забыть его контракт метода;
- принимать неизвестные JSON-поля и скрывать опечатки клиента;
- принимать JSON после первого декодированного значения;
- использовать `len`, когда ограничение задано в Unicode-символах;
- записать тело до установки статуса или content type;
- возвращать `200` для созданного ресурса вместо `201`;
- раскрывать внутреннюю ошибку в публичном ответе;
- тестировать только успешный сценарий и не проверять сломанный JSON, пустой и слишком большой ввод;
- использовать общую изменяемую map или slice без mutex, когда handler-ы работают одновременно.

## Практика: получить одно сообщение по ID

Расшири API endpoint-ом `GET /messages/{id}` в `lessons/11-http-json`.

Требования:

1. Разбери `id` через `r.PathValue("id")` и отклоняй нечисловое или неположительное значение с `400 Bad Request`.
2. Если сообщение существует, возвращай его как JSON со статусом `200 OK`.
3. Если сообщения нет, возвращай стабильную JSON-ошибку со статусом `404 Not Found`.
4. Сохрани безопасность store при одновременных handler-ах; не возвращай внутренний slice и не изменяй его без lock.
5. Добавь целевые тесты для существующего ID, сломанного ID, неположительного ID и отсутствующего сообщения.
6. Не меняй существующие контракты POST и списка.

Не добавляй сторонний router. Используй стандартный шаблон и `PathValue`, появившийся в Go 1.22.
