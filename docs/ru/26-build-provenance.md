# Урок 26: метаданные сборки и упаковка

[English version](../26-build-provenance.md)

План на 50–65 минут: 10 минут чтения, 10–15 минут запуска примера и 30–40 минут на задание.

## От исходников к узнаваемому артефакту

В уроке 25 мы наблюдали HTTP-запросы. Теперь определим исполняемый файл, который пишет эти логи: его версию, ревизию исходников и компилятор Go. Пример — одноразовая CLI-команда, не ещё один сервер и не замена предыдущим урокам про чат.

Запусти из корня репозитория:

```sh
go run ./lessons/26-build-provenance
```

Команда выводит ровно один JSON-документ и завершается. Пример вывода; `go_version` зависит от компилятора:

```json
{"version":"dev","revision":"unknown","go_version":"go1.27.2"}
```

Контракт небольшой: версия — произвольная метка из 1–64 ASCII-букв, цифр, точек, подчёркиваний или дефисов; ревизия — `unknown` для разработки либо 40 строчных шестнадцатеричных символов для этого SHA-1-репозитория. Это не парсер semantic version и не универсальный валидатор Git object ID. Неправильные метаданные или любой позиционный аргумент дают ненулевой код завершения; ошибки записи вывода передаются вызывающему коду.

## Метаданные компиляции — не настройки окружения

В примере объявлены строковые переменные:

```go
var version = "dev"
var revision = "unknown"
```

Флаг линкера `-X` подставляет значения во время сборки. Константа или переменная с инициализацией через вызов функции не является равноценной целью для линкера. Изменение `APP_VERSION` у уже собранного процесса не переписывает его бинарник.

В чистом checkout с закоммиченными исходниками собери и запусти:

```sh
source_revision=$(git rev-parse HEAD)
build_dir=$(mktemp -d)
go build -trimpath -buildvcs=false \
  -ldflags "-X main.version=lesson26 -X main.revision=$source_revision" \
  -o "$build_dir/build-info" ./lessons/26-build-provenance
"$build_dir/build-info"
```

Сначала проверь `git status --short`, включая untracked-файлы: метка `HEAD` на изменённых исходниках не доказывает, что артефакт получен из этого коммита. Для незакоммиченного эксперимента используй ревизию `unknown`.

`-trimpath` убирает файловые пути из исполняемого файла. `-buildvcs=false` отключает автоматическую запись VCS-метаданных; здесь сборка получает ревизию явно, потому что Docker-контекст исключает `.git`. Одни эти флаги не доказывают побитовую воспроизводимость или достоверное происхождение. Бинарник может сообщить любую метку, переданную сборщиком.

## Небольшой контейнер с закреплённым образом

Готовый [Dockerfile](../../lessons/26-build-provenance/Dockerfile) собирает программу с `CGO_ENABLED=0` в отдельной стадии и копирует в `scratch` только исполняемый файл. Builder — Go 1.27.2 на Alpine, закреплённый digest индекса образов; языковой baseline корневого модуля Go 1.22 не изменён. Digest закрепляет содержимое, но не будущие исправления безопасности: обновляй его осознанно после проверки.

С ревизией из чистого checkout выше:

```sh
docker build -f lessons/26-build-provenance/Dockerfile \
  --build-arg APP_VERSION=lesson26 \
  --build-arg SOURCE_REVISION="$source_revision" \
  -t go-course-build-info:lesson26 .
docker run --rm go-course-build-info:lesson26
docker image inspect go-course-build-info:lesson26 \
  --format '{{.Config.User}} {{json .Config.Entrypoint}}'
```

В конфигурации образа ожидается:

```text
65532:65532 ["/build-info"]
```

Процесс пишет метаданные в stdout и завершается; портов и health endpoint нет. Пробный запуск на стадии сборки отбраковывает неверные метки до создания runtime-образа. Build arguments не предназначены для секретов.

Read-only референс `tetradka/chat/backend/Dockerfile` тоже разделяет стадии сборки и запуска и использует непривилегированного runtime-пользователя, но включает зависимости для медиа. Не переноси `scratch` из этой CLI вслепую в backend: HTTPS-сертификаты, данные часовых поясов или FFmpeg требуют отдельных решений об упаковке.

## Проверки и типичные ошибки

```sh
gofmt -l lessons/26-build-provenance/*.go
go test -count=1 -v ./lessons/26-build-provenance
go test ./...
go test -race ./...
go vet ./...
```

Целевые тесты проверяют правильные и ошибочные метаданные, отказ при аргументах, JSON и ошибки записи. Они также компилируют и запускают настоящий артефакт с искусственными тестовыми метками, проверяют невозможность заменить их переменными окружения и читают настройки Go-сборки. Дочерняя сборка требует Go toolchain и доступного для записи build cache. Docker-образ эти тесты не собирают: команды контейнера выполняй отдельно.

Типичные ошибки: проверить только структуру вместо артефакта; передать имя ветки или короткий SHA вместо полной ревизии; считать изменяемый тег закреплённым содержимым; принять заявленную ревизию за подписанное происхождение; спутать кеш или загрузку артефакта с attestation; передать секреты в build arguments.

## Задание: проверенный CI-артефакт — не реализовано

Добавь в `.github/workflows/go.yml` **один job для артефакта**, зависящий от существующего `verify`. Готовую CLI и прежние проверки оставь без изменений.

1. Получи исходники и полную ревизию фактически выбранного `HEAD`. Для pull request это может быть merge-коммит; не подставляй предполагаемый SHA ветки.
2. Собери эту CLI для runner с `CGO_ENABLED=0`, `-trimpath`, `-buildvcs=false`, допустимой меткой версии, отличной от значения по умолчанию, и этой ревизией. Используй версию компилятора из workflow; не закрепляй ожидаемое значение `go_version` строкой.
3. Запусти полученный бинарник. Разбери вывод как JSON и потребуй ожидаемую версию, точное совпадение с ревизией checkout (никогда `unknown`) и непустую версию компилятора. Успешной команды сборки недостаточно.
4. Покажи отрицательную проверку: неверная или отсутствующая ревизия, неверная версия, повреждённый JSON либо отсутствие версии компилятора должны давать ненулевой код проверяющей программы. Основной workflow должен проходить; отказы проверяй намеренно как негативные кейсы.
5. Создай SHA-256 checksum бинарника и загрузи бинарник, фактический JSON метаданных и checksum одним workflow-артефактом с хранением семь дней. После скачивания должна быть возможность проверить checksum.
6. Сохрани существующие проверки format/test/race/vet/build и права `contents: read`. Не публикуй образы, releases, packages или секреты; подпись и deployment не входят в задание.

Критерии завершения: успешный запуск Actions, скачанный соответствующий артефакт, проверенный checksum и отказы на негативных кейсах. Объясни, почему проверки обнаруживают случайные несоответствия, но не удостоверяют честность вредоносного сборщика. Загрузка артефакта — не подписанная attestation. Решение workflow в урок не включено.
