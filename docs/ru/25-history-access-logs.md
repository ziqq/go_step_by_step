# Урок 25: итоговый проект VI — приватные access-логи истории

[English version](../25-history-access-logs.md)

Время на урок: 50–65 минут: 10 минут чтения, 10 минут запуска и разбора записей, затем 30–45 минут на задание.

В уроке 24 мы проверяли публичный HTTP-контракт. Следующий шаг итогового проекта — получить рабочие диагностические данные: какой маршрут завершился, с каким статусом и за какое время. История чата содержит приватные ID и текст сообщений, поэтому access-запись использует явный набор разрешённых полей вместо сериализации запроса.

## Запуск и разбор

```sh
go run ./lessons/25-history-access-logs
```

Программа выполняет два внутрипроцессных запроса через demo-mux и выдаёт одну JSON-запись на каждый нормально завершившийся запрос. Их статусы — `200` и `404`; известный маршрут обозначен фиксированным шаблоном, неизвестный — `unmatched`. Одна запись выглядит так; время и длительность будут другими:

```json
{"time":"2026-10-16T06:35:00Z","level":"INFO","msg":"http request completed","method":"GET","route":"GET /conversations/{conversationID}/messages","status":200,"duration_ms":0.042}
```

Demo-маршрут возвращает только пустую JSON-фикстуру. Здесь нет аутентификации, БД и загрузки сообщений. При сборке настоящего сервиса сохраняйте границу identity/ошибок урока 24 и membership-транзакцию урока 23. Целевой chat-backend также использует аутентифицированные command envelopes и WebSocket; этот пример логирования buffered REST не реализует и не инструментирует весь его протокол.

## Намеренно небольшая access-запись

Используется стандартный Go `log/slog.JSONHandler`. Он добавляет время, уровень и сообщение; middleware добавляет только эти поля:

| Поле | Источник значения |
|---|---|
| `method` | Фиксированный список обычных HTTP-методов; остальные превращаются в `OTHER` |
| `route` | Разрешённый шаблон истории; всё остальное — `unmatched` |
| `status` | Первый итоговый статус ответа либо обычная неявная `200` |
| `duration_ms` | Длительность работы обработчика, измеренная сервером |

Логгер не читает raw URL, query, ID беседы/пользователя, заголовки, cookies и тела запроса/ответа. Если обогатить переданный logger такими значениями в другом месте, middleware их не удалит. Тест проверяет и полный набор полей, и отсутствие синтетических секретов.

Пример принимает `*http.ServeMux`, получает кандидат на метку через `ServeMux.Handler`, затем вызывает `ServeHTTP` для настоящей маршрутизации и извлечения wildcard. В запись допускается только точный настроенный шаблон истории. Дополнительный поиск сохраняет совместимость примера с API Go 1.22 из репозитория. `Request.Pattern` появился в [Go 1.23](https://go.dev/doc/go1.23#nethttppkgnethttp). Не повышайте минимальную версию модуля молча ради одного поля.

При добавлении маршрута сохраняйте явный список разрешённых меток: системный redirect mux может вернуть в качестве pattern путь перенаправления, производный от запроса. Неизвестные пути, неподдерживаемые методы и такие redirect не должны раскрывать ID через метку. См. [ServeMux.Handler](https://pkg.go.dev/net/http#ServeMux.Handler).

## Как записать статус и сохранить ответ

`statusWriter` передаёт заголовки и запись тела исходному writer. Первая запись тела подразумевает `200`; повторный итоговый `WriteHeader` не заменяет уже зафиксированный статус. Информационный ответ, например `103`, не становится итоговым статусом. `101` считается терминальным, но upgrade протокола находится вне области этого примера.

Middleware пишет completed-запись после нормального возврата mux. Он не перехватывает panic и не обозначает его как успешный пустой ответ. В работающем Go HTTP-сервере обработка panic относится к server/recovery policy и её диагностическому каналу. Запись статуса доказывает поведение обработчика, а не получение клиентом каждого байта ответа.

`Unwrap` позволяет `http.ResponseController` добраться до возможностей исходного writer. Он не сохраняет optional interfaces при прямом type assertion. Используйте обёртку только для обычных buffered endpoints; streaming и WebSocket требуют инструментирования с проверками необходимых им интерфейсов. См. [ResponseWriter](https://pkg.go.dev/net/http#ResponseWriter), [ResponseController](https://pkg.go.dev/net/http#ResponseController) и [JSONHandler](https://pkg.go.dev/log/slog#JSONHandler).

## Проверки и границы доказательства

```sh
gofmt -w ./lessons/25-history-access-logs
go test -count=1 -v ./lessons/25-history-access-logs
go test -race -count=1 ./lessons/25-history-access-logs
go test ./...
go test -race ./...
go vet ./...
```

Целевые тесты проверяют разрешённые поля, синтетические приватные значения во вводе и телах, сохранение ответа, неявный и явный статус, повторные итоговые и информационные заголовки, неизвестные/перенаправленные пути, неизвестные методы, доступ controller к исходному writer, распространение panic и целостность конкурентных JSON-записей. Они не доказывают production-retention, доступность сборщика, настоящую сетевую доставку или приватность остальных логов приложения. PostgreSQL-интеграция остаётся отдельной проверкой и при отсутствии `POSTGRES_TEST_URL` должна отмечаться пропущенной.

## Задание — связать один запрос, не доверяя ID клиента

Добавьте один серверный request ID в ответ, context обработчика и completed access-запись.

1. Генерируйте 16 случайных байт через `crypto/rand` и кодируйте их 32 строчными шестнадцатеричными символами. Передавайте генератор функцией, чтобы тесты могли задавать фиксированные ID и ошибки; внешняя UUID-библиотека не нужна.
2. Храните ID под закрытым context-ключом и предоставьте небольшой accessor. Наследуйте входящий context, сохраняя отмену, deadline и существующие значения.
3. Устанавливайте `X-Request-ID` до вызова mux, передавайте ID обработчику через context и добавляйте то же значение в access-запись. Заменяйте заголовок клиента; correlation ID не является аутентификацией.
4. При ошибке генератора возвращайте общую `500`, не вызывайте mux и пишите очищенную запись ошибки инструментирования без исходного текста ошибки и выдуманного request ID.
5. Добавьте тесты формата ID, равенства header/context/log, поддельного входящего заголовка, сохранения родительского context, ошибки генератора и независимых ID конкурентных запросов. Расширьте список успешной записи только полем `request_id`; сохраните содержательность тестов приватности и ответа.

Запланируйте 30–45 минут. Задание завершено, когда один ID проходит через три наблюдения одного запроса, конкурентные запросы не делят изменяемое состояние запроса, а секреты и текст внутренних ошибок отсутствуют в записях.

## Типичные ошибки

- Логирование всего запроса, raw path, query или объекта ошибки ради удобства.
- Копирование redirect-пути mux в якобы безопасное поле маршрута.
- Восприятие JSON-кодирования как автоматического сокрытия секретов.
- Использование информационного или повторного заголовка как итогового статуса.
- Принятие HTTP-статуса за доказательство доставки или ожидание, что `Unwrap` сохраняет все интерфейсы.
- Повторное использование ID клиента, замена context на `Background` или хранение ID запроса в общем состоянии middleware.
- Выдача request ID за distributed tracing или его использование в metric label.
