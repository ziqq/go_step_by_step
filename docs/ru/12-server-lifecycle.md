# Урок 12: Конфигурация, структурированные логи и graceful shutdown

## Цель

Загружать и проверять конфигурацию процесса, писать структурированные JSON-логи через `log/slog`, возвращать стабильные HTTP-ошибки и корректно останавливать HTTP-сервер при сигнале прерывания или завершения.

Эти части соединяют HTTP-handler из урока 11 с работающим backend-процессом. Сервер отвечает за запуск и остановку, а handler-ы — за проверку запросов и публичный контракт ответа.

## Запускаемый сервер

Полный пример находится в `lessons/12-server-lifecycle/main.go`.

```sh
go run ./lessons/12-server-lifecycle
```

По умолчанию сервер слушает `:8080`. В другом терминале запроси health endpoint:

```sh
curl -i http://localhost:8080/healthz
```

```text
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"status":"ok"}
```

Процесс пишет по одной JSON-записи для запуска, каждого запроса и остановки. Нажми Ctrl+C, чтобы отправить сигнал прерывания и увидеть graceful shutdown.

## Конфигурация из окружения

Пример читает только необходимые настройки и проверяет их один раз при запуске:

| Переменная | По умолчанию | Значение |
|---|---|---|
| `APP_ADDR` | `:8080` | TCP host и port |
| `APP_READ_HEADER_TIMEOUT` | `5s` | Максимальное время чтения заголовков запроса |
| `APP_SHUTDOWN_TIMEOUT` | `10s` | Максимальное ожидание активных запросов при остановке |

Для локальной разработки настройки можно переопределить только для одного процесса:

```sh
APP_ADDR=127.0.0.1:9090 APP_SHUTDOWN_TIMEOUT=15s go run ./lessons/12-server-lifecycle
```

Отклоняй неверную конфигурацию до открытия listener-а. Понятная ошибка при запуске проще для диагностики, чем сервер с опасным таймаутом или неверным адресом.

## Структурированное логирование через slog

`slog` хранит поля отдельно от текстового сообщения. В примере используется `JSONHandler`, поэтому система сбора логов может искать method, path, duration и address, не разбирая произвольный текст.

```go
logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
logger.Info("http request completed", "method", r.Method, "path", r.URL.Path)
```

Не записывай в логи тело запроса, authorization-заголовки, пароли, токены и другие секреты. Логируй достаточно стабильного контекста для понимания события, не раскрывая приватные данные запроса.

## Стабильные HTTP-ошибки

HTTP-ошибка состоит из двух частей: status code для обработки на уровне протокола и тела ответа, на которое может опираться клиент. Сохраняй публичную форму ошибки стабильной и не возвращай внутренний текст ошибки.

```go
type apiError struct {
	Code    string `json:"code"`
	Message string `json:"message"`
}
```

В этом уроке неизвестные пути возвращают `404 Not Found` с одной и той же JSON-формой. В большом сервисе преобразуй известные domain-ошибки в публичные статусы на границе handler-а, а внутреннюю причину записывай отдельно в лог.
Стандартный mux возвращает `405 Method Not Allowed`, если известный путь вызван с неподдерживаемым методом.

## Жизненный цикл graceful shutdown

Пример использует `signal.NotifyContext`, чтобы преобразовать Ctrl+C или SIGTERM в отмену context. После отмены `Server.Shutdown` прекращает принимать новые соединения и ждет завершения активных handler-ов. Shutdown context создается от `context.Background()`, потому что context запроса или сигнала уже отменен; для остановки задается отдельный конечный таймаут.

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()

if err := server.Shutdown(shutdownCtx); err != nil {
	_ = server.Close()
	return err
}
```

Ожидание при остановке ограничено по времени. Если deadline истек, пример закрывает оставшиеся соединения и возвращает ошибку. Так у системы развертывания есть предсказуемая верхняя граница времени остановки процесса.

## Тестирование жизненного цикла

Используй `httptest`, чтобы проверить статус и JSON-ответ без открытия публичного порта. Для shutdown открой локальный listener на временном порту, запусти один намеренно заблокированный handler, отмени context сервера, затем освободи handler. Сервер должен дать активному запросу завершиться до возврата из `serve`.

Так тестируется поведение, а не только факт вызова `Shutdown`. Race detector дополнительно проверяет конкурентную работу сервера и теста.

## Типичные ошибки

- читать переменные окружения во время каждого запроса вместо однократной проверки при запуске;
- принимать нулевые или отрицательные таймауты;
- логировать секреты или полное тело запроса;
- возвращать клиентам внутренние ошибки как есть;
- использовать уже отмененный signal context для shutdown и не оставлять время на завершение запросов;
- завершать процесс сразу, не вызывая `Server.Shutdown`;
- ждать активные запросы бесконечно, не ограничивая shutdown deadline;
- считать, что `200` health endpoint доказывает готовность всех зависимостей.

## Практика: настрой write timeout

Добавь `APP_WRITE_TIMEOUT` в конфигурацию и сервер в `lessons/12-server-lifecycle`.

Требования:

1. Значение по умолчанию — `10s`; неверные, нулевые и отрицательные duration должны отклоняться.
2. Передавай это значение в `http.Server.WriteTimeout`.
3. Добавь табличные тесты для значения по умолчанию, корректного переопределения и ошибочных значений.
4. Сохрани существующие значения по умолчанию и поведение остальных параметров.
5. Коротко объясни в Go-комментарии или заметках к уроку, чем write timeout отличается от read-header и shutdown timeout.

Проверь пакет и весь репозиторий командами выше. Не добавляй сторонний пакет конфигурации или логирования.

## Критерии завершения

Ты можешь проследить путь от переменных окружения до проверенного сервера, объяснить, какой context управляет работой запросов и какой ограничивает shutdown, и показать тестом, что активные запросы завершаются при корректной остановке.
