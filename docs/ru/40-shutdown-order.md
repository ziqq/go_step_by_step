# 40. Как завершить HTTP и воркеры перед закрытием общих ресурсов

[English version](../40-shutdown-order.md) · [Запускаемый пример](../../lessons/40-shutdown-order/main.go)

HTTP-обработчик чата и фоновый воркер могут работать с одним пулом PostgreSQL. Если закрыть пул сразу после остановки слушателя, уже принятые операции могут завершиться ошибкой. Владелец сервиса должен дождаться обеих групп.

Урок 12 ввёл остановку HTTP, а урок 39 показал, как снимать готовность. Backend чата использует один дедлайн для HTTP и фоновой работы и отдельно обрабатывает случай, когда ожидание завершилось неудачей. Здесь разберём порядок закрытия общего ресурса.

## Запуск примера

go test -count=1 -v ./lessons/40-shutdown-order
go test -race -count=20 ./lessons/40-shutdown-order

В примере HTTP-сервер без слушателя, один имитированный воркер и заглушка хранилища. Тесты управляют этапами через функции и каналы.

## Порядок остановки

1. Владелец сервиса один раз вызывает `shutdownService` со свежим контекстом и одним дедлайном. Контекст сигнала к этому моменту уже может быть отменён. Если создать дочерний контекст от него, времени на остановку не останется.

2. Сними готовность и сообщи воркерам, что пора прекратить приём работы. Функция отправки сигнала возвращается сразу. Канал завершения закрывается только после того, как воркеры перестали использовать общий ресурс.

3. Передай в `http.Server.Shutdown` тот же контекст, с которым ждёшь воркеров. HTTP и воркеры могут завершаться одновременно. После обоих этапов ещё раз проверь контекст перед закрытием ресурса. Если оба канала готовы, `select` может выбрать канал завершения.

4. Если остановка HTTP вернула ошибку или срок истёк до начала закрытия, верни ошибку и оставь ресурс открытым. Владелец сервиса выбирает, как безопасно завершить процесс. Метод `io.Closer.Close` не принимает контекст. Дедлайн ограничивает ожидание и операции, которые его учитывают.

Возврат `http.ErrServerClosed` из `Serve` сообщает об остановке приёма соединений. Владелец должен также дождаться возврата из `Shutdown`. Для соединений с изменённым протоколом, например WebSocket, нужно отдельно отслеживать завершение. [Go Server.Shutdown](https://pkg.go.dev/net/http#Server.Shutdown)

## Практика: закрыть несколько ресурсов в обратном порядке

Передай финальному этапу список ресурсов в порядке их получения. Владелец вызывает координатор один раз и передаёт ненулевые ресурсы. Адаптируй пример и подготовку тестов, сохранив поведение остановки.

1. После успешной остановки HTTP и завершения воркеров закрывай ресурсы в обратном порядке. Пустой список допустим.

2. После начала закрытия попробуй закрыть каждый ресурс, даже если предыдущий вернул ошибку или контекст отменён. Объедини ошибки через `errors.Join`, чтобы вызывающий код мог найти каждую причину через `errors.Is`.

3. Проверь пустой список, обратный порядок, две независимые ошибки, отмену при закрытии первого ресурса и отсутствие вызовов `Close` после ошибки HTTP или незавершённых воркеров.

Критерий завершения. Объясни, почему отмена до начала закрытия может оставить ресурсы открытыми, почему поздняя отмена не откатывает закрытие и почему остановки слушателя недостаточно для закрытия общего пула.

## Типичные ошибки

- Закрывать пул через `defer` в функции, которая возвращается сразу после остановки слушателя.
- Создавать отдельный таймаут для каждого этапа ожидания и случайно увеличивать общий срок.
- Считать отправку сигнала воркеру доказательством его завершения.
- Ожидать, что `http.Server.Shutdown` дождётся WebSocket или что контекст прервёт произвольный `Close`.
