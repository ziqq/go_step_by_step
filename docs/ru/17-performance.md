# Урок 17: сначала измеряй, потом оптимизируй

## Цель

Использовать бенчмарки, отчёты об аллокациях, CPU- и memory-профили, а также ограниченный локальный нагрузочный эксперимент, чтобы опираться на измерения, а не на догадки. В примере подсчитываются непрочитанные сообщения пользователя в нескольких чатах — это похоже на подготовку сводок для списка чатов в backend.

Текущая `CountUnread` намеренно устроена просто: для каждого входящего сообщения функция перебирает курсоры чтения и ищет самый поздний курсор пользователя для этого чата. Это удобная отправная точка для измерений, а не рекомендуемый окончательный алгоритм.

## Запуск примера и тестов

```sh
go run ./lessons/17-performance
go test ./lessons/17-performance
```

```text
unread messages: 1
```

Контракт намеренно небольшой: собственные сообщения пользователя не считаются непрочитанными; сообщение непрочитано, только если оно новее последнего подходящего курсора этого пользователя; сообщение с тем же временем, что и курсор, уже прочитано; если курсора нет, входящие сообщения считаются непрочитанными. Курсоры других пользователей и чатов не должны влиять на результат.

## Измерение исходного алгоритма

```sh
go test -run '^$' -bench '^BenchmarkCountUnread$' -benchmem -count=5 ./lessons/17-performance
```

Бенчмарк готовит входные данные до начала измерения. `ns/op` — время на операцию; `B/op` и `allocs/op` показывают объём и число аллокаций за операцию. Сейчас функция не создаёт аллокаций при каждом вызове, но повторный перебор курсоров расходует CPU по мере роста входных данных. Не проверяйте в обычном unit-тесте машинозависимый порог времени.

До изменения алгоритма сохраните точную команду, версию Go, размеры входных данных и исходный результат. После оптимизации повторите тот же бенчмарк. Сравнивайте несколько запусков на одной машине и при похожей нагрузке: один необычно быстрый результат ещё не доказывает улучшение. Корректность по-прежнему защищают тесты, чтобы оптимизация не изменила правила подсчёта.

## Поиск затрат CPU и памяти

Снимайте CPU- и allocation-профили в отдельных запусках. Тестовый бинарник и профили останутся во временном каталоге, а не появятся в репозитории.

```sh
profile_dir="$(mktemp -d)"
go test -run '^$' -bench '^BenchmarkCountUnread$' -benchtime=5s -cpuprofile "$profile_dir/cpu.pprof" -o "$profile_dir/performance.test" ./lessons/17-performance
go tool pprof -top "$profile_dir/performance.test" "$profile_dir/cpu.pprof"
```

```sh
go test -run '^$' -bench '^BenchmarkCountUnread$' -benchtime=5s -memprofile "$profile_dir/heap.pprof" -o "$profile_dir/performance.test" ./lessons/17-performance
go tool pprof -sample_index=alloc_space -top "$profile_dir/performance.test" "$profile_dir/heap.pprof"
go tool pprof -sample_index=inuse_space -top "$profile_dir/performance.test" "$profile_dir/heap.pprof"
```

CPU-профиль показывает функции, на которые пришлось выборочно измеренное процессорное время. `alloc_space` помогает найти суммарный объём аллокаций, а `inuse_space` — память, остающуюся занятой на момент снимка. Профиль описывает измеренную нагрузку, а не всю production-систему. Профилирование добавляет накладные расходы, а разные типы профилей могут мешать друг другу, поэтому для сравнения снимайте их отдельно. Подробнее инструменты описаны в [руководстве Go по диагностике](https://go.dev/doc/diagnostics), документации [`testing.B`](https://pkg.go.dev/testing#B) и [статье Go о pprof](https://go.dev/blog/pprof).

## Бенчмарк — не нагрузочное тестирование

Микробенчмарк вызывает одну функцию с данными в памяти. Он помогает сравнить эту часть работы, но не учитывает HTTP-маршрутизацию, задержку базы данных, пулы соединений, очереди и сеть. Параллельный бенчмарк может показать конкуренцию за ресурсы внутри функции, но всё ещё не является production-нагрузочным тестом.

Для эксперимента на уровне сервиса запускайте нагрузку только на локальном тестовом сервере или в явно разрешённом staging-окружении. Используйте фиксированные данные, ограничьте время и число параллельных клиентов, записывайте количество запросов, ошибки и перцентили задержки. Не запускайте эксперимент на production или общем сервисе без явного разрешения. Результат бенчмарка функции из этого урока нельзя выдавать за пропускную способность API целиком.

## Типичные ошибки

- оптимизировать по интуиции, не сохранив повторяемую исходную точку;
- менять семантику ради скорости или сравнивать запуски с разными данными;
- включать подготовку тестовых данных во время измерения функции;
- доверять одному запуску или фиксированному порогу `ns/op` для разных машин;
- путать `B/op` с удерживаемой памятью или читать профиль без учёта выбранного типа выборки;
- одновременно снимать разные профили и принимать их накладные расходы за поведение приложения;
- считать микробенчмарк или бенчмарк `httptest` доказательством production-пропускной способности;
- запускать нагрузку на публичный или общий сервис без разрешения и строгих ограничений.

## Практика: индексируй курсоры и измерь результат

Улучши `CountUnread`, чтобы функция не перебирала все курсоры для каждого сообщения. Построй индекс последнего курсора по паре `(user, conversation)`, затем подсчитывай непрочитанные сообщения, сохранив текущий контракт функции.

1. Оставь все существующие тесты зелёными. Добавь целевые случаи, если при реализации обнаружится неучтённая граница контракта; не ослабляй и не удаляй текущие проверки.
2. До изменения алгоритма сними исходный результат имеющегося бенчмарка. После изменения запусти ту же команду, с тем же размером данных и версией Go; укажи старые и новые `ns/op`, `B/op` и `allocs/op`.
3. Сними и изучи CPU- и memory-профили до и после. Объясни, какая функция или операция изменилась и что профили могут и не могут доказать.
4. Для небольшого эксперимента на уровне сервиса оберни функцию локальным HTTP-обработчиком и отправь запросы через локальный тестовый сервер с фиксированным числом работников и ограничением по времени. Запиши общее количество запросов, ошибки и p50/p95. Отдели этот результат от микробенчмарка и не добавляй хрупкие пороги задержки в unit-тесты.
5. После изменений запусти race detector и vet. Храни профили и результаты бенчмарка вне репозитория.

## Критерии завершения

Ты можешь объяснить сложность исходного алгоритма и компромисс при индексировании курсоров; сохраняешь контракт подсчёта непрочитанных сообщений; показываешь повторяемое сравнение бенчмарков до и после; различаешь выделенную и удерживаемую память; используешь профиль для изучения измеренной нагрузки; и объясняешь, почему бенчмарк внутри процесса не доказывает пропускную способность API. Реализацию задания ты выполняешь самостоятельно.
