# Урок 19: проектирование систем — контракты, пагинация, кеш и фоновые задачи

Время на урок: 35–50 минут.

В этом уроке объединены темы production-части курса в небольшой проверяемый дизайн. Запускаемый пример реализует HTTP-контракт списка сообщений с keyset-пагинацией. Это учебный REST-пример, а не утверждение, что в референсном chat-backend есть именно такой маршрут: текущий сценарий списка сообщений там использует аутентифицированные команды и непрозрачные курсоры. Используйте backend только как read-only источник реалистичных ограничений.

## Запуск примера

```sh
go run ./lessons/19-system-design
go test ./lessons/19-system-design
```

Пример сортирует сообщения по `created_at DESC, id DESC`. ID служит стабильным вторым ключом, если время совпадает. Код читает одну дополнительную строку, чтобы понять, существует ли следующая страница, а курсор строит по последней возвращённой строке. В этом упражнении курсор — URL-safe Base64 от JSON для наглядности; он не зашифрован и не подписан, а также не является удостоверением доступа.

В endpoint с базой данных используйте такое же сравнение в SQL и подходящий индекс. PostgreSQL предупреждает, что пагинация без предсказуемого `ORDER BY` может возвращать непоследовательные подмножества, а строки, пропущенные через `OFFSET`, всё равно приходится вычислять. См. [LIMIT и OFFSET](https://www.postgresql.org/docs/current/queries-limit.html).

## Контракт, который нужно сохранить

`GET /messages` принимает `conversation_id`, необязательный `limit` (по умолчанию 20, диапазон 1–50) и необязательный `cursor`. Успешный ответ содержит `messages` и `next_cursor`; на последней странице курсор пуст. Отсутствующий ID беседы, некорректный курсор, курсор для другой беседы и limit вне диапазона приводят к JSON-ошибке `400`. Поддерживается только GET.

В реальном сервисе проверяйте права пользователя на беседу при каждом запросе, включая запросы с валидным курсором. Привязывайте состояние курсора к области запроса и сортировке; непрозрачный токен не доказывает наличие доступа. Сохраняйте форму ошибок и порядок результатов стабильными, чтобы клиент мог безопасно переходить между страницами.

## Кеширование приватных ответов

Если кешировать список сообщений конкретного пользователя, ключ кеша должен включать все входные данные, меняющие представление: пользователя или область прав, беседу, фильтры, курсор, limit и версию представления. Кеш, ключом которого служит только URL, может раскрыть данные одного пользователя другому. Для приватных данных явно выберите политику: например, `Cache-Control: private, no-cache`, если допустимо приватное хранение с повторной проверкой; используйте `no-store`, если хранение недопустимо. `private` запрещает хранение в общем кеше, а `no-cache` требует проверять валидность перед повторным использованием. См. [RFC 9111, HTTP Caching](https://www.rfc-editor.org/rfc/rfc9111.html).

ETag может идентифицировать представление. Позже клиент отправляет его в `If-None-Match`; если выбранное представление не изменилось, сервер отвечает `304 Not Modified` без тела. Валидатор должен меняться при изменении любого отображаемого поля, а не только при изменении числа сообщений. Условные запросы описаны в [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html).

Инвалидация кеша — часть контракта записи: новое сообщение может изменить первую страницу и её курсор, а обновление статуса прочтения может изменить поля, даже если состав и порядок списка остались прежними. Определите, какие события инвалидируют или обновляют каждый затронутый ключ. Не помещайте аутентифицированный контент в общий кеш, если модель доступа явно этого не допускает.

## Фоновые задачи и развитие сервиса

Не запускайте неограниченную отсоединённую горутину из обработчика запроса для надёжной фоновой работы. Если транзакция БД должна запустить доставку, сохраняйте запись outbox в той же транзакции; worker может забирать её, ограниченно повторять попытки и обрабатывать идемпотентно. Это связано с очередью и обратным давлением из практики урока 18. Определите, что происходит после повторных ошибок, как обрабатываются дубликаты и какой сигнал покажет оператору, что задача застряла.

Предпочитайте аддитивное развитие API: необязательные поля ответа и новые необязательные query-параметры обычно безопаснее для старых клиентов, чем изменение смысла полей, порядка или кодов ошибок. Поддерживайте декодирование курсоров в течение всего срока их действия либо версионируйте формат и задайте срок годности. Для несовместимых изменений нужны явный путь миграции и план обновления клиентов и сервера.

## Задание — условное кеширование

Реализуйте условное кеширование этого endpoint, не меняя контракт пагинации:

1. Вычисляйте ETag для точного представления ответа и возвращайте заголовок с политикой приватного кеширования.
2. При совпадающем `If-None-Match` отвечайте `304 Not Modified` без тела; изменившееся представление должно давать другой валидатор.
3. Добавьте целевые тесты для cache hit, изменения сообщения и изоляции двух бесед или областей прав. Добавьте случай, когда отображаемое поле меняется, но число сообщений остаётся прежним.
4. Напишите короткую заметку о том, какие записи инвалидируют кеш и происходит ли инвалидация синхронно или через идемпотентный worker с outbox.

Не реализуйте в этом задании общий кеш или фонового worker. Сначала обеспечьте корректность валидатора и HTTP-контракта. Запустите целевые тесты, затем все проверки репозитория. Задание завершено, когда тестами покрыты ответы `200` и `304`, тело `304` пусто, а в заметке указаны ключ кеша и события инвалидации.

## Типичные ошибки

- Пагинация только по времени, из-за которой пропускаются строки с одинаковым timestamp.
- Использование `OFFSET` для глубоких страниц без учёта стоимости запроса и параллельных вставок.
- Повторное использование курсора с другой беседой, фильтром или сортировкой.
- Восприятие Base64 как шифрования, защиты целостности или авторизации.
- Отсутствие пользователя или области запроса в ключе кеша приватного ответа.
- Ответ `304` с телом или неизменный ETag после изменения отображаемых данных.
- Бесконечные повторы worker, неидемпотентная обработка дубликатов или потеря задачи между commit и enqueue.
