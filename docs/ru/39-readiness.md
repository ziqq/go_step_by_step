# 39. Готовность сервиса и ограниченная проверка зависимости

[English version](../39-readiness.md) · [Запускаемый пример](../../lessons/39-readiness/main.go)

Liveness показывает, способен ли процесс ответить на проверку. Readiness показывает, стоит ли направлять на этот экземпляр рабочий трафик. При временной недоступности PostgreSQL полезно убрать экземпляр из маршрутизации. Перезапуск всех исправных процессов во время того же сбоя может затруднить восстановление.

В уроке 15 готовность хранилась в памяти. В backend чата один дедлайн запроса охватывает проверки PostgreSQL и хранилища медиа. Этот пример ограничивает число одновременных обращений к зависимости и показывает, как снять готовность, пока HTTP ещё отвечает.

## Запуск и проверка

```sh
go run ./lessons/39-readiness
go test -count=1 -v ./lessons/39-readiness
go test -race -count=20 ./lessons/39-readiness
go vet ./lessons/39-readiness
```

```text
/readyz 204
/readyz 503
/healthz 204
```

Пример вызывает маршрутизатор в памяти и передаёт в `newProbes` имитацию зависимости. При сборке реального сервиса можно передать значение метода `db.PingContext`. Конструктор ожидает ненулевую функцию и положительный таймаут.

## Как проходит запрос

1. `GET /healthz` возвращает 204 без обращения к зависимостям. `GET /readyz` возвращает 204 после успеха и 503 при остановке, занятости, отмене, истечении срока или ошибке зависимости. В Go шаблоны GET также принимают HEAD. Ответы пустые, с `Cache-Control: no-store`.

2. Канал ёмкостью один пропускает одну активную проверку готовности. Второй запрос сразу получает 503. Место остаётся занятым до возврата из функции проверки и освобождается при любом выходе.

3. `context.WithTimeout(parent, timeout)` наследует отмену и более ранний дедлайн запроса. После вызова проверь `ctx.Err()`, чтобы поздний возврат nil не превратил отмену в успех. Таймаут кооперативный. Функция, которая его игнорирует, может удерживать место.

4. Вызови `beginDrain` перед остановкой HTTP-сервера. Запросы, начавшиеся после его возврата, пропустят зависимость. Активная проверка тоже вернёт 503, если увидит флаг на финальной проверке. Уже принятое решение о 204 может дойти до клиента позже. Снятие готовности само по себе не отменяет и не дожидается обработчиков. У остановки сервера и обновления маршрутизации свои сроки.

## Практика: проверить фиксированный набор зависимостей под одним дедлайном

Замени одну функцию проверки упорядоченным срезом функций и возвращай из конструктора `(*probes, error)`. Адаптируй пример и подготовку существующих тестов к сигнатуре, сохранив их проверки поведения.

1. Отклоняй пустой список, nil в любом элементе и неположительный таймаут. Возвращай nil и общую ошибку конфигурации. Скопируй срез, чтобы замена элемента вызывающим кодом после создания не меняла проверки.

2. Запускай проверки последовательно в заданном порядке. Занимай одно место и создавай один дочерний контекст на всю последовательность. Останавливайся на первой ошибке. Проверяй отмену и флаг остановки перед каждым вызовом и перед возвратом успеха. Сохрани коды и пустые ответы.

3. С помощью имитаций проверь ошибки конфигурации, порядок и общий дедлайн, независимость от среза вызывающего кода, пропуск оставшихся проверок после ошибки, а также остановку или отмену во время первой проверки. Докажи, что второй запрос не входит в последовательность, пока первый держит место. Управляй порядком через каналы и дождись запущенных горутин.

Критерий завершения. Только успех всех проверок под общим дедлайном даёт 204. Объясни, почему новый таймаут на каждую зависимость удлиняет возможное ожидание и чем снятие готовности отличается от ожидания завершения активных запросов.

## Типичные ошибки

- Проверять базу в liveness или отдавать клиенту текст ошибки зависимости.
- Освобождать место по таймеру, пока функция ещё работает.
- Создавать новый таймаут от `context.Background()` и терять отмену запроса.
- Считать успешный ping доказательством исправности всех операций приложения.
- Считать, что после 503 уже направленные запросы мгновенно прекратятся.
