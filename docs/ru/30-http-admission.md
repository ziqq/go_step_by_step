# Урок 30: ограничение параллельной HTTP-работы без неограниченной очереди

[English version](../30-http-admission.md)

Выделите не меньше 40 минут: прочитайте и запустите пример, затем потратьте минимум 30 минут на задание с маршрутизацией. Soft-delete миграция из урока 29 остаётся отдельным заданием: этот урок не меняет её SQL и не содержит решения.

## Почему одного пула соединений мало

Небольшой SQL-пул ограничивает соединения, но не все ожидающие HTTP-обработчики. Если запросы приходят быстрее, чем завершается работа, ожидания продолжают накапливаться. В уроке 18 мы ограничивали очередь; здесь **очереди ожидания приложения нет**: допускаем ограниченное число синхронных обработчиков, а лишнюю работу сразу отклоняем.

Откройте [запускаемый пример](../../lessons/30-http-admission/main.go) и [его тесты](../../lessons/30-http-admission/main_test.go). Нужны только стандартная библиотека и `httptest`, без базы и слушающего порта. Пример — транспортная заготовка, а не чат с настоящей аутентификацией.

В backend чата чтение истории, запись сообщений и обработка медиа конкурируют за ресурсы. Референсный backend тоже ограничивает параллельную дорогую обработку медиа. Здесь берём только небольшой локальный бюджет: распределённые квоты того проекта не воспроизводим и его код не меняем.

## Одна обёртка — один бюджет

`limitConcurrency(max, next)` отклоняет неположительный лимит и nil-обработчик при создании. Создайте обёртку один раз и переиспользуйте результат. Если создавать её **для каждого запроса**, каждый получит собственный пустой бюджет: общего ограничения не будет.

Основной фрагмент:

```go
select {
case slots <- struct{}{}:
    defer func() { <-slots }()
    if r.Context().Err() != nil {
        admissionError(w, "request_canceled", false)
        return
    }
    next.ServeHTTP(w, r)
default:
    admissionError(w, "overloaded", true)
}
```

Полная обёртка проверяет отмену ещё и **до** этого фрагмента. Отправка токена резервирует место, отложенное получение освобождает его. Ветка `default` отклоняет запрос вместо ожидания. Не закрывайте канал-семафор при shutdown: запросы ещё могут писать в него, закрытие канала не заменяет протокол завершения сервера.

Запросы к одной возвращённой обёртке используют общий канал. Две отдельно созданные обёртки имеют независимые бюджеты, даже при одинаковом `max = 2`. Несколько процессов умножают локальную ёмкость: это не общий лимит кластера и не лимит пользователя. Ограничиваются входы в `next.ServeHTTP`, а не принятые TCP-соединения, уже созданные HTTP-сервером горутины, память одного запроса или запросы в секунду.

## Отмена кооперативная; место принадлежит обработчику

Уже отменённый запрос не запускает работу. Повторная проверка после получения места сужает гонку с отменой, но не делает отмену и запуск обработчика атомарными. После входа исходный запрос и его context передаются дальше без изменений. SQL-запросы и другие блокирующие операции всё равно должны учитывать этот context.

Не запускайте `next.ServeHTTP` в отдельной оторванной горутине с освобождением места при отмене клиента. Обработчик может продолжать работу: раннее освобождение позволит превысить лимит. Держите место до возврата синхронного вызова или раскрутки стека. `defer` срабатывает и при panic; обёртка не проглатывает панику и не подменяет её успешным ответом.

Исходный `ResponseWriter` передаётся напрямую: нет буферизации и потери необязательных интерфейсов. Обёртка не создаёт таймаут, не останавливает игнорирующий отмену обработчик, не реализует recovery и не разрешает писать после возврата `ServeHTTP`. Долгоживущий stream занял бы место на всё время работы обработчика: не переносите этот бюджет обычной HTTP-работы на SSE/WebSocket или health-проверки без отдельного решения.

## Контракт публичных ответов

Когда свободных мест нет, пример возвращает:

```text
HTTP status: 503
Content-Type: application/json; charset=utf-8
Cache-Control: no-store
Retry-After: 1
Body: {"error":"overloaded"}
```

Обнаруженная до входа в обработчик отмена возвращает `503` с `{"error":"request_canceled"}` и **без** `Retry-After`. Это явно выбранная политика урока, а не статус, который Go автоматически отправляет отменённым клиентам. Отключившийся клиент может вообще не получить ответ. Если работа уже началась, обёртка не переписывает ответ обработчика из-за отмены.

`Retry-After: 1` — подсказка, не бронь места и не гарантия свободной ёмкости через секунду. Повторяющего запросы клиента в примере нет. Нельзя вслепую повторять записывающий сообщение POST после неопределённого результата: admission не заменяет идемпотентность и не выясняет исход неоднозначного commit. `429` обычно относится к отдельной политике частоты запросов клиента, а не к этому общему счётчику параллельной работы.

## Запуск и проверка

Из корня репозитория:

```sh
go run ./lessons/30-http-admission
go test -count=1 -v ./lessons/30-http-admission
go test -race -count=20 ./lessons/30-http-admission
```

Ожидаемый вывод:

```text
busy: 503, retry-after: 1
first: 204
after release: 204
```

Первый запрос удерживается барьером на канале, поэтому второй встречает занятый бюджет. После освобождения следующий запрос проходит. Для создания перегрузки не нужен подобранный `Sleep`.

Тесты проверяют ошибочную конфигурацию, сохранение запроса/writer/ответа, два допущенных запроса и отклонённую пачку, повторное использование мест, заранее отменённый запрос при свободной и занятой ёмкости, отмену во время работы, распространение panic с освобождением места и стабильный вывод примера. Таймеры только завершают зависший тест ошибкой, порядок задают сигналы каналов. Это локальные тесты обработчика, **не** сетевой нагрузочный тест и не доказательство production-задержек, disconnect или общей ёмкости кластера.

## Задание: общий бюджет работы и отдельная health-проверка — не реализовано

Соберите в этом уроке локальную композицию `http.ServeMux` с контрактом ниже. Используйте синтетические обработчики, без настоящего хранилища сообщений и аутентификации.

1. `GET /healthz` возвращает `204`, даже когда бюджет работы исчерпан, и не занимает рабочее место. Это заготовка, не проверка готовности базы.
2. `GET /conversations/{conversationID}/messages` и `POST /conversations/{conversationID}/messages` используют **один** бюджет ёмкостью 1. Примените существующую обёртку без изменения политики допуска. Оба синтетических обработчика возвращают `204` после открытия тестового барьера.
3. Пока GET удерживается внутри рабочего обработчика, POST получает существующий JSON перегрузки, `503` и `Retry-After: 1`; затем проверьте обратный случай: POST занимает место, GET отклоняется. Отдельный limiter на каждый маршрут должен приводить к падению ваших тестов.
4. Докажите, что health завершается в обоих случаях перегрузки, отклонённая работа не попадает в обработчики, а после освобождения место переиспользуется. Неизвестные пути возвращают `404`, неподдерживаемые методы известных маршрутов — `405`, без занятия рабочего места. Выбирайте маршрут до admission и сохраняйте запрос/context.
5. Добавьте независимые тесты с каналами и конечными watchdog-таймерами, включая заранее отменённый рабочий запрос; запустите race detector. Сохраните опубликованные тесты обёртки. Не добавляйте очередь, повторы, инфраструктуру метрик, распределённые lease и решения предыдущих заданий.

Критерий завершения: тесты подтверждают один бюджет двух рабочих маршрутов, обход для health, ошибки маршрутизации, отмену и повторное использование места. Объясните, почему отдельная обёртка на каждый маршрут удвоит предполагаемую суммарную ёмкость. Композиция и новые тесты остаются за вами.

## Финальные проверки и типичные ошибки

```sh
gofmt -l lessons/30-http-admission/*.go
go test -p 1 -count=1 ./...
go test -race -p 1 -count=1 ./...
go vet ./...
```

SQL integration tests прошлых уроков требуют временную базу и `POSTGRES_TEST_URL`; без этой переменной они пропускаются. Самому уроку 30 Docker не нужен. Зелёные unit tests не доказывают работу базы.

Типичные ошибки: создавать limiter внутри каждого запроса; блокировать отправку и получать неявную очередь; освобождать место по отмене, пока работа идёт; терять токен после panic; закрывать канал при shutdown; давать маршрутам независимые бюджеты; ограничивать health вместе с дорогой работой; путать параллельность с частотой запросов или авторизацией; считать retry-подсказку разрешением дублировать запись.
