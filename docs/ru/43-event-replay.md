# 43. Повторная доставка сохранённых событий чата по курсору

[English version](../43-event-replay.md) · [Запускаемый пример](../../lessons/43-event-replay/main.go)

После переподключения клиент может запросить сохранённые события после последнего применённого ID. Сервер чата читает события для аутентифицированных арендатора и пользователя и продвигает курсор сессии после каждой успешной постановки в очередь. Здесь разберём этот цикл на хранилище в памяти и функции доставки. Урок 27 показывает запись событий, а урок 42 посвящён рассылке временных подсказок.

## Запуск примера

```sh
go run ./lessons/43-event-replay
go test -count=1 -v ./lessons/43-event-replay
go test -race -count=20 ./lessons/43-event-replay
go vet ./lessons/43-event-replay
```

```text
4 message created
7 message edited
cursor: 7
```

Пример начинает с ID 2 и запрашивает по одному событию. Он доставляет 4 и 7, затем читает пустую страницу. Поменяй начальный курсор на 4 и посмотри, какое событие останется.

## Как движется курсор

1. Загрузчик читает разрешённый поток строго после курсора. В SQL можно применить фильтр по доверенной области доступа, условие `event_id > cursor`, сортировку `ORDER BY event_id ASC` и `LIMIT`. В ID допустимы пропуски. Загрузчик должен обеспечить стабильный порядок: событие с ID позади курсора уже не может впервые стать видимым. Одна возрастающая последовательность не гарантирует этого при конкурентных коммитах.

2. Цикл проверяет всю страницу до первого вызова доставки. Превышение лимита, старый ID, дубликат или убывающая пара означают ошибку загрузчика. Загрузчик заполняет страницу до лимита, если событий достаточно. Неполная или пустая страница завершает проход. Позднее добавленные события можно прочитать следующим проходом.

3. Курсор продвигается, когда функция доставки возвращает nil. При ошибке чтения, доставки или отмене контекста возвращай последний принятый ID. Хранилище и функция доставки получают один контекст и сами соблюдают его при блокирующих операциях.

4. Постановка в локальную очередь и применение события клиентом происходят в разные моменты. Клиент переподключается со своим последним применённым курсором. Если событие дошло, но подтверждение потерялось, клиент может увидеть тот же ID снова. Повторное применение должно быть идемпотентным.

## Практика · Ограничь число страниц за один проход

Добавь положительный параметр `maxPages` и возвращай флаг `needsAnotherPass`. Сохрани правила курсора, проверки страниц и обработки ошибок.

1. Считай каждую успешную загрузку, включая пустую. Неполная или пустая страница завершает проход с false. Если последняя разрешённая страница полная и все её события приняты, верни true с обновлённым курсором. True означает, что остаток можно узнать только следующим чтением. Соблюдай лимит, даже если последняя доступная страница заполнилась ровно.

2. При ошибке входных данных, отмене, ошибке чтения или доставки возвращай false и последний принятый курсор. Отклоняй неположительный лимит до вызова загрузки или доставки. Перед успешным возвратом проверь отмену.

3. Проверь полную страницу на границе лимита и продолжение, которое читает пустую страницу. Также проверь неполную страницу на границе, некорректный лимит и ошибку посреди последней разрешённой страницы. Сверь точные курсоры загрузок, число вызовов, возвращённый прогресс и исходную ошибку.

## Типичные ошибки

- Включающий курсор повторно загружает последнее событие.
- Курсор, заранее переставленный в конец страницы, может пропустить события после ошибки записи.
- Остановка при пропуске в нумерации теряет следующие события.
- Один лимит размера страницы допускает долгий проход, когда накопилось много событий или продолжают приходить новые.

## Критерии завершения

Пример печатает три ожидаемые строки. Исходные и добавленные тесты проходят с детектором гонок. Проход соблюдает лимит страниц, а следующий продолжает с последнего принятого ID.
