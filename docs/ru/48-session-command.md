# 48. Разбираем одну команду сессии до обработки

[English version](../48-session-command.md) · [Запускаемый пример](../../lessons/48-session-command/main.go)

Урок 47 ограничивает данные кадра. Теперь преврати байты в команду перед передачей прикладному коду. В бэкенде чата hello-кадр читается и проверяется до создания сессии устройства. В этом уроке границу показывает небольшая команда отправки сообщения.

## Запусти и изучи

```sh
go run ./lessons/48-session-command
go test -count=1 -v ./lessons/48-session-command
go test -race ./lessons/48-session-command
go vet ./lessons/48-session-command
```

```text
send to conversation 7: hello
```

На вход приходит полное содержимое одного кадра. Его размер уже проверен владельцем транспорта.

```json
{"type":"send","conversation_id":7,"body":"hello"}
```

## Проследи за проверками

1. Создай новый decoder и получателя для каждого кадра. DisallowUnknownFields отклоняет поля за пределами структуры. Команда содержит клиентские данные. Principal берётся из аутентифицированной сессии, а прикладной код проверяет участие в беседе до записи.

2. Декодируй в указатель, чтобы явно отклонить null верхнего уровня. Потребуй type со значением send, положительный int64 идентификатор беседы и хотя бы один непробельный символ в body. После проверки сохрани исходное body вместе с пробелами отправителя.

3. Декодируй ещё раз и потребуй io.EOF. Пробелы после объекта допустимы. Второе значение, включая null, и некорректный хвост вызывают ошибку. При любой ошибке возвращай нулевую команду, чтобы частично заполненные поля не дошли до обработки.

4. Оборачивай ошибки decoder через %w. Тесты используют errors.As для ошибок синтаксиса и типов, errors.Is для ошибок значений и второго объекта. На границе соединения преобразуй их в стабильную публичную ошибку протокола. Исключи детали парсера и содержимое кадра из публичных ошибок и логов.

Стандартный decoder принимает повторяющиеся ключи и сопоставляет поля структуры без учёта регистра. DisallowUnknownFields сохраняет это поведение. В практике нужно ужесточить обработку имён полей. [Документация encoding/json](https://pkg.go.dev/encoding/json)

## Практика · Потребуй уникальные канонические ключи

Дополни decodeCommand. Каждый ключ верхнего уровня должен встречаться максимум один раз и после декодирования называться ровно type, conversation_id или body. Это одно изменение входного контракта.

1. Проверь ключи объекта до декодирования в sendCommand. Сравнивай декодированные JSON-строки, чтобы type и запись \u0074ype обозначали один ключ. Единственное экранированное написание канонического имени допустимо. Отклоняй варианты регистра Type и CONVERSATION_ID. Повтор недопустим даже при одинаковых значениях.

2. Сохрани приём исходной команды, обработку пробелов, проверки значений, запрет второго значения, нулевой результат при ошибке и обёрнутые причины decoder. Сохрани проверку пропущенных полей и null. Введи различимую ошибку для повторного или неканонического ключа. Заверши проверки до возврата команды для обработки.

3. Добавь тесты повторных type, conversation_id и body с одинаковыми и разными значениями, экранированного повтора, единственного экранированного имени, вариантов регистра и верной команды с другим порядком полей. Проверь некорректный JSON, неизвестные поля, вложенные значения неверного типа, хвост и исходные тесты. Карта, заполненная после декодирования, уже потеряла повторные ключи.

4. Запусти целевые тесты и проверки из корня ниже. Объясни, кто отвечает за лимит байтов, проверку команды, доверенную identity и доступ к беседе. Объясни, зачем успешно разобранной команде нужна авторизация до побочного эффекта.

```sh
gofmt -w lessons/48-session-command/main.go lessons/48-session-command/main_test.go
go test ./...
go test -race ./...
go vet ./...
```

## Типичные ошибки

- Один вызов Decode пропускает второе значение после команды.

- Повторное использование получателя между кадрами сохраняет поля, пропущенные в следующем кадре.

- Частично декодированная команда выглядит пригодной для обработки даже при ошибке.

- Ожидание, что запрет неизвестных полей отклонит повторные ключи, скрывает неоднозначность.

- Поле user_id из кадра смешивает клиентские данные с аутентифицированной identity.

## Критерии завершения

Запусти пример и проследи каждую проверку. Выполни практику уникальных ключей с положительными и отрицательными тестами. Исходные и новые тесты должны проходить, включая детектор гонок. Своими словами объясни границы транспорта, парсера и авторизации.
