# Урок 27: одна транзакция для сообщения и outbox-события

[English version](../27-transactional-outbox.md)

План на 55–80 минут: 10–15 минут чтения, 10–15 минут запуска примера и минимум 35 минут на задание.

## Окно потери события

В уроке 26 мы упаковали бинарник с метаданными сборки. Теперь разберём сбой во время работы: между сохранением сообщения и добавлением события в очередь в памяти есть разрыв. Если процесс остановится между этими действиями, сообщение останется, а событие потеряется. Обратный порядок может объявить сообщение, которое так и не закоммитится.

Пример сохраняет сообщение и намерение доставки в одной транзакции PostgreSQL. Он **не отправляет** уведомления. Отдельный consumer впоследствии читает закоммиченные события; обработка и политика повторов — другие обязанности.

## Запуск с одноразовой БД

Нужны Go, Docker и `openssl`. Из корня репозитория запусти отдельный PostgreSQL со случайным паролем, случайным портом только на loopback и временными данными:

```sh
lesson27_password=$(openssl rand -hex 24)
lesson27_container=$(docker run --rm -d \
  --tmpfs /var/lib/postgresql/data \
  -p 127.0.0.1::5432 \
  -e POSTGRES_USER=course -e POSTGRES_DB=course \
  -e POSTGRES_PASSWORD="$lesson27_password" postgres:17-alpine)
docker exec "$lesson27_container" pg_isready -U course -d course
```

Если последняя команда сообщает, что PostgreSQL ещё не готов, повтори именно проверку готовности перед продолжением. Тег образа предназначен для локальной практики, а не закреплённого production-развёртывания. Не направляй пример и тесты в production или общую БД. Не печатай и не коммить URL подключения: в нём временный пароль.

```sh
lesson27_port=$(docker port "$lesson27_container" 5432/tcp | awk -F: '{print $NF}')
export DATABASE_URL="postgres://course:$lesson27_password@127.0.0.1:$lesson27_port/course?sslmode=disable"
export POSTGRES_TEST_URL="$DATABASE_URL"
go run ./lessons/27-transactional-outbox
go test -count=1 -v ./lessons/27-transactional-outbox
```

Пример вывода; идентификаторы и время будут другими:

```json
{"message":{"id":1,"conversation_id":"lesson-chat","text":"hello atomic outbox","created_at":"2026-10-21T06:30:00Z"},"event_id":1}
```

Каждый запуск создаёт ещё одно сообщение. Этот writer намеренно **не идемпотентен**.

## Проследи транзакцию

Прочитай [main.go](../../lessons/27-transactional-outbox/main.go) и [schema.sql](../../lessons/27-transactional-outbox/schema.sql).

1. Нормализуй draft до обращения к БД. ID беседы содержит 1–80 ASCII-букв, цифр, подчёркиваний или дефисов. После обрезания пробелов текст содержит 1–280 Unicode code points, корректный UTF-8 и не содержит NUL.
2. Начни один `sql.Tx` и отложи rollback через `defer`.
3. Добавь строку в `lesson27_messages` с параметрами; `RETURNING` вернёт сгенерированные БД ID и время.
4. Через **ту же транзакцию** добавь строку в `lesson27_outbox`. Её `message_id` — уникальный внешний ключ. JSON payload содержит только ID сообщения и беседы; тип события — `message.created`.
5. Сделай commit до возврата сообщения и ID события.

При любой ошибке функция возвращает пустой `Created`. В частности, получение сгенерированных ID ещё не означает успех:

```go
if err := tx.Commit(); err != nil {
    return Created{}, fmt.Errorf("commit message and outbox: %w", err)
}
return result, nil
```

После успешного commit отложенный rollback безвреден. Если второй INSERT не удался, сообщение тоже откатывается. Не заменяй транзакционный вызов на `db.ExecContext`: он выполнится вне этой транзакции. После rollback последовательности могут иметь пропуски; не проверяй непрерывность ID и не выводи из них порядок commit.

`applySchema` встраивает SQL и создаёт две учебные таблицы. `CREATE TABLE IF NOT EXISTS` не заменяет миграции для обновления существующей схемы; сравни с версионированными миграциями урока 23. Здесь нет аутентификации, tenant isolation, проверки membership, HTTP endpoint, publisher или подтверждения доставки. Объединение с уроком 21 требует согласованного контракта проверки доступа и записи, а не незащищённого маршрута к этому store.

Read-only референс `tetradka/chat/backend/internal/storage/postgres/repository.go` тоже записывает сообщения и outbox через одну транзакцию, но дополнительно учитывает tenant и состояние чата, получателей, результаты команд и push jobs. Его событие `message.new` — не упрощённый протокол этого урока.

## Что доказывают тесты

Unit-тесты проверяют нормализацию, неверные и слишком длинные тексты и ID, отсутствие конфигурации и заранее отменённый запрос. Текст, похожий на SQL, остаётся данными, а не исполняемой командой.

При заданном `POSTGRES_TEST_URL` интеграционные тесты создают отдельную схему со случайным именем для каждого подтеста и удаляют только её. Проверяются согласованные записи и payload, ошибка ограничения outbox после вставки сообщения, ошибка отложенного внешнего ключа **на commit**, отсутствие записей после отказа валидации/отмены и восемь параллельных независимых записей.

Тест ошибки commit добавляет заведомо невыполнимое отложенное ограничение в собственную тестовую схему. Это не production-переключатель отказа. После такого известного отказа обе таблицы должны быть пустыми.

Без `POSTGRES_TEST_URL` проверки БД пропускаются, а не считаются выполненными. Тесты не моделируют падение БД, потерю сети во время commit или внешнюю доставку. Потерянный ответ на commit может оставить результат неизвестным: нельзя вслепую повторять этот неидемпотентный writer или утверждать, что любая ошибка commit доказывает отсутствие записи.

## Задание: идемпотентный локальный consumer — не реализовано

Создай **один consumer**, превращающий закоммиченные outbox-события в счётчик сообщений по беседам. В этом задании всё остаётся внутри PostgreSQL; не добавляй очередь, сетевую доставку, polling loop или систему горутин.

Метод, который ты добавишь, должен иметь такой контракт:

```go
func (s *outboxStore) Consume(ctx context.Context, eventID int64) (applied bool, err error)
```

1. Отклоняй неположительный ID и отдельно сообщай об отсутствующем событии. Загрузи событие из БД, проверь тип и payload по связанному сообщению; не доверяй ID беседы, переданному вызывающей стороной.
2. Добавь receipt с ключом `(consumer_name, event_id)` для consumer `conversation-count-v1` и отдельную таблицу счётчиков по беседам.
3. Записывай receipt и увеличивай счётчик атомарно. Возвращай `true, nil` только после успешного commit. Повтор уже применённого события возвращает `false, nil` без нового увеличения.
4. Параллельные вызовы для одного события должны давать один receipt и одно увеличение. Два разных события одной беседы должны увеличить счётчик оба, без lost update.
5. Проверь первую обработку, последовательный и параллельный повтор, разные события, отсутствующее/неверное событие, отмену и принудительный отказ записи счётчика. После отказа receipt отсутствует; повтор после удаления тестового ограничения применяет событие один раз.
6. Сохрани все тесты writer. Объясни, почему удаление receipts может снова разрешить дубли и почему локальная транзакция не гарантирует exactly-once доставку email, push или WebSocket.

Схема receipts/счётчиков и реализация consumer не приложены. Критерий завершения: метод и тесты ошибочных сценариев проходят на одноразовом PostgreSQL, а ты можешь объяснить границу транзакции без обещаний внешней доставки.

## Проверки и очистка

Пока временная БД работает:

```sh
gofmt -l lessons/27-transactional-outbox/*.go
go test -p 1 -count=1 ./...
go test -race -p 1 -count=1 ./...
go vet ./...
```

`-p 1` запускает пакеты последовательно, не меняя проверки. Когда закончишь, останови **только ID контейнера, сохранённый выше**. Его временные данные намеренно будут потеряны:

```sh
docker stop "$lesson27_container"
unset DATABASE_URL POSTGRES_TEST_URL lesson27_password lesson27_port lesson27_container
```

## Типичные ошибки и источники

Типичные ошибки: добавлять событие после commit только в память; смешивать вызовы `db` и `tx`; возвращать ID до commit; считать повторный `Create` защитой от дублей; принимать outbox-строку за подтверждение доставки; сохранять receipt до commit его эффекта; проверять SQL только через fake; называть пропущенную интеграцию успешно проверенной.
