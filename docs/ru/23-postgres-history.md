# Урок 23: итоговый проект IV — хранение истории в PostgreSQL

Время на урок: 45–60 минут.

В уроке 22 появились стабильный cursor `(created_at, id)` и проверка membership перед чтением. Теперь переносим тот же контракт страницы в PostgreSQL. Адаптер проверяет active membership и читает страницу в одной read-only транзакции `REPEATABLE READ`; каждый запрос сообщений по-прежнему ограничен указанной беседой.

Пример использует pgx stdlib driver, закреплённый в репозитории, через `database/sql`. Транзакция даёт проверке membership и запросу страницы один снимок внутри текущего запроса; она не фиксирует историю между отдельными запросами страниц. См. [`database/sql` transaction options](https://pkg.go.dev/database/sql#TxOptions), документацию PostgreSQL по [изоляции транзакций](https://www.postgresql.org/docs/current/transaction-iso.html) и [pgx stdlib guide](https://github.com/jackc/pgx/wiki/Getting-started-with-pgx-through-database-sql).

## Запустите временную локальную базу

```sh
docker run --rm --name go-course-history -e POSTGRES_USER=go -e POSTGRES_PASSWORD=go -e POSTGRES_DB=go_course -p 127.0.0.1:5434:5432 postgres:16
```

Во втором терминале запустите пример. Он применит версионированные миграции урока и попробует прочитать demo-беседу. В новой базе membership ещё нет:

```sh

```


Для другой локальной базы задайте `DEMO_USER_ID` и `DEMO_CONVERSATION_ID` с ID пользователя и беседы. Пример только читает данные: он не создаёт и не удаляет данные бесед.

## Как работает адаптер

Миграции создают небольшую таблицу membership, таблицу сообщений и индекс `(conversation_id, created_at DESC, id DESC)`. Версии миграций записываются транзакционно под advisory lock. Файлы уже применённых миграций считаются неизменяемыми.

`ListPage` проверяет ID и размер страницы, начинает read-only транзакцию `REPEATABLE READ`, проверяет active membership и только после этого читает сообщения. Запрос страницы всегда передаёт `conversation_id` как `$1`; при наличии cursor PostgreSQL применяет исключительное сравнение кортежей `(created_at, id) < ($2, $3)`. Пользовательские значения передаются как SQL-аргументы, а не форматируются в запрос. PostgreSQL сравнивает поля row constructor слева направо; см. [правила сравнения строк](https://www.postgresql.org/docs/current/functions-comparisons.html#ROW-WISE-COMPARISON).

Запрос выбирает не более `limit + 1` строк. Дополнительная строка определяет `has_more`, но клиенту не возвращается. Следующий cursor соответствует последней возвращённой строке, поэтому следующая страница начинается строго перед этим кортежем. Строки закрываются и проверяются до commit read-транзакции. Ошибки БД оборачиваются для логов и вызывающего кода; HTTP-обработчик должен преобразовать `ErrNotMember` в `403` и не раскрывать клиенту детали неожиданной ошибки БД.

Транзакция обеспечивает один снимок membership и данных страницы внутри одного запроса. Она не объединяет страницу 1 и страницу 2 в общий снимок и не заменяет durable history revision. Контракт `messages.load` целевого chat-backend содержит дополнительные правила, которых нет в этом учебном REST/store-примере.

## Тесты

Unit-тесты проверяют границы размера страницы, SQL-аргументы (включая вредоносный ID беседы), запрос с tuple-cursor и порядок встроенных миграций. PostgreSQL integration test создаёт уникальные тестовые строки, проверяет две страницы с совпадающими timestamp, отказ пользователю без membership и удаляет только собственные строки. Если `POSTGRES_TEST_URL` не задан, тест пропускается.

Используйте отдельную временную test-базу, не базу с важными данными. Тест применяет туда миграции урока; очистка удаляет только тестовые строки и намеренно оставляет схему миграций.

```sh
go test ./lessons/23-postgres-history
```

```sh
POSTGRES_TEST_URL='postgres://go:go@localhost:5434/go_course_test?sslmode=disable' go test ./lessons/23-postgres-history -run TestPostgresHistoryIntegration -count=1
```

Проверьте весь репозиторий:

```sh
gofmt -w ./lessons/23-postgres-history
go test ./...
go test -race ./...
go vet ./...
```

## Задание — добавить фильтры времени создания в PostgreSQL-запрос

Расширьте `ListPage` необязательными границами `created_from` включительно и `created_to` исключительно:

1. Проверяйте диапазон до начала транзакции; отклоняйте неправильный формат или не возрастающие границы стабильной ошибкой.
2. Передавайте timestamp как SQL-аргументы. Сохраните условие беседы, membership-проверку, tuple-cursor и стабильный порядок.
3. Применяйте те же границы к каждой cursor-странице. При переходе по `Next` вызывающая сторона должна передавать прежние значения фильтров.
4. Добавьте unit-тесты построения запроса и неверных границ, а также opt-in integration-тест границ и двухстраничного прохода. Используйте уникальную область тестовых данных и удаляйте только свои строки.

Запланируйте минимум 40 минут. Задание завершено, когда проходят существующие тесты страниц, отфильтрованные страницы не выходят за область беседы, а при отсутствии test-базы integration test явно отмечен как пропущенный.

## Типичные ошибки

- вставка ID беседы или cursor в SQL через форматирование строки;
- проверка membership на одном соединении и чтение сообщений вне транзакции;
- забытая особенность: `database/sql` закрепляет операции транзакции за одним соединением;
- использование одного timestamp как cursor при совпадающем времени;
- потеря условия по беседе в запросе следующей страницы;
- возврат клиенту дополнительной строки `limit + 1`;
- commit при открытых result rows или отсутствие проверки `rows.Err()`;
- запуск opt-in тестов против production или ценных локальных данных;
- утверждение, что одна транзакция создаёт общий снимок для нескольких HTTP-запросов.

## Критерии завершения

Вы можете пройти проверку membership и чтение страницы через одну context-aware транзакцию, объяснить составной индекс и исключительный cursor predicate, а также отличить снимок одного запроса от history revision между страницами.
