# Урок 14: аутентификация, авторизация и безопасность веб-приложения

## Цель

Разделять аутентификацию (кто отправил запрос?) и авторизацию (может ли эта личность выполнить действие?). Добавить HTTP middleware для аутентификации, проверку tenant и роли, а также потокобезопасный ограничитель запросов.

В примере используются `net/http` и `httptest`. Таблица фиксированных токенов — только учебная заглушка: она не реализует JWT, не выдает учётные данные и не хранит реальных пользователей. Роль получается отдельным шагом, а не из поиска токена. Не копируй заглушку в развернутый сервис. Целевой chat backend проверяет JWT поддерживаемой библиотекой, разрешает только заданный алгоритм, требует срок действия и subject, а получение роли отделено от разбора токена в `internal/auth/jwt.go`. Запросы к базе также ограничивают данные по tenant ID.

Bearer-токены — учётные данные: передавай их в заголовке `Authorization` поверх TLS, никогда не помещай в URL и не записывай в логи. RFC 6750 различает неверный токен (обычно 401) и действительный токен без нужных полномочий (403). Principal относится к конкретному запросу, поэтому хранить его в `context` уместно.

Ссылки: [RFC 6750, разделы 2 и 3.1](https://www.rfc-editor.org/rfc/rfc6750.html#section-3.1), [пакет Go `context`](https://pkg.go.dev/context#WithValue) и read-only пример целевого backend `internal/auth/jwt.go`.

## Запуск примера

Запусти локальный сервер:

```sh
go run ./lessons/14-auth-security
```

В другом терминале запроси отчеты tenant `acme` с учебным токеном viewer:

```sh
curl -i -H 'Authorization: Bearer viewer-demo-token' http://localhost:8080/tenants/acme/reports
```

Ответ будет JSON со статусом 200. Внутрипроцессный ограничитель пропускает два запроса этого principal за минуту; следующий запрос получает 429 и заголовок `Retry-After`. Перезапуск процесса очищает учебные токены и состояние ограничителя.

Пример тела ответа:

```text
{"tenant_id":"acme","message":"reports are available"}
```

## Middleware аутентификации

Аутентификация проверяет один credential и формирует доверенную identity с ID пользователя и tenant ID. Авторизация отдельно получает текущую роль и объединяет её с identity в principal для обработчика. Пример отвечает 401 с заголовком `WWW-Authenticate`, если credential отсутствует или используется неподдерживаемая схема; 400 — если Bearer-заголовок некорректный или дублированный; 401 — если токен неизвестен. Текст ошибок не содержит credential.

Middleware аутентификации сохраняет проверенную identity в context запроса; middleware авторизации добавляет principal после получения роли. Следующие обработчики читают эти значения из context, а не из query-параметров, тела запроса или присланных клиентом заголовков с идентичностью. Собственные неэкспортируемые типы ключей context не позволяют случайно пересечься с ключами других пакетов.

В реальном сервисе используй настроенный и поддерживаемый verifier токенов. Проверяй разрешенный алгоритм подписи, подпись, срок действия, а также обязательные issuer/audience согласно контракту сервиса. Не пиши свой парсер JWT или алгоритм подписи. Claims tenant и роли из токена не заменяют проверку актуального членства и прав, если приложению нужны отзыв токенов или немедленное применение смены роли.

## Авторизация и границы tenant

После аутентификации endpoint сравнивает path-параметр `tenantID` с tenant доверенного principal и проверяет допустимую роль. Несовпадение tenant и запрещенная роль возвращают одинаковый 403, не раскрывая, какая именно проверка не прошла.

Повторяй проверку tenant и на границе данных: SQL-запросы к принадлежащим tenant строкам должны принимать аутентифицированный tenant ID параметром и включать его в условия. Одна проверка в HTTP-обработчике не делает неограниченный запрос к базе безопасным.

## Ограничение частоты запросов

Ограничитель с фиксированным окном считает запросы отдельно для пары tenant/user. Mutex защищает map и счетчик; тест проверяет конкурентные вызовы. После превышения лимита сервер отвечает 429 и задает `Retry-After` в секундах.

Этот небольшой ограничитель намеренно работает только в одном процессе и хранит ключи без очистки. В таком виде он не подходит публичному сервису: нескольким экземплярам нужна общая политика или gateway, сохраненным ключам нужна ограниченная очистка, а публичным неаутентифицированным endpoint нужны отдельные меры от злоупотребления. Не доверяй `X-Forwarded-For`, если доверенный proxy не удаляет значения клиента и не задаёт канонический адрес.

## Тесты

Целевые тесты проверяют успешный доступ, отсутствие/неверность/ошибочный формат credentials, дублированный заголовок, запрет другого tenant и роли, ответы при превышении лимита, сброс окна, неверную конфигурацию ограничителя и конкурентный доступ.

```sh
go test ./lessons/14-auth-security
go test -race ./lessons/14-auth-security
```

Также выполни проверки репозитория:

```sh
gofmt -w ./lessons/14-auth-security
go test ./...
go test -race ./...
go vet ./...
```

## Типичные ошибки

- считать, что аутентификация автоматически разрешает любое действие;
- доверять tenant ID, user ID или роли из тела запроса или заголовка клиента;
- проверить tenant только в обработчике и забыть его в SQL-запросе;
- отвечать 401 аутентифицированному пользователю без прав вместо 403;
- логировать или раскрывать bearer-токен либо помещать его в URL;
- принимать алгоритм токена без allow-list или самостоятельно писать криптографию JWT;
- считать неограниченный внутрипроцессный limiter защитой многосерверного приложения;
- изменять общее состояние ограничителя без синхронизации;
- доверять forwarded-заголовкам с IP от неизвестного клиента.

## Практика: создать сообщение внутри tenant

Добавь в сервер урока `POST /tenants/{tenantID}/messages`.

Требования:

1. Требуй аутентификацию; для маршрута разреши только роли `writer` и `admin`.
2. Требуй совпадение tenant в пути с tenant principal. Возвращай 401 при отсутствующей/неверной аутентификации, 403 для аутентифицированного, но неавторизованного запроса, 400 при неверном вводе и 429 с `Retry-After`, когда principal превышает существующий лимит.
3. Принимай ровно один JSON-объект с полем `text`. Обрезай пробелы; отклоняй пустой текст, неизвестные поля, некорректный или дополнительный JSON, тело больше 1 MiB и текст длиннее 280 Unicode code points.
4. Сохраняй сообщения в защищенном mutex внутрипроцессном хранилище с возрастающими ID. Каждая запись должна включать tenant ID и ID создавшего пользователя. Возвращай JSON созданной записи со статусом 201; никогда не включай bearer-токен в ответ.
5. Добавь целевые тесты создания, запрета viewer, доступа к чужому tenant, неверных и некорректных тел, неизвестных полей, лишнего JSON, слишком большого тела, Unicode-границы длины и ограничения запросов. Проверь безопасность хранилища и limiter при `go test -race`.

Не добавляй выдачу токенов и собственную JWT-криптографию. Практика учит применять уже проверенный principal и на HTTP-, и на data-границе.

## Критерии завершения

Ты можешь объяснить разницу аутентификации и авторизации, почему principal берётся из проверенной сервером аутентификации, почему tenant должен учитываться в запросах к БД и чем различаются 401, 403 и 429. Тесты примера проходят, а у нового маршрута есть позитивные и негативные тесты, проходящие с race detector.
