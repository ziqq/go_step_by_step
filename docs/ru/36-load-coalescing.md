# Урок 36: объединять загрузки, сохраняя владельца их времени жизни

[English version](../36-load-coalescing.md)

После истечения TTL много запросов могут одновременно получить промах. Проследи одного leader и двух follower, сравни отмену ожидания с отменой leader, запусти тесты с каналами-барьерами и выполни задание на закрытие приёма. Инвалидация беседы из урока 35 остаётся отдельным нерешённым заданием.

## Разделять загрузку, пока она выполняется

Открой [main.go](../../lessons/36-load-coalescing/main.go) и [тесты](../../lessons/36-load-coalescing/main_test.go). `loadGroup` хранит один активный вызов на `loadKey`. Первый принятый caller становится leader и синхронно выполняет загрузчик в собственной горутине. Дубликаты ждут результат этого вызова. Группа не создаёт горутины и не кеширует завершённые результаты.

Ключ включает точные непустые tenant, viewer и conversation ID для одного фиксированного представления. Все вызовы одного ключа должны означать одно чтение; загрузчик follower не вызывается. В реальном ключе учитывай и остальные входы, меняющие представление. Каждый caller всё равно должен пройти текущую авторизацию перед использованием приватного результата. Не применяй этот пример к mutation или durable-доставке.

В целевом chat backend `internal/storage/postgres/command_result.go` сериализует durable-квитанции mutation в PostgreSQL. Урок не заменяет этот протокол и не утверждает, что backend использует такую группу в памяти. Референс остаётся read-only.

## Контракт приёма и завершения

`newLoadGroup(capacity)` требует положительную ёмкость активных ключей; иначе возвращает nil и `ErrInvalidGroup`. Создавай группу через конструктор и не копируй её.

| Ситуация в `Do(ctx, key, load)` | Результат |
|---|---|
| Nil context/loader или пустое поле ключа | Пустая строка и `ErrInvalidLoad` до проверки context/приёма |
| Верный вызов с уже отменённым context | Пустая строка и `ctx.Err()`, без новой загрузки |
| Тот же ключ активен | Присоединиться, даже при полной ёмкости; игнорировать загрузчик этого caller |
| Новый ключ при заполненной ёмкости | Пустая строка и `ErrBusy`, без запуска загрузчика |
| Новый ключ при наличии места | Выполнить загрузчик вне mutex; выдать его строку и ошибку без изменений |
| Вызов завершён | Удалить ключ; следующий вызов начинает новую загрузку после успеха или ошибки |

Один mutex сериализует поиск и приём активных ключей. Перед загрузкой и ожиданием он освобождается, поэтому разные ключи могут продвигаться независимо. Ёмкость считает разные активные загрузчики, а не ожидающих caller, байты, HTTP-запросы или подключения к базе. При адаптации сервиса сочетай её с приёмом запросов и бюджетами зависимостей из уроков 30–32; лимит ожидающих здесь не добавляется.

## Выбрать владельца отмены

Leader передаёт загрузчику собственный context. Отмена кооперативная: операция базы/HTTP должна учитывать context и вернуться. Follower может независимо прекратить ожидание. Его отмена не отменяет leader и не освобождает активный слот. Даже если все follower ушли, leader владеет загрузкой до её возврата.

Фрагмент ветки follower после освобождения mutex группы:

```go
select {
case <-ctx.Done():
    return "", ctx.Err()
case <-call.done:
    if err := ctx.Err(); err != nil {
        return "", err
    }
    return call.value, call.err
}
```

В запускаемом файле выше есть валидация, регистрация и завершение. Follower повторно проверяет отмену после сигнала завершения: уже видимая при этой проверке ошибка побеждает. Отмена всё ещё может произойти позже. Leader публикует ровно результат загрузчика; группа не заменяет его более поздней ошибкой context. Если загрузчик игнорирует отмену и возвращает успех, follower могут получить успех. Это явная политика, а не гарантия независимого времени жизни backend-операции. Отвязать общую загрузку можно только с отдельными владельцем, бюджетом и shutdown-протоколом.

Поля результата записываются до закрытия канала завершения. Follower читают их после получения сигнала, который публикует эти записи. Пример разделяет строки и ошибку, значение которой нельзя конкурентно менять. Для изменяемых slice или map нужны правила владения/копирования, как в уроке 35.

## Освобождать при аварийном выходе, сохраняя его смысл

Отложенное завершение удаляет ключ и будит follower даже при panic загрузчика. Вызов начинается с `ErrLoadAborted`; нормальный возврат заменяет её результатом загрузчика. При аварийном выходе follower получают пустые данные и `ErrLoadAborted`. Исходный panic распространяется в горутине leader; группа не перехватывает его и не превращает в успешный возврат. Неперехваченный panic по-прежнему завершает процесс. Заблокированный загрузчик не выполнит отложенное завершение до выхода.

Загрузчик не должен синхронно повторно входить в эту группу с тем же ключом: он будет ждать самого себя. Другой ключ разрешён, если есть ёмкость. Тесты удерживают callback каналами, наблюдают вычисление `Done` follower после присоединения, затем отпускают/отменяют в известном порядке. Таймаут тестов только защищает от deadlock; sleep не доказывает порядок выполнения.

## Практика: закрыть приём и дождаться активных загрузчиков

Добавь `Close() <-chan struct{}` и `ErrClosed`, сохранив поведение открытой группы и существующие тесты:

1. Первый close атомарно останавливает приём. Повторные/конкурентные вызовы возвращают тот же сигнал без ожидания внутри метода и без вспомогательной горутины. Пустая группа завершается немедленно.
2. `Do` сначала проверяет валидацию, затем context, затем закрытое состояние до присоединения или запуска. Корректный вызов с живым context после закрытия возвращает пустые данные и `ErrClosed`, даже для существующего ключа. Уже принятые follower могут получить результат или отменить ожидание обычным способом.
3. Не отменяй принятые загрузчики. Общий сигнал close публикуется только после выхода всех принятых загрузчиков, включая отложенную очистку, учёт аварийного выхода и публикацию результата их вызова. Ждать возврата каждого follower из `Do` не требуется. Никогда не освобождай активный слот только из-за ухода follower.
4. Загрузчик может вызвать `Close`, но не должен ждать завершения собственной группы. Проверь пустой/повторный close, удерживаемый leader с присоединённым follower, отказ новых ключей и дубликатов, приоритет валидации/отмены, очистку загрузчика до завершения, гонку приёма с close. Включи panic загрузчика, перехваченный его caller, во время закрытия. Используй каналы и дожидайся тестовых горутин при cleanup.
5. Объясни, почему возврат из `Close` не доказывает завершение и почему такой обработке остатка нужен отдельный бюджет ожидания shutdown. Не реализуй таймаут, принудительное завершение, адаптер кеша или инвалидацию урока 35 здесь.

Критерий: после закрытия не принимаются ни новые загрузки, ни присоединения; каждый принятый до закрытия leader учтён, все caller close наблюдают один сигнал завершения. Объясни, что доставка follower и завершение загрузчика — разные события. Метод и его тесты остаются за тобой.

## Проверки и типичные ошибки

```sh
gofmt -l lessons/36-load-coalescing/*.go
go test -p 1 -count=1 ./...
go test -race -p 1 -count=1 ./...
go vet ./...
```

Для прежних SQL-интеграций нужны одноразовый PostgreSQL и `POSTGRES_TEST_URL`; без него они пропускаются. Типичные ошибки: считать объединение TTL-кешем; терять область авторизации; давать одному ключу разные загрузки; держать mutex во время I/O; отменять leader из-за ухода follower; обещать лимит ожидающих; читать результат до завершения; перехватывать panic без освобождения ключа.

Источники: [объединение дубликатов в Go singleflight](https://pkg.go.dev/golang.org/x/sync/singleflight), [контракт отмены context](https://pkg.go.dev/context#Context), [публикация через канал](https://go.dev/ref/mem#Channel_communication). У учебной реализации своя политика приёма и времени жизни; она не является API-совместимой заменой singleflight.
