# 45. Одна горутина и отдельный дедлайн на каждую запись в сессии чата

[English version](../45-session-writer.md) · [Запускаемый пример](../../lessons/45-session-writer/main.go)

У сессии может быть несколько источников событий. Урок 44 читает сохранённые события, а тикер подсказывает, когда отправить ping. Выдели одну горутину для записи в соединение. Остальные горутины передают ей данные через каналы. В эталонном бэкенде чата цикл записи выбирает между исходящими кадрами и тикером и задаёт дедлайн каждой записи.

## Запусти пример

```sh
go run ./lessons/45-session-writer
go test -count=1 -v ./lessons/45-session-writer
go test -race ./lessons/45-session-writer
go vet ./lessons/45-session-writer
```

```text
sent event: message 42
sent ping
```

Пример сам отправляет тик и использует тестовую функцию записи. Он показывает порядок исходящих кадров. В WebSocket-сессии задай дедлайн на соединении или используй операцию записи, которая учитывает отмену. Читающая горутина принимает pong и может отменить общую сессию, если клиент перестал отвечать.

## Проследи за циклом записи

1. Цикл берёт по одному кадру. События из одного канала сохраняют порядок получения, а ping записывается отдельным вызовом. Следующая запись начинается после возврата из предыдущей.
2. Перед каждой записью создай новый контекст от контекста сессии. Вызови его функцию отмены сразу после возврата из записи. Родительский дедлайн ограничивает дочерний, а отмена останавливает ожидание кадра и передаётся операции записи.
3. Ошибка записи завершает сессию. Сохрани причину через %w. При ошибке часть кадра уже могла быть отправлена. Для сохранённых событий клиент может переподключиться и продолжить чтение с последнего принятого курсора.
4. Отправитель закрывает канал событий после последнего события. Содержимое буфера остаётся доступным для чтения. Когда закрытый канал опустеет, цикл завершится. Закрытие канала тиков отключает ping и оставляет запись событий активной. При отмене сессии в очереди могут остаться события.

## Практика · Разреши ожидающему ping пройти первым

Измени цикл так, чтобы тик, который уже ждёт к моменту выбора следующего кадра, обрабатывался раньше следующего события. Сохрани одну горутину записи и отдельный дедлайн на каждый кадр.

1. Если тик пришёл во время записи события, дождись её завершения. Если тик ещё ждёт, отправь ping раньше следующего события. Сохрани порядок событий, обработку закрытого канала тиков и проверку отмены перед очередной записью.
2. В тесте задержи первую запись события каналом, поставь в очередь тик и второе событие, затем отпусти первую запись. Используй общий таймаут и дождись завершения горутины. Проверь порядок «событие, ping, событие». Добавь случай, в котором отмена сессии во время первой записи предотвращает последующие записи.
3. Объясни, как тикер задаёт частоту ping в реальной сессии. Сохрани запускаемый пример с управляемым тиком.

## Типичные ошибки

- Отдельная горутина на каждую запись усложняет порядок и позволяет медленным записям накапливаться.
- Один таймаут записи на всю сессию передаёт поздним записям уже истёкший дедлайн.
- Вызов cancel через defer внутри цикла оставляет таймеры завершённых записей до выхода из цикла.
- Дополнительная ветка select сама по себе не даёт готовому ping приоритета перед готовым событием.

## Критерии завершения

Пример отправляет событие и ping. Исходные и новые тесты проходят с детектором гонок. Ожидающий ping отправляется перед вторым событием, первая запись завершается своим ходом, а отмена сессии предотвращает дальнейшие записи.
