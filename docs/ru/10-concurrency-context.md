# Урок 10: Конкурентность и context

## Цель

Научиться запускать независимую работу в goroutine, передавать значения через каналы, ждать завершения через `sync.WaitGroup` и останавливать работу с помощью `context.Context`. В примере используется небольшой worker pool, который разбирает записи в формате логов.

Такие границы встречаются в backend: HTTP-запрос создает context, сервис запускает ограниченную параллельную работу, а отмена не дает worker-ам продолжать после ухода клиента или завершения родительской операции.

## Запускаемый пример

Полный пример находится в `lessons/10-concurrency-context/main.go`.

```sh
go run ./lessons/10-concurrency-context
```

```text
0 info connected
1 warn slow request
2 error database unavailable
```

`analyze` принимает context, список заданий и число worker-ов. Worker-ы получают индексированные задания из `jobs`, разбирают их и отправляют результаты через `results`. Результаты могут прийти в любом порядке, поэтому индекс сохраняется, а итоговый срез сортируется.

## Context — это контракт отмены

Передавай context первым аргументом. Не храни его в структуре и не используй `context.Background()` внутри функции, которая уже получила context.

```go
func Handle(ctx context.Context, request Request) error {
	return service.Process(ctx, request)
}
```

`ctx.Done()` — канал, который становится доступным при отмене context или истечении его deadline. `select` позволяет выбрать между полезной работой и отменой:

```go
select {
case job := <-jobs:
	return process(job)
case <-ctx.Done():
	return ctx.Err()
}
```

Отмена не завершает goroutine принудительно. Каждая goroutine должна сама увидеть сигнал и выйти. Поэтому в примере у каждой потенциально блокирующей отправки и операции чтения есть ветка отмены.

## Goroutine и каналы

Goroutine — легкая параллельная функция. Канал передает владение значением между goroutine. Заранее определи, кто закрывает каждый канал:

- канал закрывает отправитель, который владеет им, после отправки всех значений;
- получатель не закрывает канал, который не создавал;
- `WaitGroup` ждет worker-ов, но не отменяет их;
- `results` закрывается только после завершения всех worker-ов.

В примере есть один producer, несколько worker-ов и один closer для канала результатов. Такая схема не позволяет отправлять в уже закрытый канал и дает главной goroutine понятный сигнал завершения.

## Зачем нужен worker pool

Запускать отдельную goroutine для каждого входного элемента подходит не всегда. Worker pool ограничивает конкурентность фиксированным числом worker-ов. В настоящем backend это помогает не создавать неконтролируемое количество запросов к базе или внешним сервисам.

Количество worker-ов нужно проверить до запуска goroutine. Для общего изменяемого состояния тоже нужно правило владения: используй mutex или передавай обновления по каналу одной goroutine, которая владеет map. В задании ниже нужно выбрать и объяснить один из вариантов.

## Типичные ошибки

- игнорировать `ctx.Done()` в цикле и оставлять goroutine после отмены;
- закрывать канал со стороны получателя;
- вызвать `WaitGroup.Add` после того, как worker уже может вызвать `Done`;
- забыть `Done` на одном из путей выхода;
- использовать общую map из нескольких worker-ов без синхронизации;
- полагаться на порядок завершения вместо сохранения явного индекса;
- неправильно захватить переменную цикла при запуске goroutine;
- считать, что race detector доказывает все логические свойства программы.

Race detector находит много несинхронизированных обращений к памяти, но не доказывает правильность отмены, порядка результатов и обработки ошибок.

## Практика: параллельный подсчет уровней

Реализуй `CountLevels` в `lessons/10-concurrency-context/main.go`:

```go
func CountLevels(ctx context.Context, lines []string, workers int) (map[string]int, error)
```

Требования:

1. Переиспользуй `parseLine` и те же ограничения worker pool, что и в `analyze`.
2. Считай нормализованные уровни: `info`, `warn`, `error`.
3. Возвращай ошибку для неверного числа worker-ов, неверной строки или отмененного context.
4. Не допускай data race. Можно использовать mutex вокруг map или одну collector goroutine, которая владеет map; решение о владении запиши коротким комментарием.
5. Для пустого входа возвращай пустую ненулевую map.
6. Добавь тесты для обычного подсчета, пустого входа, неверных данных, неверного числа worker-ов и отмены.

Не меняй поведение `analyze`. Доказательство завершения задания:

```sh
go test ./lessons/10-concurrency-context
go test -race ./lessons/10-concurrency-context
```
