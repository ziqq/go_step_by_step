# Урок 35: ограничить TTL-кеш и владеть его снимками

[English version](../35-ttl-cache.md)

Продолжим раздел проектирования систем: зададим кешу явные область ключа, срок жизни, ёмкость и владение данными. Проследи подставные часы, нарисуй время жизни записи, запусти граничные тесты, затем выполни задание на инвалидацию. Приём пачки из урока 34 остаётся отдельным нерешённым заданием.

## Одноразовое превью, а источник истины — база

Открой [main.go](../../lessons/35-ttl-cache/main.go) и [тесты](../../lessons/35-ttl-cache/main_test.go). Этот самостоятельный пример кеширует байты одного фиксированного представления превью беседы. Здесь нет HTTP-адаптера, загрузчика из базы, фоновой очистки или общего сервиса кеширования. Пример работает локально с подставными часами и без sleep.

Ключ — структура с `TenantID`, `ViewerID` и `ConversationID`. Все три поля должны быть непустыми и не состоять только из пробелов; остальные строки сохраняются точно, включая пробелы по краям. Структура исключает неоднозначное склеивание через разделитель. Каждое поле независимо меняет идентичность. Если позже кешировать страницы или другое представление, фильтрам, cursor, limit и версии представления тоже нужны явные поля ключа либо отдельный кеш.

Попадание в кеш не авторизует пользователя. На каждом запросе проверяй identity и текущий доступ к беседе до использования приватного превью; задай политику отзыва доступа. Эти поля предотвращают случайные коллизии в примере, но не реализуют авторизацию. Не помещай в пример секреты или реальные приватные сообщения.

В read-only референсе `docs/DATA_MODEL.md` PostgreSQL указан источником истины. Durable-протокол `command_results` в `internal/storage/postgres/command_result.go` отвечает за идемпотентность; этот кеш его не заменяет. Файлы целевого backend не меняются.

## Контракт небольшого API

Создавай `previewCache` через `newPreviewCache(capacity, ttl, now)`. Ёмкость и TTL должны быть положительными, часы — ненулевыми; иначе возвращаются nil и `ErrInvalidCache`. Кеш требует конструктора и не допускает копирования.

| Операция | Результат |
|---|---|
| `Put` с пустым полем ключа | `ErrInvalidKey`, без изменений |
| `Put` нового ключа при заполнении живыми записями | `ErrCacheFull`, без вытеснения или продления живых записей |
| `Put` существующего живого ключа | Заменить байты и перезапустить только его TTL, даже при полном кеше |
| `Get` неверного, отсутствующего или просроченного ключа | `(nil, false)` |
| `Get` живого ключа | Отдельный снимок байтов и `true`; TTL не меняется |

Nil и пустой payload — допустимые значения кеша. Проверяй флаг попадания, а не считай пустые данные промахом. Здесь нет LRU-вытеснения, кеширования ошибок загрузчика или объединения конкурентных промахов.

## Одна граница истечения, одно чтение часов

`Put` читает часы под mutex, удаляет все просроченные записи, проверяет предел числа записей и сохраняет срок как прочитанное время плюс TTL. `Get` проверяет нужную запись под тем же mutex и удаляет её при истечении. Запись жива только строго до срока:

```go
if !c.now().Before(entry.expiresAt) {
    delete(c.entries, key)
    return nil, false
}
```

Это фрагмент `Get`; ссылка на полный запускаемый пример есть выше. Равенство означает истечение. Чтение никогда не продлевает TTL. Тесты с подставными часами проверяют наносекунду до срока, точное равенство и момент после него без ожидания реальных таймеров. Операция наблюдает время при чтении под блокировкой; возвращённый снимок естественно может устареть после возврата.

В приложении передавай `time.Now`: Go может сохранять монотонную составляющую для сравнения интервалов внутри процесса. Не сериализуй такие deadlines и не сравнивай их со сроками из базы. Подставные часы должны быть быстрыми, неубывающими и не вызывать кеш: callback работает под mutex. Захваченное время примера меняется только последовательно; конкурентные тесты используют синхронизированные подставные часы.

## Копирование — часть владения

`Put` сохраняет `slices.Clone(data)`, а `Get` возвращает ещё одну копию. Передача одного заголовка slice оставляет общий backing array. Без копирования вызывающий код мог бы изменить кеш после `Put` или результат другого читателя после `Get`, даже если каждый доступ к map защищён mutex. При этом вызывающий код всё равно не должен менять входные байты конкурентно с `Put`: кеш не может синхронизировать нарушения внешнего владения.

Mutex защищает поиск, истечение, ёмкость и замену совместно. Копирование выдаваемых байтов разрешает читателям менять собственные снимки после `Get`. Для этих отдельных снимков внешние блокировки не нужны. Тесты подтверждают поведение примера, а не production throughput.

Ёмкость ограничивает число хранимых записей, а не байты, всю память процесса или число запросов. `Put` просматривает до capacity записей и копирует вход под mutex; `Get` копирует выход. Бездействующий кеш может удерживать просроченные байты до обращения, но не превышает предел числа записей. Перед адаптацией под трафик выбирай лимиты payload и вытеснение по измеренным требованиям; бюджет байтов здесь не реализуется.

## Практика: инвалидировать беседу для всех читателей

Добавь `InvalidateConversation(tenantID, conversationID string) (int, error)`, сохранив опубликованные методы и тесты:

1. Пустой/пробельный аргумент возвращает ноль и `ErrInvalidKey` без изменений. Сохраняй точные непустые идентификаторы.
2. Удали все хранимые записи с совпадающими tenant и conversation для всех viewer. Верни число физически удалённых записей, включая ещё хранящиеся просроченные совпадения. Нет совпадений — ноль и nil. Не продлевай, не очищай и не удаляй посторонние записи.
3. Сериализуй операцию с `Put` и `Get`. Запись, упорядоченная до инвалидации, удаляется; `Put`, упорядоченный после неё, может сохранить новое значение. Это не вечный запрет записи и не гарантия распределённой согласованности.
4. Добавь детерминированные тесты нескольких viewer, другого tenant с тем же conversation ID, другой беседы, повторной инвалидации, пустых аргументов без изменений, просроченных совпадений, повторного использования ёмкости, а также заданного каналами порядка и конкурентной инвалидации с `Put`/`Get`. Синхронизируй подставные часы и не используй sleep как доказательство порядка.
5. В объяснении расположи инвалидацию после успешного commit базы и разбери `загрузка старых данных → commit/инвалидация → устаревший Put`. Объясни, почему одного метода недостаточно против позднего заполнения старыми данными и для отзыва уже выданных снимков. Назови возможную проверку версии; не реализуй загрузчик, распределённый кеш или протокол версий в этом задании.

Критерий завершения: тесты доказывают точное число удалений, изоляцию, повторное использование ёмкости и оба допустимых порядка операций. Объясни границу позднего заполнения без заявлений о строгой согласованности. Новый метод и его тесты остаются за тобой.

## Проверки и типичные ошибки

```sh
gofmt -l lessons/35-ttl-cache/*.go
go test -p 1 -count=1 ./...
go test -race -p 1 -count=1 ./...
go vet ./...
```

Для прежних SQL-интеграций нужны одноразовый PostgreSQL и `POSTGRES_TEST_URL`; без него они пропускаются. Типичные ошибки: случайно продлевать TTL чтением; считать равенство живой записью; выдавать общий backing array; считать ключ авторизацией; принимать TTL за немедленное освобождение памяти; незаметно вытеснять живые записи; путать TTL с durable-идемпотентностью или инвалидацией после записи.
