# 52. Повтор отправки с сохранённым ключом команды

[English version](../52-command-idempotency.md) · [Запускаемый пример](../../lessons/52-command-idempotency/main.go) · [Схема](../../lessons/52-command-idempotency/schema.sql)

Урок 51 разделил результат операции и доставку ответа. Соединение может исчезнуть после commit записи. Повтор отправки с новым ключом создаст ещё одно сообщение. Здесь неизменяемая строка отправки одновременно служит квитанцией: те же tenant, actor, key, conversation и body возвращают сохранённый ID. Повтор ключа с другими данными приводит к конфликту.

Референсный dispatcher собирает CommandMeta из доверенной identity tenant/user, ID команды, метода и хеша запроса. Пример изучает одну операцию с небольшими числовыми ID и точным сохранённым вводом. Он не воспроизводит весь протокол backend. Аутентификация и текущая проверка доступа к беседе выполняются перед каждым Send, включая повторы; tenant/actor поступают из доверенного вызывающего кода.

## Запустите одноразовый PostgreSQL

Пароль ниже — публичное значение для локального примера. Используйте только одноразовую базу. Контейнер хранит данные в памяти и открывает PostgreSQL на loopback. Запустите его в одном терминале и дождитесь сообщения о готовности. После проверок остановите через Ctrl-C.

```sh
docker run --rm --name go-lesson52 \
  --tmpfs /var/lib/postgresql/data:rw,size=512m \
  -e POSTGRES_PASSWORD=lesson52_local \
  -p 127.0.0.1:55452:5432 postgres:17-alpine
```

В другом терминале, из корня репозитория:

```sh
export DATABASE_URL='postgres://postgres:lesson52_local@127.0.0.1:55452/postgres?sslmode=disable'
export POSTGRES_TEST_URL="$DATABASE_URL"
go run ./lessons/52-command-idempotency
go run ./lessons/52-command-idempotency
go test -count=1 -v ./lessons/52-command-idempotency
go test -race ./lessons/52-command-idempotency
go vet ./lessons/52-command-idempotency
```

Оба запуска примера выводят:

```text
same message: true
changed input rejected: true
```

Первый запуск сохраняет фиксированную команду примера. Последующие используют её квитанцию. Пример подготавливает только lesson52_sends; это не runner миграций. Интеграционные тесты создают и удаляют собственные случайные схемы. Без POSTGRES_TEST_URL они явно пропускаются, поэтому зелёный запуск одних unit-тестов не подтверждает поведение базы.

## Как база принимает решение

1. Проверьте context, затем положительные ID, непустой после проверки пробелов UTF-8 ключ до 64 байт и UTF-8 body до 280 кодовых точек, не состоящий только из пробелов. Запретите NUL. Сохраняйте принятый ввод без изменений: начальные пробелы в непустом body значимы. Ключ отделён от грамматики ID корреляции урока 51; этот пример хранения принимает знаки пунктуации в ключе и передаёт все значения SQL-аргументами.

2. Выполните один INSERT с уникальным ограничением tenant_id, actor_id, command_key. Conversation — данные, связанные с ключом, а не часть области уникальности. RETURNING id определяет новую строку. При конфликте вставка ничего не делает, поэтому Scan возвращает sql.ErrNoRows. В identity-последовательности возможны пропуски; ID не показывает число сохранённых сообщений.

```sql
INSERT INTO lesson52_sends
    (tenant_id, actor_id, command_key, conversation_id, body)
VALUES ($1, $2, $3, $4, $5)
ON CONFLICT (tenant_id, actor_id, command_key) DO NOTHING
RETURNING id;
```

3. После конфликта выполните отдельный SELECT с теми же tenant, actor и key. Сравните сохранённые conversation и body точно в Go. Совпадение возвращает сохранённый ID с Created false; изменённые данные дают errConflict и нулевой результат. Победитель вставки сообщает Created true. Отдельный SQL-запрос важен при commit пересекающейся вставки: конфликтующая строка могла не быть видна snapshot исходного INSERT. См. документацию PostgreSQL по [INSERT](https://www.postgresql.org/docs/17/sql-insert.html) и [Read Committed](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED).

4. Пример не изменяет и не удаляет сохранённые строки. Их неизменяемый ввод служит квитанцией. Редактирование body, удаление строк или истечение квитанции нарушают гарантию повторов этого варианта. Реальной системе с редактируемыми сообщениями нужны отдельная неизменяемая квитанция и явная политика хранения. Схема и контракт урока сохраняют записи без очистки; ограничения ролей базы и миграции жизненного цикла находятся вне примера.

5. Ошибка ввода-вывода при INSERT может скрывать уже сохранённый результат. Верните ошибку, не придумывая успех и не утверждая rollback. Повторно получите результат с теми же областью, ключом и данными в рамках ограниченной политики повторов приложения. Конфликт не должен раскрывать старые body или ID. Created — диагностический признак, а не разрешение публиковать событие после транзакции: сбой между отправкой и публикацией потеряет событие. Этому посвящена практика.

## Практика · Сохраните одно outbox-событие новой отправки

Расширьте Send этого урока так, чтобы новая отправка и одно outbox-событие message.created сохранялись атомарно: объедините сохранённый ключ с границей транзакции из урока 27. Сохраните тип результата и исходное поведение. Не добавляйте worker и сетевую публикацию.

1. Добавьте таблицу outbox только для этого урока с уникальной ссылкой message_id и событием, содержащим сохранённые ID сообщения и беседы. Выполняйте вставку, чтение квитанции при необходимости и вставку нового события в одной явной транзакции READ COMMITTED. Повтор не создаёт событие. Возвращайте Created true только после успешного commit отправки и события. При любой предыдущей ошибке выполняйте rollback; ошибка commit возвращает нулевой результат и ошибку.

2. Сохраните точное сравнение области/данных и неизменяемую квитанцию. Совпадающие параллельные вызовы возвращают один ID и оставляют одну отправку и одно событие. Несовпадение body или conversation даёт конфликт без события. Разные tenant/actor/key независимы. Не устраняйте неопределённость сменой ключа или картой дедупликации в памяти.

3. Добавьте тесты базы для новой отправки, повтора после намеренного отбрасывания первого ответа, одновременных повторов, конфликтующих данных, ошибки вставки outbox и отложенного ограничения, падающего при commit. Проверяйте число строк обеих таблиц, данные события, нулевые результаты при ошибке и успешный повтор того же ключа после rollback транзакции. Сохраните исходные тесты. Объясните, почему потерянное подтверждение commit всё ещё требует получения сохранённого результата и почему идемпотентная запись не гарантирует доставку события.

```sh
gofmt -w lessons/52-command-idempotency/main.go lessons/52-command-idempotency/main_test.go
go test ./...
go test -race ./...
go vet ./...
```

## Типичные ошибки

- SELECT перед INSERT без уникального ограничения допускает гонку между процессами.

- Включение conversation в уникальный ключ позволяет одной команде создать сообщения в разных беседах.

- Сравнение только ключа незаметно принимает изменённые данные.

- Новый ключ после потери ответа создаёт новую операцию.

- Публикация события после автоматически сохранённой отправки оставляет окно сбоя.

- Удаление или редактирование неизменяемой квитанции превращает повтор в другую операцию.

## Критерии завершения

Запустите пример дважды с одной одноразовой базой. Покажите один сохранённый ID при повторе данных, отклонение изменённых данных и изоляцию доверенных областей. Выполните задание атомарного outbox без публикации после commit. Пройдите все тесты базы и общие проверки с заданным POSTGRES_TEST_URL; различайте сохранённый результат записи, доставку ответа и доставку события.
